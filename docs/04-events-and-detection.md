# Access-логи, обнаружение и дашборд

Нормативные источники: [Detector API](../contracts/detector-api.openapi.yaml), [AccessLog/LogBatch](../contracts/schemas/logs.yaml), [Incident](../contracts/schemas/detector.yaml), [правила завершения](../contracts/semantics.md).

## Источник данных

Shop и Gateway отправляют access-логи прямо в Detector по HTTP/JSON. Detector хранит их у себя. Control подготавливает анализ, передаёт границы потоков и получает только итоговые инциденты. Дополнительного сервиса сбора или SQL-проекции между компонентами нет.

Detector получает runId и HTTP-наблюдения, без режима vulnerable/protected, сценария, ATTACK/BENIGN, эталона, владельцев объектов или результата бизнес-проверки. Правила применяются к доступным признакам и могут ошибаться. Успешность атаки устанавливает отдельный Evaluator в Control по плану, ответам и БД.

## Одна запись на запрос

Каждый producer пишет одну запись после завершения обработки, включая отказы и исключения. Если Gateway остановил запрос до Shop, запись будет только у Gateway. При обычном проксировании два producer дают две записи одного requestId; Detector не считает их двумя запросами.

| Поле | Смысл |
|---|---|
| sequence | Номер 1..N отдельно для producer/run |
| requestId | UUID из X-Request-Id, связь с Runner и incident |
| time | Время завершения запроса в UTC |
| remote_addr | Вычисленный IP клиента, с учётом доверенного X-Forwarded-For |
| user | ID подтверждённого пользователя или null |
| method, path | HTTP-метод и исходный путь с query |
| route | Шаблон маршрута или null, если ещё не определён |
| status | Итоговый HTTP-код после обработки ошибок |
| bytes | Размер тела ответа без заголовков |
| request_time | Длительность в секундах |
| user_agent | User-Agent или null |
| req_hash | SHA-256 полного запроса по общему правилу или null |

req_hash вычисляется от method + LF + исходного path с query + LF + полного тела запроса; lowercase hex, 64 символа. Пустое тело допустимо; если прочитать полное тело не удалось, ставится null. Заголовки и requestId не входят в хэш. Поэтому разные order ID или query не схлопываются по одному route. Равный хэш означает совпадение содержимого, а не доказанную атаку Replay.

Пароли, JWT, Authorization и исходные тела в лог не попадают. Шаблон route, user и фактический итоговый status добавляются из результатов маршрутизации/аутентификации/обработки ошибок. Запись из finally до обработки исключения не должна ошибочно выдавать status=200. Подробная схема и валидный [пример пачки](../contracts/examples/log-batch.json) являются источником типов и nullable-полей.

## Доставка и полнота

1. Control вызывает prepareAnalysis для runId; Detector переходит в ACCEPTING. runId уже задан в URL и не дублируется в ответе статуса.
2. Producer отправляет LogBatch `{producer, entries}` в POST `/internal/v1/runs/{runId}/log-batches`. Ответ 204 без тела подтверждает сохранение всей пачки, включая повторы.
3. Сетевой retry сохраняет sequence и содержимое. Идентичный producer/sequence повтор допустим; изменённое содержимое - 409. Конкретная схема очереди и хранения является внутренней реализацией.
4. После CLOSED Gateway и Shop Control передаёт gatewayLastSequence, shopLastSequence и deadlineAt в finishAnalysis.
5. Detector ждёт непрерывные диапазоны 1..N, переходит через FINISHING в COMPLETED и публикует observedRequestIds. Пустой поток имеет N=0.
6. В FINISHING новые sequence принимаются только в объявленных границах. После COMPLETED/FAILED допустимы только идентичные сохранённые повторы; новые записи и изменённый finish дают 409. Граница finish ниже уже сохранённого sequence также даёт 409. Конфликт отклоняет пачку целиком.
7. Control сверяет observedRequestIds с attempts и читает итоговые incidents. До COMPLETED их получение даёт 409.

Отсутствие requestId попытки с transportOutcome=RESPONSE означает неполноту. У TIMEOUT запрос мог дойти и завершиться позже; сам timeout не определяет наличие записи или бизнес-эффекта.

До 100 записей в пачке, 64KiB на запись, 8MiB на пачку, 100000 записей/run/producer и до 100000 уникальных observedRequestIds: все запросы Shop проходят через Gateway. Последовательности могут доставляться с задержкой; наличие последнего номера не заменяет проверку всего диапазона. Перезапуск instanceId, пропуск записи и deadline делают результат INCONCLUSIVE. Client timeout не доказывает отсутствие операции или access-записи.

JSONL допустим как локальный формат файлов: одна JSON-запись на строку. Формат межсервисной доставки остаётся HTTP/JSON LogBatch. Файловые маркеры и чтение томов Control не требуются.

## Признаки для правил

| Наблюдение | Возможная интерпретация и ограничение |
|---|---|
| Много login 401 с одного IP, затем 200 | Подозрительная серия входов; по логам без login нельзя уверенно отличить stuffing от brute force |
| Последовательные ID в path, много 403/404 | Возможный перебор объектов; принадлежность объекта по логу неизвестна |
| SQL-подобный query, изменение status/bytes | Возможная injection; апострофы бывают легитимными, успешность SQL-вмешательства не доказана |
| Повтор req_hash одного пользователя | Возможный Replay или обычный технический retry |
| Всплеск обращений к cart/orders | Подозрительное поведение; нарушение цены, купона или атомарности по access-логу не доказать |

Пороги и окна задаёт реализация Detector до испытания. User-Agent скрипта, отдельный 404, высокий темп или совпадение хэша сами по себе не являются надёжной классификацией. Правила не используют UUID, номер режима или заранее выбранный виртуальный IP как метку атаки.

## Инцидент и UI

Incident содержит incidentId, detectedAt, непустой requestIds, description и необязательный family. Неизвестное семейство опускается или равно null. Инцидент сообщает подозрение на попытку, а не доказанный успех. Итоговые инциденты неизменяемы; ручного статуса подтверждения/отклонения в API нет.

Control добавляет IncidentAssessment: verdict TRUE_POSITIVE/FALSE_POSITIVE/UNASSESSED, matchedEpisodeIds и reason. Подтверждённая попытка может быть TRUE_POSITIVE и при блокировке. Отсутствие или ошибочный family не превращает обнаружение в FALSE_POSITIVE; ошибку классификации Control поясняет в reason. Подготовительный login или общий IP не подтверждают атакующий episode.

Дашборд получает прогресс через GET trial, итоговые инциденты и оценку - внутри общего TrialReport. Он вычисляет показатели из cases/incidents. При незавершённом анализе incidents=null, а detection у cases - INCONCLUSIVE; это не отсутствие атак. JSON-отчёт можно сохранить как файл на стороне UI без отдельного export API. Тела запросов, JWT и пароли не экспортируются.

Физические таблицы хранения Detector и Control не являются частью OpenAPI. [Историческая SQL-модель](data/legacy-lab/README.md) не используется как инструкция миграции действующей архитектуры.

Поле detection вычисляется по [таблице правил](../contracts/semantics.md): подтверждённый ATTACK episode - DETECTED, benign episode с инцидентом - FALSE_POSITIVE; MISSED/CLEAN требуют полной серии шагов и логов. Неполные данные и неразрешённая оценка дают INCONCLUSIVE. Связанный TP и MISSED в одном episode недопустимы.
