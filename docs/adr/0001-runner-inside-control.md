# ADR-0001. Runner внутри lab-control

Дата: 1 ноября 2026 года. Статус: предложен для ревью в [задаче #21](https://github.com/Valentin92257/api-security-lab/issues/21).

Основание: [архитектура](../01-architecture.md#встроенное-исполнение-сценариев), [модель эксперимента](../05-scenarios-and-experiments.md) и [HTTP-контракты](../../contracts/README.md).

## Контекст

Control готовит данные, управляет Shop/Gateway и Detector, оценивает результат и собирает отчёт.
Runner исполняет план нагрузки по вызову Control. Один trial включает два последовательных
run: VULNERABLE, затем PROTECTED, с одинаковыми seed, данными и планом.

В MVP работает один экземпляр Control и один активный trial. Независимое масштабирование runner и продолжение прерванного run не требуются.

## Решение

Runner - пакет `lab.control.runner` внутри lab-control. Control вызывает его через
Java-интерфейсы, без отдельного HTTP API и контейнера.

### Границы ответственности

| Компонент | Что делает |
|---|---|
| Control API | Проверяет запрос оператора, создаёт trial, возвращает состояние |
| Orchestrator | Управляет двумя прогонами, подготовкой, отменой и финализацией |
| Fixture | Готовит данные напрямую в БД при закрытых runtimes |
| Runner | Исполняет план: последовательности, конкурентные группы, HTTP-попытки и повторы |
| Хранение Control | Сохраняет план, результаты попыток и отчёт |
| Evaluator | Независимо оценивает эффект атаки и инциденты |

Runner получает план, учебных пользователей, встроенный target, лимиты, deadline
и сигнал отмены. Результаты сохраняет через адаптер Control. Java-интерфейсы вводятся
при реализации, внешние DTO используются на границе HTTP API.

Подготовкой БД и оценкой эффекта управляет Control. Сценарный код не получает datasource, Fixture, Runtime-клиенты и evaluator.

### Исполнение и ограничения

Runner использует отдельный executor; API и управление экспериментом работают в своих потоках.
Для HTTP I/O допустимы virtual threads с semaphore. Лимиты одновременных запросов,
попыток, очередей, тел и результатов задаются до запуска.

Runner проверяет deadline и отмену перед шагом, HTTP-попыткой, повтором и ожиданием барьера.
При отмене, ошибке сохранения или переполнении новые действия прекращаются.
Завершение подтверждается после сохранения результатов всех начатых запросов.

HTTP-клиент принимает встроенный target и маршрут из каталога. Запросы идут через
фиксированные входы Gateway. Произвольные URL, перенаправления, прокси и служебные маршруты запрещены.
Каждая попытка получает новый UUID в `X-Request-Id`. Повтор бизнес-операции сохраняет её ключ идемпотентности.

В результатах сохраняются только разрешённые поля ответа, без паролей, JWT и секретных тел. Detector получает access-логи без сценарных labels и приватного эталона Control.

### Слот исполнения

Trial, ключ идемпотентности и единственный слот хранятся в PostgreSQL.
Создание trial, сохранение ключа и резервирование слота выполняются в одной транзакции.
Правила создания и повторов описаны в [семантике Control API](../../contracts/semantics.md#создание-trial).

Слот освобождается после завершения и подтверждения `cleanupSafe`. Терминальный статус сам по себе не разрешает новый запуск.

### Завершение и сбои

Завершением управляет Control:

1. Остановить новые действия runner и сохранить результаты попыток.
2. Закрыть Gateway и дождаться CLOSED, затем закрыть Shop и дождаться CLOSED.
3. Передать окончательные lastSequence в Detector и дождаться COMPLETED анализа.
4. Проверить полноту данных, выполнить oracle и сохранить отчёт.

Таймаут или отмена HTTP-клиента не подтверждают завершение SQL в магазине.
До подтверждения безопасного завершения `cleanupSafe=false`, сброс данных запрещён.

После перезапуска Control до приёма HTTP-запросов незавершённый trial получает
INCONCLUSIVE и `cleanupSafe=false`. Ключ сохраняется, слот остаётся занят.
Перезапуск другого компонента или потеря обязательных результатов также дают INCONCLUSIVE.
Прерванное исполнение не возобновляется.

## Рассмотренные варианты

| Вариант | Почему не выбран |
|---|---|
| Отдельный сервис runner | Нужны сетевой протокол, аутентификация и доставка результатов. Независимое масштабирование в MVP не требуется |
| Внешний процесс или скрипт | Нужны управление процессом и протокол результатов. Пользовательский код стенд не исполняет |
| Выполнение в HTTP-потоке Control | Занимает поток API на всё время эксперимента и связывает run с запросом оператора |

Решение стоит пересмотреть, если понадобятся несколько workers, независимое масштабирование или изоляция отказов runner.

## Последствия

Один процесс упрощает запуск и передачу результатов.

Heap, CPU, GC и права JVM общие. OOM runner может остановить Control.
Зависимости от JDBC/admin/evaluator проверяются архитектурными тестами при реализации модулей.
Это граница доверенного кода внутри JVM. Контейнер Control работает без доступа в интернет.

## Что входит в задачу #21

ADR и каркас создания и чтения trial с PostgreSQL. Сейчас POST создаёт trial в PREPARING
и занимает слот; исполнение, отмена и безопасная финализация подключаются следующими задачами.
Целевой контракт с автоматическим запуском обоих режимов остаётся в OpenAPI.
Миграции выполняет отдельный init job; HTTP-приложение получает только runtime-права БД.
