# ADR-0001. Runner внутри lab-control

Дата: 1 ноября 2026 года. Статус: предложен для ревью в [задаче #21](https://github.com/Valentin92257/api-security-lab/issues/21).

Основание: [архитектура](../01-architecture.md#встроенное-исполнение-сценариев), [модель эксперимента](../05-scenarios-and-experiments.md) и [HTTP-контракты](../../contracts/README.md).

## Контекст

Runner исполняет план нагрузки на учебный магазин и передаёт результаты Control. Его вызывает только lab-control.

Control готовит данные, управляет Shop/Gateway и Detector, оценивает результат и собирает отчёт. Один trial включает два последовательных run: VULNERABLE, затем PROTECTED. У них одинаковые seed, исходные данные и план нагрузки.

В MVP работает один экземпляр Control и один активный trial. Независимое масштабирование runner и продолжение прерванного run не требуются.

## Решение

Runner остаётся в пакете `lab.control.runner` внутри lab-control. Control вызывает его через Java-интерфейсы. Отдельные HTTP API и контейнер не нужны.

### Границы ответственности

| Компонент | Что делает |
|---|---|
| Control API | Проверяет запрос оператора, создаёт trial, возвращает состояние |
| Orchestrator | Управляет двумя runs, подготовкой, отменой и финализацией |
| Fixture | Готовит данные напрямую в БД при закрытых runtimes |
| Runner | Исполняет план: последовательности, конкурентные группы, HTTP-попытки и повторы |
| Хранение Control | Сохраняет план, результаты попыток и отчёт |
| Evaluator | Независимо оценивает эффект атаки и инциденты |

Runner получает план, подготовленных учебных пользователей, встроенный target, лимиты, deadline и сигнал отмены. Результаты сохраняет через адаптер Control. Java-интерфейсы вводятся вместе с реализацией; внешние DTO используются на границе HTTP API.

Подготовкой БД и оценкой эффекта управляет Control. Сценарный код не получает datasource, Fixture, Runtime-клиенты и evaluator.

### Исполнение и ограничения

У runner отдельный executor. HTTP API и управление экспериментом используют свои потоки. Для HTTP I/O допустимы virtual threads с semaphore. Число одновременных запросов, попыток, размер очередей, тел и результатов ограничиваются до запуска.

Runner проверяет deadline и отмену перед шагом, каждой HTTP-попыткой, повтором и ожиданием барьера. При отмене, ошибке сохранения или переполнении он прекращает новые действия. Завершение подтверждается после сохранения результатов всех начатых запросов.

HTTP-клиент принимает встроенный target и маршрут из каталога. Бизнес-запросы идут через фиксированные входы Gateway; произвольный URL, redirects, proxy и служебные маршруты запрещены. Каждая попытка получает новый UUID в `X-Request-Id`. Повтор той же бизнес-операции сохраняет её ключ идемпотентности.

В результатах сохраняются только разрешённые поля ответа, без паролей, JWT и секретных тел. Detector получает access-логи без сценарных labels и приватного эталона Control.

### Создание эксперимента

`POST /control/v1/trials` принимает от одного до пяти известных families и необязательный seed. Заголовок `Idempotency-Key` обязателен. Если seed не передан, Control выбирает его один раз и возвращает в trial.

Проверка ключа и резервирование единственного слота выполняются атомарно:

1. Тот же ключ и тело возвращают существующий trial с HTTP 200. Эта проверка выполняется до проверки занятого слота.
2. Тот же ключ с другим телом даёт 409.
3. Новый ключ при занятом слоте даёт 409.
4. Новый trial получает PREPARING и HTTP 202. После подключения управления runs эта же операция запускает оба режима. Отдельная команда start не вводится.

Слот освобождается после завершения и подтверждения `cleanupSafe`. Терминальный статус сам по себе не разрешает новый запуск.

Families сравниваются как набор. Порядок families, JSON-полей и запись одного числа
как `42`, `42.0` или `4.2e1` не меняют запрос. Для seed отдельно хранится признак
его отсутствия. Если первый запрос был без seed, повтор с явным seed даёт 409,
даже если значение совпадает с выбранным.

### Завершение и сбои

Завершением управляет Control:

1. Остановить новые действия runner и сохранить attempts.
2. Закрыть Gateway и дождаться CLOSED, затем закрыть Shop и дождаться CLOSED.
3. Передать окончательные lastSequence в Detector и дождаться COMPLETED анализа.
4. Проверить полноту данных, выполнить oracle и сохранить отчёт.

Timeout или отмена HTTP-клиента не подтверждают завершение SQL в магазине. Пока Control не подтвердил безопасное завершение, `cleanupSafe=false` и reset запрещён.

Trial, ключи идемпотентности и слот хранятся в PostgreSQL. При перезапуске Control
незавершённый trial получает INCONCLUSIVE и `cleanupSafe=false` до приёма HTTP-запросов.
Слот остаётся занят. Перезапуск другого участника или потеря обязательных результатов
также дают INCONCLUSIVE; прерванное исполнение не возобновляется.

## Рассмотренные варианты

| Вариант | Почему не выбран |
|---|---|
| Отдельный сервис runner | Нужны сетевой протокол, аутентификация и доставка результатов. Независимое масштабирование в MVP не требуется |
| Внешний процесс или скрипт | Нужны управление процессом и протокол результатов. Пользовательский код стенд не исполняет |
| Выполнение в HTTP-потоке Control | Занимает поток API на всё время эксперимента и связывает run с запросом оператора |

Решение стоит пересмотреть, если понадобятся несколько workers, независимое масштабирование или изоляция отказов runner.

## Последствия

Один процесс упрощает запуск и передачу результатов. Runner можно разрабатывать отдельно по Java-интерфейсам внутри Control.

Heap, CPU, GC и права JVM общие: OOM runner может остановить Control.
Границы доступа к JDBC/admin/evaluator проверяются архитектурными тестами при реализации
этих модулей. Это ограничение доверенного кода внутри JVM. Внешний egress запрещается
для всего контейнера Control.

## Что входит в задачу #21

ADR и каркас создания и чтения trial с PostgreSQL по [плану задачи](../plans/21-lab-control.md).
Сценарии, Fixture, Runtime API, Detector, evaluator и UI подключаются следующими задачами.

Сейчас POST только создаёт trial в PREPARING и занимает слот. Исполнение, отмена
и безопасная финализация ещё не реализованы. Целевой контракт с автоматическим запуском
обоих режимов остаётся в OpenAPI. Миграции выполняет отдельный init job;
HTTP-приложение получает только runtime-права БД.
