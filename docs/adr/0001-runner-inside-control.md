# ADR-0001. Runner внутри lab-control

1 ноября 2026 года. Статус: предложен для ревью в [задаче #21](https://github.com/Valentin92257/api-security-lab/issues/21).

## Решение

Runner - пакет `lab.control.runner` внутри Control с Java-интерфейсами, без отдельного HTTP API и контейнера.
В MVP один Control и один активный trial: VULNERABLE, затем PROTECTED с одинаковыми seed, данными и планом.
Независимое масштабирование и продолжение прерванного run не требуются.

Control готовит БД, управляет Runtime/Detector, оценкой и отчётом. Runner исполняет план, сохраняя результаты через адаптер Control.
Сценарный код не получает datasource, Fixture, Runtime-клиенты и evaluator; внешние DTO остаются на границе HTTP API.

У runner отдельный executor и лимиты запросов, попыток, очередей, тел и результатов.
Deadline и отмена проверяются перед каждым действием и ожиданием. Ошибка сохранения или переполнение останавливают новые действия.
Завершение подтверждается после сохранения результатов всех начатых запросов.

HTTP идёт только через фиксированные входы Gateway; произвольные URL, перенаправления, прокси и служебные маршруты запрещены.
Каждая попытка получает новый `X-Request-Id`, повтор сохраняет бизнес-ключ идемпотентности.
В результатах нет секретов; Detector не получает метки сценария и эталон Control.
Подготовка и безопасное завершение описаны в [архитектуре](../01-architecture.md#завершение-и-очистка).

## Альтернативы и последствия

Отдельный сервис добавит сетевой протокол и аутентификацию, внешний процесс - управление его жизненным циклом.
Запуск в HTTP-потоке займёт его на весь эксперимент. Для MVP достаточно отдельного executor.

Один процесс упрощает запуск, но heap, CPU, GC и права JVM общие: OOM runner может остановить Control.
Код внутри JVM доверенный; запреты зависимостей проверим архитектурными тестами при реализации runner. Доступ в интернет закрыт.
Решение пересматривается при нескольких workers, независимом масштабировании или необходимости изоляции отказов.

## Что входит в задачу #21

Создание и чтение trial с PostgreSQL. Trial, ключ идемпотентности и слот сохраняются атомарно; правила повторов - в [контракте](../../contracts/semantics.md#создание-trial).
Trial остаётся PREPARING. После перезапуска до приёма HTTP он получает INCONCLUSIVE и `cleanupSafe=false`; ключ и занятый слот сохраняются.
Исполнение, отмена и безопасная финализация появятся позже. Слот освобождается только после подтверждения `cleanupSafe`.
Миграции выполняются отдельно; HTTP-приложение получает DML-права, без DDL и административного пароля.
