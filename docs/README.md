# API Security Lab

Версия документации 1.8, 25 октября 2026 года. Это самостоятельная стартовая спецификация проекта; реализация сервисов и измерения ещё предстоят. Актуальные [OpenAPI-контракты](../contracts/README.md), Java-порты и генерация кода уже находятся в репозитории.

API Security Lab - локальный учебный стенд для исследования защиты API. Синтетический магазин предоставляет объекты и операции; основной результат - воспроизводимое сравнение уязвимого и защищённого режимов, объяснимые решения защиты, независимое обнаружение и подтверждённая оценка эффекта.

Пользователь выбирает семейства атак и seed, запускает эксперимент, изучает incidents/evidence и экспортирует отчёт. Система раздельно показывает, достиг ли атакующий цели, сработала ли защита, обнаружено ли поведение и достаточно ли доказательств для вывода.

## Схемы

`api-security-lab.html` - автономный альбом из 12 основных схем, согласованный с этой спецификацией: семь архитектурных видов и моделей, пять sequence-диаграмм. Файл открывается в браузере без сервера и интернета; все SVG и пояснения встроены. Оформление - светло-серый фон, холодные голубые акценты и градации серого.

Порядок: назначение стенда → компоненты и четыре роли → изоляция трафика → эксперимент, события и независимый эталон → контрольные точки защиты → detector и evaluator → состояния run → BOLA → login limits → checkout retry/replay → структурированные логи и обработка → FINALIZING. Под каждой схемой раскрываются детали контрактов и границы упрощения. Восемь Markdown-документов и этот HTML составляют итоговый комплект.

## Команда

| Роль | Ответственность и поставка |
|---|---|
| Р1. Разработчик API и данных | Shop в двух режимах, OpenAPI/DTO, миграции/фикстуры, транзакции/owner-check, access logging и readonly данные oracle |
| Р2. Разработчик защиты | Gateway/политики/JWT, limiter, access logging, Runtime/lastSequence, сети/Compose и базовая наблюдаемость |
| Р3. Разработчик атак | Runner, catalog scenarios/benign, seed/планы, concurrency, встроенный executor/cancel и результаты шагов |
| Р4. Разработчик детектора и дашборда | Detector/rules/incidents; control/orchestration/Fixture/evaluator и интеграция runner, UI, метрики и отчёты |

Четыре роли обслуживают четыре Java-приложения: shop-api, lab-gateway, lab-detector, lab-control. Scenario-runner - внутренняя библиотека control с отдельным executor и лимитами; Р3 продолжает отвечать за неё. Shop запускается двумя экземплярами; detector выделен для изоляции данных и независимого обнаружения. Чтобы Р4 не стал узким местом, Р1 поставляет fixture/oracle adapters, Р2 - управление допуском и полнотой access-логов, Р3 - интерфейсы исполнения, отмены и результатов. Независимые проверки совместно ревьюят Р1, Р3 и Р4.

Gateway один, лимиты Bucket4j и backoff хранятся в его памяти. В базовом стенде семь контейнеров: пять Java-процессов, PostgreSQL и LGTM. Перезапуск прерывает опыт; репликация gateway не входит в MVP.

## Объём и границы

Обязательны регистрация/login/профиль по ID, поиск каталога, чтение корзины, установка количества/купона, создание и чтение заказа; пользователей и начальные данные готовит fixture-модуль; общий контракт двух режимов; пять семейств угроз со всеми business subcases; gateway; отдельный detector; UI; независимые oracle; JSON-export; logs/traces и security regression suite. Политики конфигурируются до run, данные синтетические, цели встроенные и локальные.

Магазин остаётся модульным API. Платежи/возвраты, внешние цели, универсальное исполнение пользовательских атак, отдельные доменные микросервисы, broker, SPA и ML в обязательный результат не входят. OpenFGA, Schemathesis, PyOD, mTLS и sender-constrained tokens допустимы как отдельные дальнейшие исследования.

Protected гарантирует описанные owner-check и бизнес-инварианты. Действительный access JWT многократен; checkout защищён версией корзины и транзакционной идемпотентностью. Первая корректная пара credentials и новые допустимые операции с украденным bearer остаются рисками выбранной модели. Базовое допущение: процессы и хранилища работают непрерывно во время опыта. Источник Detector - итоговые access-логи API/Gateway, передаваемые напрямую по HTTP/JSON; Detector хранит их сам, Control получает итоговые incidents. Бизнес-commit и запись лога не атомарны; продолжение run после сбоя не реализуется. Неполные access-логи или перезапуск процесса не превращается в успешное предотвращение или FN: run получает INCONCLUSIVE.

Готовность означает работающий путь от создания эксперимента до отчёта, сопоставимые runs, подтверждённые инварианты и воспроизведённые учебные слабости, осмысленные benign-контроли, автоматическую приёмку и запуск на описанной чистой машине. Порог качества detector и результаты performance публикуются только после измерения с видимыми знаменателями и ограничениями.
