Что делает API Security Lab

Учебный эксперимент сравнивает защиту двух режимов API, обнаружение угроз и доказанный эффект атакующего.

Пояснения и границы схемы

Детали и допущения

  • Один experiment содержит последовательные vulnerable/protected runs с одинаковыми fixture, seed, business-time base, workload, concurrency и ruleset. Порядок targets чередуется при повторениях; concurrency внутри race сохраняется.
  • Vulnerable использует учебные shop-стратегии и OBSERVE экспериментальных gateway-политик; protected — защищённые стратегии и ENFORCE. JWT, ресурсные пределы, admission и audit обязательны в обоих режимах.
  • Case effect — EFFECT_OBSERVED / EFFECT_NOT_OBSERVED / ERROR / INCONCLUSIVE. Отдельно проверяются инварианты HELD / VIOLATED / NOT_APPLICABLE. Например, первая корректная чужая пара credentials может дать доступ при корректной работе парольной аутентификации.
  • ASR считается по оценимым malicious cases, recall и benign FPR — по полностью наблюдённым episodes, precision — по FINAL incidents. Benign workload нужен также для false block rate. Отчёт сохраняет знаменатели, coverage и причины исключений.
  • HTTP-код и incident сами по себе не доказывают эффект или предотвращение. Обязателен JSON-export; Markdown — дополнительный формат. Это проектная модель без заявленных результатов измерений.

Основные компоненты стенда

Control объединяет управление, UI и сценарный runner. Gateway и API пишут JSONL; отдельный detector анализирует безопасную проекцию.

Пояснения и границы схемы

Детали и допущения

  • Четыре Java-приложения: lab-control, lab-gateway, shop-api и lab-detector. Shop работает в двух экземплярах; вместе с PostgreSQL и LGTM — семь постоянных контейнеров.
  • Р1 реализует оба API и данные; Р2 — gateway/политики; Р3 — библиотеку modules/scenario-runner; Р4 — detector, orchestration, UI, log-ingestor и evaluator. Объединение приложений не объединяет роли участников.
  • Runner — модуль lab-control с отдельным executor, semaphore, конечными бюджетами и cancellation token. Вызовы prepare/start/cancel и AttemptSink — Java, без HTTP, heartbeat или lease. UI не ждёт окончания сценария в servlet-потоке.
  • Один активный run; target enum выбирает фиксированный gateway listener 8081 либо 8082. Произвольные URL/redirects/proxy запрещены ScenarioHttpClient. Контейнер control не имеет внешнего egress.
  • Control имеет admin/SQL/log mounts, поэтому внутри общей JVM нет сетевого sandbox для runner. Сценарные классы используют только ограниченные порты; зависимости от JDBC/admin/evaluator запрещены правилами сборки и ArchUnit. Сценарии — доверенный код репозитория.
  • Gateway/shop пишут собственные JSONL без credentials lab DB. Сборщик читает volumes readonly и индексирует audit; блок «Сборщик + Lab DB» — группа модуля существующего control и PostgreSQL, не новый сервис.
  • Detector остаётся отдельным процессом с SQL whitelist-view без приватного эталона. Control ждёт результаты runner, полноту логов и detector CLOSE; затем выполняет oracle/report. Общие heap/CPU control остаются общей областью отказа.

Сценарный трафик проходит через gateway

Показан сценарный HTTP из встроенного runner через gateway. Административные и SQL-связи общего процесса control здесь опущены.

Пояснения и границы схемы

Детали и допущения

  • На рисунке только сценарный HTTP: встроенный runner в lab-control → gateway → выбранный shop. Две ветки означают разные runs, а не возможность указать backend в запросе.
  • Control входит в lab-traffic, shop-admin, lab-data и lab-observe. Эти административные и SQL-связи опущены; рисунок не утверждает, что контейнер control физически изолирован от shop/DB.
  • ScenarioHttpClient принимает target enum и разрешённый route, запрещает arbitrary origin, absolute URL override, proxy, redirects и management endpoints. Сценарный модуль не получает admin/datasource/log-reader interfaces; это граница доверенного кода одной JVM.
  • Контейнеры не имеют внешнего egress, Docker socket, host network или privileged-режима. Только UI/Grafana опубликованы на loopback; gateway доступен вручную в opt-in profile. Отсутствие published port не является ACL между контейнерами.
  • Gateway выбирает backend по local listener port 8081/8082. Host/query/headers не меняют target. /internal/** не проксируется бизнес-входом; admin endpoints защищены отдельными credentials и binding.
  • Проверки разделены: сетевые тесты внешнего egress control, контрактные тесты ScenarioHttpClient против обхода gateway и ArchUnit против запрещённых зависимостей модуля. Внутри JVM не обещается изоляция от злонамеренного Java-кода.

Эксперимент, события и независимый эталон

События и инциденты отделены от приватного эталона; эффект атаки, инварианты и качество обнаружения имеют разные результаты.

Пояснения и границы схемы

Детали и допущения

  • Это концептуальная ER-модель, не физическая DDL. Физическое соответствие: Эксперимент — control.experiments; Прогон — control.runs; SecurityEvent — audit.security_events через audit.detector_observations; Приватный эталон — control.experiments.definition и control.runs.fixture_manifest; результаты и оценки — control.reports.body; инцидент, evidence и история — detection.incidents. Case/episode/assessment на схеме — вложенные объекты, а не отдельные SQL-таблицы. Результаты и оценки относятся к control.reports.revision. Полные поля и FK: подробные ER-схемы, DBML и SQL в data. 1:N обозначает связь с множеством, допускающим ноль элементов; M:N — необязательные связи через evidence или matching. Run содержит один target; experiment объединяет сравниваемые runs.
  • Приватный эталон до запуска задаёт cases/episodes, benign/malicious labels, attack-specific steps, цели, владельцев и oracle. Один эталон применяется в нескольких runs. Episode — единица detection recall и benign FPR; case/subcase — единица оценки эффекта.
  • SecurityEvent имеет CloudEvents envelope specversion/id/source/type/time/datacontenttype/dataschema и вложенный data. На схеме приведены сокращённые пути полей. Raw audit доступен control; detector получает whitelist-view без scenario/case/step, target, policy mode, labels и oracle.
  • Результат случая хранит effect EFFECT_OBSERVED / EFFECT_NOT_OBSERVED / ERROR / INCONCLUSIVE и отдельно invariant verdicts HELD / VIOLATED / NOT_APPLICABLE. Эффект атакующего не обязательно означает ошибку конкретного защитного механизма.
  • Incident содержит evidence event IDs, rule/ruleset version и analysisState PROVISIONAL / FINAL / RETRACTED. Operator status OPEN / ACKNOWLEDGED / RESOLVED — другая ось. Детектор описывает impact только как SUSPECTED/UNKNOWN.
  • IncidentAssessment создаёт evaluator: TP/FP/UNASSESSED, matched episodes и confirmedImpact. Связь incident→assessment 1:N допускает новые report revisions. Evidence сопоставляется через request и attack-specific step, с проверкой класса угрозы. FN хранится у episode без искусственного incident.
  • Log streams, steps/attempts, detection jobs/processed markers и отчёты опущены. События поступают из JSONL через log-ingestor в control. Итоговый immutable report объединяет эти данные только после проверки полноты и detector CLOSE. Общая lab DB не даёт detector права читать control.

Защита: где выполняется каждая проверка

Gateway исполняет цепочку политик, API сохраняет инварианты, а отдельный detector анализирует события по YAML-правилам.

L1–L4 — где выполняются проверки. OFF / OBSERVE / ENFORCE — как работает выбранная политика gateway. Режимы не относятся к отдельным уровням API или БД.

Какие защиты отключаются и как сравниваются прогоны

Уровни и режимы — разные вещи

  • L1–L4 показывают места выполнения проверок: gateway, API, PostgreSQL и detector. Нижние карточки OFF / OBSERVE / ENFORCE — три возможных режима каждой экспериментальной политики gateway. Они не соответствуют уровням API/БД и не являются тремя этапами обработки запроса.
  • Схема контрольных точек показывает protected-реализацию: L1–L3 предотвращают недопустимые эффекты, L4 асинхронно обнаруживает поведение. Это не четыре последовательных сетевых вызова.

Что можно отключать в gateway

  • Schema validation, login limits и дополнительные input signals имеют режим, выбранный до начала run. OFF: проверка не вычисляется, evaluationStatus=SKIPPED, wouldDecision=null, состояние политики не меняется; сама эта политика пропускает запрос дальше.
  • OBSERVE: политика вычисляет решение и пишет его в security-лог, но сама не блокирует запрос. Например, превышение login limit записывается как wouldDecision=BLOCK при enforcedAction=CONTINUE. Shadow-счётчики отделены от ENFORCE и других runs.
  • ENFORCE: вычисленное BLOCK приводит к REJECT, ALLOW или FLAG — к CONTINUE. После первого отказа следующие экспериментальные проверки получают NOT_REACHED. При NOT_APPLICABLE/NOT_REACHED/MISSING_CONTEXT/ERROR wouldDecision=null, а не ALLOW.
  • CONTINUE означает только прохождение данной политики: другая обязательная проверка gateway или предметная защита API всё ещё может отказать. Snapshot режимов и параметров фиксируется до запуска; во время run переключений нет.

Как запускается эксперимент без исследуемых защит

  • Основная сравниваемая пара: vulnerable API с OBSERVE для экспериментальных политик gateway и protected API с ENFORCE. В первом прогоне gateway наблюдает попытки и пропускает их к намеренно ослабленным адаптерам магазина; во втором применяет блокировки, а магазин проверяет свои инварианты.
  • OFF нужен для отдельного baseline без вычисления выбранной политики. Для оценки вклада одной политики фиксируют backend, fixture, workload и остальные настройки, меняя только её режим. Сравнение общей пары vulnerable/protected показывает совокупный эффект защит, а не вклад одного gateway.
  • OFF/OBSERVE в gateway не отключают owner-check, параметризованный SQL и ограничения protected API/БД. Для воспроизведения учебных слабостей выбирается vulnerable backend; выбор backend и режимы политик — разные настройки.

Что остаётся обязательным

  • Изоляция локального стенда, admission активного run, технические пределы размера/времени/параллельности, security-логирование и JWT на закрытых маршрутах включены в обоих режимах. Это эксплуатационные границы опыта, а не переключаемые политики исследования.
  • Admission допускает только назначенный активный run; технический бюджет ограничивает ресурсы. Его согласуют с планом и задают с запасом относительно исследуемой нагрузки. Если технический предел мешает выполнить сценарий, это ограничение/ошибка опыта, а не доказательство срабатывания изучаемой защиты.
  • Проверка JWT не мешает заявленным сценариям: credential stuffing идёт через публичный login, а BOLA/replay/бизнес-злоупотребления выполняются с действительными тестовыми токенами. Наличие токена удостоверяет пользователя, но не право на чужой объект и не допустимость повторного бизнес-эффекта.

Логи, инварианты и оценка

  • Gateway сначала проверяет admission/ресурсный бюджет, затем JWT там, где он обязателен, и экспериментальные политики в выбранных режимах. Start и policy facts записываются до proxy, terminal — после результата; ранние отказы тоже попадают в security-лог. Логи содержат наблюдения, а не готовый диагноз успешной атаки.
  • Owner-check и параметризованный SQL находятся в shop. Checkout использует порядок locks key → cart → coupon; order/items, cart revision и сохранённый успешный ответ фиксируются одной SQL-транзакцией. Лог пишется после commit/rollback и не атомарен с БД.
  • Лимиты хранятся в памяти единственного gateway. Переполнение бюджета ключей или внутренняя ошибка limiter дают 503/INFRA_REJECT и INCONCLUSIVE независимо от mode; активные ограничения не вытесняются. Ошибка обязательного логирования до downstream не позволяет вызвать shop. Restart прерывает опыт.
  • Detector создаёт incidents по фактам, не блокирует HTTP и не читает эталон. Evaluator отдельно проверяет эффект атаки, инварианты и качество обнаружения. WouldBlock из OBSERVE описывает наблюдённый поток и не является точным прогнозом поведения ENFORCE.

Детектор наблюдает, evaluator проверяет

Эталон и независимый oracle доступны оценщику, а детектор получает только допустимые наблюдения.

Пояснения и границы схемы

Детали и допущения

  • Верхний путь — наблюдение и обнаружение; нижний — независимая оценка внутри lab-control. Это потоки данных, не полный список сетевых вызовов. EVENTS означает JSONL-файлы → log-ingestor в control → audit; промежуточный сборщик на этом виде опущен. PostgreSQL один, но SQL grants разделяют audit, detection и private control.
  • Safe view допускает только фиксированные facts/outcomes, нормализованный producerKind GATEWAY/SHOP и непрозрачную partition. Она исключает source URI, target/backend name, policy mode/snapshot, scenario/case/step, labels и oracle results. Correlation IDs служат join/evidence, но не классификационными признаками правил.
  • Эталон фиксируется до запуска. Oracle проверяет разрешённые поля ответа, before/after committed state и доверенные fixture snapshots через readonly доступ. Production calculator, BLOCK или incident не заменяют независимую проверку.
  • Case effect и invariant verdicts независимы. Первая корректная чужая пара credentials может достигнуть цели при корректной парольной аутентификации. Ошибка инфраструктуры не превращается в успешную защиту.
  • В live-потоке incidents PROVISIONAL. После подтверждения полного набора событий CLOSE пересчитывает окна и делает результаты FINAL либо RETRACTED; история сохраняется. Схема показывает оценку FINAL incidents после DRAINING.
  • Evaluator сопоставляет evidence event → request → attack-specific step и класс угрозы, создаёт TP/FP/UNASSESSED assessment и подтверждает impact. FN относится к episode без incident. Совпадения run/source или подготовительного login недостаточно.
  • ASR считается по cases, recall/benign FPR — по episodes, precision — по incidents. В отчёте видны знаменатели и coverage; нулевой знаменатель — N/A. Неполный run INCONCLUSIVE не участвует в окончательном paired comparison.
  • Ruleset snapshot фиксируется до PREPARE. CLOSE передаёт detector только безопасные event IDs через detection.jobs.expected_event_ids и ожидаемый hash. Детектор не получает полный evaluation manifest или приватный эталон.

Жизненный цикл одного прогона

Любой выход из RUNNING проходит DRAINING; terminal state сам по себе не разрешает сброс данных.

Пояснения и границы схемы

Детали и допущения

  • Показаны CREATED, PREPARING, RUNNING, DRAINING, EVALUATING, COMPLETED, FAILED, CANCELLED, INCONCLUSIVE. Переходы сохраняются с revision/CAS; сохранение state не означает возможность продолжить run после restart.
  • PREPARING закрывает admission, устанавливает и проверяет фикстуру, регистрирует gateway/shop streams и sourceInstanceId, получает detector READY и локальный prepare(planHash). Затем допускается RUNNING.
  • STOP означает конец плана, cancel или fatal. Выход из RUNNING проходит DRAINING; desired terminal state хранится отдельно. При сбое процессы не возобновляют прежнюю работу, run заканчивается INCONCLUSIVE.
  • DRAINING закрывает admission и ждёт in-flight=0 при неизменных работающих процессах. Producers пишут STREAM_END; collector проверяет seq и пары started/completed, сверяет результаты runner. Затем detector получает CLOSE.
  • Дедлайн, missing EVENT/result/terminal/END, смена instance или неподтверждённый ACK означают INCONCLUSIVE. Client timeout сам по себе не означает завершения SQL.
  • EVALUATING получает readonly конечное состояние и выполняет независимые oracle. COMPLETED означает достоверность отчёта, а не обязательно эффективность защиты.
  • cleanupSafe=true требует отсутствия старых работ. После отказа сначала останавливаются старые исполнители, стенд перезапускается и подготавливается новый опыт. Reset по одному истечению таймера запрещён.
  • Для читаемости опущены отмена до RUNNING и часть ошибок подготовки/оценки; они сохраняют причину и полноту, не создают положительный отчёт.

Чужой заказ: где проверяется владелец

Один запрос пользователя B к заказу A даёт разные результаты в двух режимах магазина.

Пояснения и границы схемы

Последовательность

  1. B отправляет GET /api/v1/orders/{orderIdA} с собственным корректным JWT.
  2. Gateway проверяет JWT и admission, устанавливает доверенный harness-контекст, пишет request start и policy facts в JSONL до proxy и передаёт запрос backend фиксированного listener.
  3. В protected API повторно проверяет JWT и выбирает заказ по id и доверенному actorId из sub.
  4. Чужой заказ не попадает в разрешённую выборку пользователя B.
  5. Protected фиксирует lab.object.accessed.v1 с subjectMatchesOwner=false; факт чтения/отказа и terminal записаны в JSONL до ответа 404. Чужие поля клиенту не возвращаются.
  6. Пользователь получает такой же публичный статус, как для отсутствующего объекта.
  7. В vulnerable альтернативный repository adapter выбирает заказ только по id.
  8. База возвращает существующий заказ A без ограничения владельцем.
  9. Vulnerable возвращает чужие поля с 200. Та же наблюдающая логика фиксирует subjectMatchesOwner=false и operationExecuted=true без ground-truth label.
  10. Oracle BO-01 подтверждает раскрытие заказа A пользователю B по контрольным полям ответа.

Детали и допущения

  • ALT — два отдельных последовательных run с одной фикстурой, а не переключатель в HTTP-запросе. Listener gateway выбирает backend; пользовательские headers этого не меняют.
  • JWT подтверждает личность B; право чтения заказа A проверяет shop рядом с данными. JWT обязателен в обоих режимах. ID + OWNER обозначает owner-scoped SQL-выборку.
  • Для внутреннего audit разрешено безопасное чтение метаданных владельца. Чужой и отсутствующий заказ остаются одинаковыми 404 снаружи; неизвестный факт owner передаётся null, не false.
  • События описывают факты одинаково в обеих реализациях. Detector может обнаружить и предотвращённую попытку, и раскрытие с 200. Case BO-01 подтверждает эффект по allowlist полей ответа независимо от incident.
  • Сохранение read/refusal audit до ответа обязательно, но дополнительные SQL-вызовы опущены. Отдельные детализации доставки и итоговой оценки включены в этот альбом.

Вход: лимит и доверенный результат проверки

В ENFORCE лимит допускает попытку либо возвращает 429; ошибки пароля обновляют состояние по доверенному ответу API.

Пояснения и границы схемы

Последовательность

  1. Приходит POST /api/v1/auth/login с синтетической парой. SourceKey назначает control и связывает с проверяемым harness assignment; произвольный X-Forwarded-For его не меняет.
  2. Policy проверяет и расходует бюджет попытки по независимым source и HMAC нормализованного login до вызова shop. Namespace: opaque partition, policy version, mode, source/account key.
  3. Локальный модуль gateway возвращает разрешение либо срок действия ограничения.
  4. Если политика допускает запрос, магазин проверяет пароль по хэшу; показан случай неверного пароля.
  5. API возвращает доверенный факт неуспешной аутентификации и сохраняет собственное событие отказа.
  6. Шлюз увеличивает счётчик ошибок и вычисляет ограниченный backoff/nextAllowedAt по snapshot политики.
  7. Состояние счётчиков и TTL сохранено.
  8. Клиент получает отказ аутентификации для допущенной, но неверной пары.
  9. Если ограничение уже активно, шлюз возвращает 429 с Retry-After без проверки пароля в магазине.

Детали и допущения

  • ALT показывает два альтернативных состояния rate policy одного HTTP-запроса. При допуске неверный пароль даёт 401, при активном лимите — 429 с Retry-After без вызова shop.
  • Успешный пароль в разрешённой ветке даёт 200 LoginResult и JWT. Первая корректная чужая fixture-пара может пройти: CS-02 демонстрирует остаточный риск парольной аутентификации. Такой эффект не равен ошибке проверки подписи JWT.
  • «Счётчики» — внутренний модуль того же gateway, стрелки к нему означают Java-вызовы. Bucket4j in-memory ограничивает source и account. Account key вычисляется одинаково для существующего и неизвестного login. Доверенный authOutcome поступает только от shop; клиент не задаёт результат проверки.
  • Моделируемый sourceKey выдаёт control; runner не превращает произвольный X-Forwarded-For в новый источник. Физическая сеть и синтетическая модель источников различаются и фиксируются в manifest.
  • Backoff — ограниченный timestamp/TTL, а не сон HTTP-потока. Thresholds, окна, TTL и budgets фиксируются до run. Повторы/targets не наследуют счётчики друг друга.
  • Бюджет ключей ограничен. Переполнение/ошибка локального limiter закрывают admission и дают 503/INFRA_REJECT, run INCONCLUSIVE; активные ограничения не вытесняются. Restart gateway прерывает опыт, состояние не восстанавливается.
  • В OBSERVE вычисляется wouldDecision, но запрос продолжается с отдельными shadow counters; в OFF evaluate не вызывается и состояние не меняется. 401 от shop не является REJECT login rate policy.
  • JSONL start/решения до proxy, terminal log и detector опущены. Эти обязанности выполняются и для раннего 429; пароль и bearer не попадают в audit.

Повтор: прежний результат или конфликт

Бизнес-идемпотентность остаётся в PostgreSQL; лог результата пишется после завершения транзакции.

Пояснения и границы схемы

Детали и допущения

  • Защищённый checkout сначала берёт transaction-scoped advisory lock по user/key hash и ищет orders по этому ключу. Ключ не хранится открытым. Одинаковый key с иным fingerprint даёт 409; ветка опущена.
  • Верхняя ветка: тот же key и fingerprint возвращают прежний успешный status/body из orders. Read-транзакция завершается и освобождает lock; затем пишутся operation REPLAYED/stateChanged=false и request terminal, после чего возвращается HTTP-ответ.
  • Нижняя ветка: новый key для уже оформленной версии корзины отклоняется. После rollback пишутся refusal operation и terminal. Лог не откатывается с бизнес-транзакцией, потому что записывается после её завершения.
  • Создание нового заказа здесь опущено: key lock → cart → coupon; orders/items, cart revision и coupon counter фиксируются одним commit. Успешный ответ для retry хранится в orders. Protected очищает позиции/купон корзины и повышает revision. Vulnerable для демонстрации replay оставляет их прежними и пропускает key lookup/проверку оформленной версии. Затем пишутся JSONL-события.
  • При параллельных запросах второй участник ждёт SQL lock и видит committed order; отдельная таблица идемпотентности не требуется. Ошибки оформления не кешируются; атомарность заказа обеспечивает PostgreSQL.
  • Запись security-логов обязательна в обоих режимах. Ошибка записи после commit не отменяет заказ; run становится INCONCLUSIVE. Схема не обещает атомарности БД и файла.
  • JWT многократен до expiry. Уникальность cart/revision предотвращает повтор одного бизнес-эффекта; создание новых допустимых операций с украденным bearer остаётся риском. Oracle считает effects независимо от HTTP и detector.

От JSON-лога к обработанному событию

API фиксирует бизнес-изменения, пишет лог; control индексирует строки, detector анализирует разрешённые факты.

Пояснения и границы схемы

Детали и допущения

  • COMMIT подтверждает только бизнес-транзакцию. Shop затем синхронно пишет operation и terminal в JSONL; на схеме они объединены в WRITE JSONL. START был записан до обработки и здесь опущен. Flush не даёт crash-durability.
  • Gateway аналогично пишет request start, policy facts и terminal, включая downstreamInvoked. Security JSONL — отдельный обязательный поток, а не debug/console-лог. Формат наблюдений одинаков для vulnerable и protected.
  • Log-ingestor входит в control, читает readonly named volumes без Docker socket. Он проверяет привязку источника/instance, schema, eventId, seq и redaction; вставляет событие и двигает курсор одной lab SQL-транзакцией.
  • «Сборщик + Lab DB» — графическая группа двух существующих частей: модуля control и PostgreSQL. SAFE VIEW и STATE + MARK — SQL detector к БД, не вызов API collector. Приложение магазина не пишет в lab DB.
  • Повтор той же строки допустим лишь с идентичными id/seq/payload. Конфликт, пропуск или невалидная строка делают run INCONCLUSIVE. Частичная строка в конце файла ждёт LF до deadline.
  • Detector использует audit.detector_observations с whitelist facts без target, labels и oracle; anti-join processed markers не пропускает поздний commit. Один worker на partition, один процесс detector; DB lease/failover нет.
  • State, incident/evidence/history и processed marker фиксируются вместе. Без срабатывания marker тоже создаётся. Event-time окна учитывают поздние события; после CLOSE результаты FINAL либо RETRACTED.
  • Подтверждение полноты требует STREAM_END каждого producer, непрерывных seq, lifecycle pairs и результатов runner. TP/FP/confirmedImpact определяет evaluator. После сбоя старый run не восстанавливается.

DRAINING: барьер перед окончательным отчётом

Остановка нагрузки, завершение запросов, STREAM_END и detector CLOSE подтверждают полноту перед оценкой.

Пояснения и границы схемы

Детали и допущения

  • Линии «Управление», «Runner» и «Сборщик» показывают модули одного lab-control. Вызовы между ними локальные Java; producers и detector — отдельные процессы. HTTP 202 относится только к командам оператора/административному API, не к вызову runner.
  • Orchestrator отменяет новые шаги/retries runner и ждёт completion handle, сохранения всех attempts и финального step manifest. Cancellation/deadline заменяют распределённый heartbeat/lease. Client Future cancel не доказывает завершения SQL в shop.
  • CLOSE закрывает admission gateway и выбранного shop; producers дожидаются in-flight=0 и flush STREAM_END(lastSeq). Нужны неизменный sourceInstanceId и исправный процесс. Маркер collector получает через файл, не через ответ control.
  • Collector — отдельный рабочий модуль control, который не использует executor нагрузки. DRAINED требует END, seq 1…lastSeq, started/completed, shop result и корреляцию с attempts.
  • CLOSE + IDS — SQL job detector с безопасными UUID/hash/count после двух DRAINED. Detector дочитывает события, закрывает окна и возвращает FINAL/RETRACTED с ACK; labels/target/эталон не передаются.
  • Затем control снимает readonly snapshot, выполняет oracle, оценивает FINAL incidents и сохраняет отчёт. Пропущенные результаты/логи, deadline или restart дают INCONCLUSIVE, без resume. cleanupSafe=false запрещает reset.
