Что делает API Security Lab

Учебный эксперимент сравнивает защиту двух режимов API, обнаружение угроз и доказанный эффект атакующего.

Пояснения и границы схемы

Детали и допущения

  • Один trial содержит последовательные vulnerable/protected runs с одинаковыми исходными данными, seed, businessTimeBase, workload и ruleset. Порядок фиксирован: vulnerable, затем protected; concurrency внутри race сохраняется.
  • Vulnerable использует учебные shop-стратегии без login limiter; protected применяет schema/login и бизнес-защиту. JWT проверяют оба Shop. Gateway одинаково маршрутизирует оба режима без защитных политик.
  • Case effect - EFFECT_OBSERVED / EFFECT_NOT_OBSERVED / INCONCLUSIVE; проверки инвариантов служат доказательством и поясняются в reason. Например, первая корректная чужая пара credentials может дать доступ при корректной парольной аутентификации.
  • ASR считается по оценимым ATTACK cases, recall и benign FPR - по episodeId, precision - по итоговым incidents. UI выводит показатели из cases/incidents; нулевой знаменатель - N/A. Полнота и правила detection заданы в контракте.
  • HTTP-код и incident сами по себе не доказывают эффект или предотвращение. JSON-отчёт сохраняется на стороне UI. Это проектная модель без заявленных результатов измерений.

Основные компоненты стенда

Control объединяет управление, UI и сценарный runner. Gateway и API доставляют access-логи по HTTP/JSON; отдельный Detector хранит и анализирует их.

Пояснения и границы схемы

Детали и допущения

  • Четыре Java-приложения: lab-control, lab-gateway, shop-api и lab-detector. Shop работает в двух экземплярах; вместе с PostgreSQL и LGTM - семь постоянных контейнеров.
  • Р1 реализует оба Shop и данные; Р2 - защита внутри Shop совместно с Р1 и Gateway-прокси; Р3 - внутренний scenario-runner; Р4 - Detector, orchestration, UI, Fixture и Evaluator. Объединение приложений не объединяет роли участников.
  • Runner - модуль lab-control с отдельным executor, semaphore и конечными бюджетами. Завершение сценариев подтверждается после сохранения результатов запросов; внутренние Java-интерфейсы определяются при реализации. HTTP API генератора нет.
  • Один активный trial; target enum выбирает фиксированный gateway listener 8081 либо 8082. HTTP-клиент генератора запрещает произвольные URL/redirects/proxy. Контейнер control не имеет внешнего egress.
  • Control имеет admin/SQL, поэтому внутри общей JVM нет сетевого sandbox для runner. Сценарные классы используют только ограниченные порты; зависимости от JDBC/admin/evaluator запрещены правилами сборки и ArchUnit. Сценарии - доверенный код репозитория.
  • Gateway/Shop отправляют LogBatch напрямую в Detector. Блок хранилища - внутренние данные Detector, не сборщик Control и не отдельный сервис. У producers нет SQL-credentials этого хранилища.
  • Detector остаётся отдельным процессом, получает только runId и HTTP-наблюдения без режима и эталона. Control ждёт результаты Runner, CLOSED runtimes и COMPLETED анализа, затем выполняет oracle/report. Общие heap/CPU Control остаются общей областью отказа.

Сценарный трафик проходит через gateway

Показан сценарный HTTP из встроенного runner через gateway. Административные и SQL-связи общего процесса control здесь опущены.

Пояснения и границы схемы

Детали и допущения

  • На рисунке только сценарный HTTP: встроенный runner в lab-control → gateway → выбранный shop. Две ветки означают разные runs, а не возможность указать backend в запросе.
  • Control входит в lab-traffic, shop-admin, lab-data и lab-observe. Эти административные и SQL-связи опущены; рисунок не утверждает, что контейнер control физически изолирован от shop/DB.
  • HTTP-клиент генератора принимает target enum и разрешённый route, запрещает arbitrary origin, absolute URL override, proxy, redirects и management endpoints. Сценарный модуль не получает admin/datasource interfaces; это граница доверенного кода одной JVM.
  • Контейнеры не имеют внешнего egress, Docker socket, host network или privileged-режима. Только UI/Grafana опубликованы на loopback; gateway доступен вручную в opt-in profile. Отсутствие published port не является ACL между контейнерами.
  • Gateway выбирает backend по local listener port 8081/8082. Host/query/headers не меняют target. /internal/** не проксируется бизнес-входом; admin endpoints защищены отдельными credentials и binding.
  • Проверки разделены: сетевые тесты внешнего egress control, контрактные тесты HTTP-клиента генератора против обхода gateway и ArchUnit против запрещённых зависимостей модуля. Внутри JVM не обещается изоляция от злонамеренного Java-кода.

Эксперимент, события и независимый эталон

События и инциденты отделены от приватного эталона; эффект атаки, инварианты и качество обнаружения имеют разные результаты.

Пояснения и границы схемы

Детали и допущения

  • Это концептуальная модель, не физическая DDL. Trial содержит два RunReport; cases и IncidentAssessment вложены в report. Episode объединяет cases по episodeId, отдельного массива episodes нет. Физическое хранение Control/Detector выбирает реализация; прежние lab-таблицы в ER-альбоме помечены как архив.
  • Приватный эталон до запуска задаёт cases/episodes, benign/malicious labels, attack-specific steps, цели, владельцев и oracle. Один эталон применяется в нескольких runs. Episode - единица detection recall и benign FPR; case/subcase - единица оценки эффекта.
  • AccessLog содержит итоговое HTTP-наблюдение. Логи доставляются напрямую в Detector, без CloudEvents, SQL-view, labels, режима или oracle. Producer и runId нужны для изоляции и дедупликации, requestId - для сопоставления с попыткой.
  • CaseResult хранит effect и detection отдельно; проверки инвариантов поясняются в reason. Эффект атакующего не обязательно означает ошибку конкретного защитного механизма.
  • Incident содержит incidentId, detectedAt, requestIds, description и необязательный family. Он сообщает подозрение на попытку; предварительные состояния, confidence и операторские статусы в API не входят.
  • IncidentAssessment создаёт Evaluator: TRUE_POSITIVE/FALSE_POSITIVE/UNASSESSED, matchedEpisodeIds и reason. Связь доказывается по requestId атакующего шага; отсутствие или ошибка family не отменяет подтверждённое обнаружение. FN хранится как detection episode, без искусственного incident.
  • Attempts, Runtime-контексты и внутренние данные Detector здесь опущены. Итоговый immutable report сохраняется после проверки полноты логов и COMPLETED анализа. Detector не имеет доступа к приватному эталону Control.

Защита: все проверки в приложении

Gateway маршрутизирует, Shop применяет защиту, Detector обнаруживает, Control проверяет эффект.

Пояснения и границы схемы

Оба Shop проверяют JWT; protected применяет схему, login limits и бизнес-инварианты, vulnerable допускает только документированные учебные нарушения. Общие DTO не запускают Bean Validation. Профиль задаётся при старте; Runtime mode не переключает реализацию. Gateway сохраняет Runtime OPEN/CLOSED и технические таймауты, но не имеет экспериментальных политик. Транспортный отказ не считается доказанным предотвращением. Gateway user=null; подтверждённый userId записывает Shop. Р2 реализует защиту внутри Shop совместно с Р1.

Детектор наблюдает, evaluator проверяет

Эталон и независимый oracle доступны оценщику, а детектор получает только допустимые наблюдения.

Пояснения и границы схемы

Детали и допущения

  • Верхний путь - доставка и анализ access-логов в Detector; нижний - независимая оценка внутри Control. Блок хранения логов принадлежит Detector. Общего SQL-протокола с Control нет; producers отправляют HTTP/JSON LogBatch.
  • Detector получает только поля AccessLog и runId, без режима, scenario/case/step, labels, владельцев и oracle. requestId связывает evidence, технические UUID не являются признаками класса атаки.
  • Эталон фиксируется до запуска. Oracle проверяет разрешённые поля ответа, before/after committed state и доверенные fixture snapshots через readonly доступ. Production calculator, BLOCK или incident не заменяют независимую проверку.
  • Effect и detection независимы; проверки инвариантов поясняются в reason. Первая корректная чужая пара credentials может достигнуть цели при корректной парольной аутентификации. Ошибка инфраструктуры не превращается в успешную защиту.
  • Внутренние предварительные выводы не публикуются. После finish и обработки всех sequence анализ становится COMPLETED, итоговые incidents неизменяемы. Схема показывает их оценку после FINALIZING.
  • Evaluator сопоставляет requestId с attack-specific step, создаёт TP/FP/UNASSESSED assessment и независимо проверяет effect. FN относится к episode без incident. Совпадения IP/run или подготовительного login недостаточно; ошибка family не меняет вердикт обнаружения.
  • ASR считается по cases, recall/benign FPR - по episodes, precision - по incidents. В отчёте видны знаменатели и coverage; нулевой знаменатель - N/A. Неполный run INCONCLUSIVE не участвует в окончательном paired comparison.
  • Ruleset фиксируется до подготовки. finish передаёт Detector gatewayLastSequence, shopLastSequence и deadlineAt. После COMPLETED Control получает observedRequestIds и итоговые incidents; приватный evaluation plan не передаётся.

Жизненный цикл одного прогона

Любой выход из RUNNING проходит FINALIZING; terminal state сам по себе не разрешает сброс данных.

Пояснения и границы схемы

Детали и допущения

  • Публичные состояния Trial: PREPARING, RUNNING, FINALIZING и COMPLETED/FAILED/CANCELLED/INCONCLUSIVE. POST /trials сразу начинает подготовку. Ожидание полноты и оценка - два подэтапа FINALIZING, отдельного EVALUATING в API нет.
  • PREPARING закрывает admission, устанавливает и проверяет фикстуру, готовит Runtime-контексты и instanceId, анализ Detector и план Runner. Затем открывает Shop, после него Gateway.
  • STOP означает конец плана, cancel или fatal. Выход из RUNNING проходит FINALIZING; desired terminal state хранится отдельно. При сбое процессы не возобновляют прежнюю работу, run заканчивается INCONCLUSIVE.
  • FINALIZING закрывает Gateway и ждёт CLOSED, затем Shop и ждёт CLOSED. CLOSED означает in-flight=0 и окончательный lastSequence. После этого finish задаёт границы Detector, Control ждёт COMPLETED и сверяет observedRequestIds с attempts.
  • Дедлайн, пропуск лога/attempt, смена instanceId или неподтверждённый COMPLETED означают INCONCLUSIVE. Client timeout сам по себе не означает завершения SQL.
  • Подэтап оценки получает readonly конечное состояние и выполняет независимый oracle. COMPLETED означает достоверность отчёта, а не обязательно эффективность защиты.
  • cleanupSafe=true требует отсутствия старых работ. После отказа сначала останавливаются старые исполнители, стенд перезапускается и подготавливается новый опыт. Reset по одному истечению таймера запрещён.
  • Для читаемости опущены отмена до RUNNING и часть ошибок подготовки/оценки; они сохраняют причину и полноту, не создают положительный отчёт.

Чужой заказ: где проверяется владелец

Один запрос пользователя B к заказу A даёт разные результаты в двух режимах магазина.

Пояснения и границы схемы

Последовательность

  1. B отправляет GET /api/v1/orders/{orderIdA} с собственным корректным JWT.
  2. Gateway проверяет OPEN, сохраняет X-Request-Id и передаёт запрос backend фиксированного listener. Итоговый access-лог формируется после результата с реальным status.
  3. В protected API проверяет JWT и выбирает заказ по id и доверенному actorId из sub.
  4. Чужой заказ не попадает в разрешённую выборку пользователя B.
  5. Protected возвращает 404 без чужих полей. Access-логи содержат путь, user и status; owner mismatch в Detector не передаётся.
  6. Пользователь получает такой же публичный статус, как для отсутствующего объекта.
  7. В vulnerable альтернативный repository adapter выбирает заказ только по id.
  8. База возвращает существующий заказ A без ограничения владельцем.
  9. Vulnerable возвращает чужие поля с 200. Формат access-лога тот же; доказательство утечки получает только независимый Evaluator по ответу и приватному baseline.
  10. Oracle BO-01 подтверждает раскрытие заказа A пользователю B по контрольным полям ответа.

Детали и допущения

  • ALT - два отдельных последовательных run с одной фикстурой, а не переключатель в HTTP-запросе. Listener gateway выбирает backend; пользовательские headers этого не меняют.
  • JWT подтверждает личность B; право чтения заказа A проверяет shop рядом с данными. JWT проверяют оба Shop. ID + OWNER обозначает owner-scoped SQL-выборку.
  • Чужой и отсутствующий заказ остаются одинаковыми 404 снаружи. Owner известен приватному baseline Control; в access-логах этого признака нет.
  • Логи описывают HTTP-наблюдения одинаково в обеих реализациях. Detector может заподозрить серию обращений, но по одному access-логу не знает владельца. BO-01 проверяет эффект по allowlist полей ответа независимо от incident.
  • Итоговые access-логи обязательны для успехов и отказов. Отдельные схемы доставки и оценки включены в этот альбом.

Вход: лимит внутри protected Shop

Gateway передаёт запрос и ответ; protected проверяет бюджет попытки до проверки пароля.

Пояснения и границы схемы

При активном лимите Shop возвращает 429 с Retry-After, иначе проверяет пароль и возвращает 200 с JWT или 401. Ошибка пароля обновляет локальный backoff, доверенного auth feedback через gateway не требуется. Ключи source и HMAC нормализованного login независимы и ограничены бюджетом/TTL. Состояние принадлежит protected Shop и текущему run; vulnerable не ведёт shadow counters. При переполнении состояния Shop возвращает 503 и закрывает admission; run INCONCLUSIVE. Первая правильная пара credentials может пройти. Gateway и Shop пишут по одной итоговой access-записи с одинаковым requestId; Detector объединяет их. Пароли и токены в лог не попадают.

Повтор: прежний результат или конфликт

Бизнес-идемпотентность остаётся в PostgreSQL; лог результата пишется после завершения транзакции.

Пояснения и границы схемы

Детали и допущения

  • Защищённый checkout сначала берёт transaction-scoped advisory lock по user/key hash и ищет orders по этому ключу. Ключ не хранится открытым. Одинаковый key с иным fingerprint даёт 409; ветка опущена.
  • Верхняя ветка: тот же key/fingerprint возвращает прежний 201/Order. Read-транзакция завершается и освобождает lock, затем формируется одна итоговая access-запись. Отдельного REPLAYED/stateChanged в логе нет.
  • Нижняя ветка: новый key для уже оформленной cartRevision отклоняется. После rollback и обработки ошибки формируется итоговый access-лог с 409. Он не откатывается с бизнес-транзакцией.
  • Создание нового заказа здесь опущено: key lock → cart → coupon; orders/items, cart revision и coupon counter фиксируются одним commit. Успешный ответ для retry хранится в orders. Protected очищает позиции/купон корзины и повышает revision. Vulnerable для демонстрации replay оставляет их прежними и пропускает key lookup/проверку оформленной версии. Затем формируется итоговая access-запись.
  • При параллельных запросах второй участник ждёт SQL lock и видит committed order; отдельная таблица идемпотентности не требуется. Ошибки оформления не кешируются; атомарность заказа обеспечивает PostgreSQL.
  • Запись security-логов обязательна в обоих режимах. Ошибка записи после commit не отменяет заказ; run становится INCONCLUSIVE. Схема не обещает атомарности БД и файла.
  • JWT многократен до expiry. Уникальность cart/revision предотвращает повтор одного бизнес-эффекта; создание новых допустимых операций с украденным bearer остаётся риском. Oracle считает effects независимо от HTTP и detector.

От access-лога к анализу запроса

API фиксирует бизнес-изменения и итоговый лог; Detector принимает пачку, хранит и анализирует HTTP-наблюдения.

Пояснения и границы схемы

Детали и допущения

  • COMMIT подтверждает только бизнес-транзакцию. После результата и обработки ошибки Shop фиксирует одну итоговую access-запись; очередь доставки относится к producer, а не к Control. Бизнес-commit и лог не атомарны.
  • Gateway аналогично пишет один итоговый AccessLog, включая отказы до Shop. Формат одинаков в vulnerable/protected; поля PolicyEvaluation и бизнес-факты не передаются.
  • Очередь producer отправляет HTTP/JSON LogBatch в Detector. 204 подтверждает сохранение всей пачки, но не завершение анализа. SQL-credentials Detector producer не получает.
  • Приём, хранение и правила на схеме - части одного Detector. Внутренние стрелки не являются API дополнительного сервиса. Control в доставке логов не участвует.
  • Повтор producer/sequence/content безопасен. Конфликт отклоняет пачку целиком с 409; пропуск, невалидная запись или deadline делают результат INCONCLUSIVE.
  • Detector читает только собственные AccessLog без режима, labels и oracle. Пачки могут приходить out-of-order; каждый requestId учитывается один раз, хотя записей producers может быть две.
  • Хранение и обработка не должны терять или повторно учитывать записи. После finish полные диапазоны обрабатываются, окна закрываются; итоговые incidents доступны только при COMPLETED.
  • Полнота требует окончательных lastSequence после CLOSED и sequence 1..N. Control сверяет observedRequestIds с attempts, затем оценивает incidents и effect. После сбоя старый run не восстанавливается.

FINALIZING: барьер перед окончательным отчётом

Остановка нагрузки, завершение запросов, CLOSED/lastSequence и COMPLETED анализа подтверждают полноту перед оценкой.

Пояснения и границы схемы

Детали и допущения

  • Управление и Runner - модули одного Control. Gateway, Shop и Detector - отдельные процессы. HTTP 202 относится к принятию управляющей команды, completion Runner подтверждается локально.
  • Orchestrator останавливает новые шаги/retries и ждёт сохранения всех attempts. Client Future cancel не доказывает завершения SQL в Shop.
  • Control закрывает Gateway и дожидается CLOSED с lastSequence при прежнем instanceId. Только после этого закрывает Shop, чтобы Gateway мог завершить уже начатые downstream-запросы.
  • Shop тоже должен вернуть CLOSED: in-flight=0 и окончательный lastSequence. Отдельного сборщика логов Control и файловых маркеров нет.
  • finish передаёт Detector обе границы N и deadlineAt. Detector принимает недостающие записи в этих границах, обрабатывает полные 1..N и возвращает COMPLETED; эталон и режим не передаются.
  • После COMPLETED Control сверяет observedRequestIds, получает все incidents, снимает readonly состояние, выполняет oracle и сохраняет отчёт. Пропуски, deadline/restart дают INCONCLUSIVE; cleanupSafe=false запрещает reset.
