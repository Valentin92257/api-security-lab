Что делает API Security Lab

Учебный эксперимент сравнивает защиту двух режимов API, обнаружение угроз и доказанный эффект атакующего.

Пояснения и границы схемы

Детали и допущения

  • Один experiment содержит последовательные vulnerable/protected runs с одинаковыми fixture, seed, business-time base, workload, concurrency и ruleset. Порядок targets чередуется при повторениях; concurrency внутри race сохраняется.
  • Vulnerable использует учебные shop-стратегии и OBSERVE экспериментальных gateway-политик; protected — защищённые стратегии и ENFORCE. JWT, ресурсные пределы, admission и audit обязательны в обоих режимах.
  • Case effect — EFFECT_OBSERVED / EFFECT_NOT_OBSERVED / ERROR / INCONCLUSIVE. Отдельно проверяются инварианты HELD / VIOLATED / NOT_APPLICABLE. Например, первая корректная чужая пара credentials может дать доступ при корректной работе парольной аутентификации.
  • ASR считается по оценимым malicious cases, recall и benign FPR — по полностью наблюдённым episodes, precision — по FINAL incidents. Benign workload нужен также для false block rate. Отчёт сохраняет знаменатели, coverage и причины исключений.
  • HTTP-код и incident сами по себе не доказывают эффект или предотвращение. Обязателен JSON-export; Markdown — дополнительный формат. Это проектная модель без заявленных результатов измерений.

Основные компоненты стенда

Четыре роли отвечают за пять Java-приложений; два экземпляра shop дают шесть Java-процессов.

Пояснения и границы схемы

Детали и допущения

  • Р1 реализует API/данные, Р2 — gateway/защиту, Р3 — генератор, Р4 — detector и control с UI/evaluator. Shop — один codebase с профилями vulnerable/protected и отдельными БД.
  • Control отправляет runner команды PREPARE/START/CANCEL на защищённый worker listener. Runner подтверждает planHash, отправляет heartbeat и результаты через узкий worker API control. Потеря lease останавливает новые шаги; runner не имеет SQL/Redis-доступа.
  • Lab DB содержит схемы audit, control и detection с разными SQL-ролями. Detector читает только audit.detector_observations и безопасные задания, пишет своё состояние, incidents/evidence и processed markers. Labels и shop DB ему недоступны.
  • PREPARE/CLOSE detector передаются через SQL jobs; отдельного HTTP management API у detector нет. Control управляет gateway/shop через отдельные admin listeners. Обратные ответы, shop outbox и эти служебные связи сокращены.
  • Порты 8081/8082 принадлежат входным listeners gateway: по ним сервер выбирает соответствующий backend и policy snapshot. Это не номера портов shop.
  • Базы shop, Redis и LGTM опущены. В Compose девять постоянно работающих контейнеров: шесть Java, PostgreSQL, Redis, LGTM; init jobs считаются отдельно. Остановка UI/detector не останавливает API при доступных обязательных хранилищах, но итоговый отчёт ждёт detector CLOSE.

Сценарный трафик проходит через gateway

Runner достигает двух API только через фиксированные listeners шлюза; прямого подключения к сети магазинов у него нет.

Пояснения и границы схемы

Детали и допущения

  • Пересечение зон означает членство gateway в lab-traffic и shop-backend; сети не вложены друг в друга. У runner нет прямого маршрута к shop-backend.
  • Серверный localPort gateway определяет target: 8081 — vulnerable, 8082 — protected. Подписи у выходящих стрелок обозначают выбор входного listener, а не порт shop. Host, query и пользовательские headers не переключают режим.
  • Всего шесть internal-сетей: lab-traffic, worker-control, shop-backend, shop-admin, lab-data, lab-observe. Здесь показан только бизнес-трафик. Runner также подключён к worker-control; LGTM collector принимает его telemetry в lab-traffic.
  • В worker-control control отправляет задания runner, а runner вызывает ограниченные heartbeat/results endpoints control. Это не proxy к operator/reset/admin функциям. У runner нет доступа к shop-admin, lab-data, lab-observe, SQL/Redis и Docker socket.
  • Изоляция обеспечивается internal networks, bind address, раздельными credentials/scopes и запретом egress. Отсутствие published port само по себе не является ACL между контейнерами. /internal/** не проксируется через бизнес-вход.
  • UI и Grafana доступны с host только на 127.0.0.1; gateway публикуется на loopback лишь в отдельном opt-in profile. Targets встроены, redirects и proxy отключены. Проверяются direct shop, внешний HTTP, host gateway, DNS/IPv6 и management bypass.

Эксперимент, события и независимый эталон

События и инциденты отделены от приватного эталона; эффект атаки, инварианты и качество обнаружения имеют разные результаты.

Пояснения и границы схемы

Детали и допущения

  • Это концептуальная ER-модель, не физическая DDL. 1:N обозначает связь с множеством, допускающим ноль элементов; M:N — необязательные связи через evidence или matching. Run содержит один target; experiment объединяет сравниваемые runs.
  • Приватный эталон до запуска задаёт cases/episodes, benign/malicious labels, attack-specific steps, цели, владельцев и oracle. Один эталон применяется в нескольких runs. Episode — единица detection recall и benign FPR; case/subcase — единица оценки эффекта.
  • SecurityEvent имеет CloudEvents envelope specversion/id/source/type/time/datacontenttype/dataschema и вложенный data. На схеме приведены сокращённые пути полей. Raw audit доступен control; detector получает whitelist-view без scenario/case/step, target, policy mode, labels и oracle.
  • Результат случая хранит effect EFFECT_OBSERVED / EFFECT_NOT_OBSERVED / ERROR / INCONCLUSIVE и отдельно invariant verdicts HELD / VIOLATED / NOT_APPLICABLE. Эффект атакующего не обязательно означает ошибку конкретного защитного механизма.
  • Incident содержит evidence event IDs, rule/ruleset version и analysisState PROVISIONAL / FINAL / RETRACTED. Operator status OPEN / ACKNOWLEDGED / RESOLVED — другая ось. Детектор описывает impact только как SUSPECTED/UNKNOWN.
  • IncidentAssessment создаёт evaluator: TP/FP/UNASSESSED, matched episodes и confirmedImpact. Связь incident→assessment 1:N допускает новые report revisions. Evidence сопоставляется через request и attack-specific step, с проверкой класса угрозы. FN хранится у episode без искусственного incident.
  • Receipt/ledger, manifests, steps/attempts, detection jobs/processed markers и отчёты опущены. Итоговый immutable report объединяет эти данные только после проверки полноты и detector CLOSE. Общая lab DB не даёт detector права читать control.

Защита: где выполняется каждая проверка

Gateway исполняет цепочку политик, API сохраняет инварианты, а отдельный detector анализирует события по YAML-правилам.

Пояснения и границы схемы

Детали и допущения

  • Каталог контрольных точек показывает protected-режим. L1–L3 предотвращают недопустимые эффекты; L4 асинхронно обнаруживает поведение. Это не четыре последовательных сетевых вызова.
  • Gateway сначала проверяет admission/ресурсный бюджет, затем обязательный JWT для маршрутов с bearer, экспериментальную schema policy, login limits и необязательные input signals. Durable audit охватывает также ранние отказы; receipt и решения фиксируются до proxy.
  • Owner-check и параметризованный SQL находятся в shop. Checkout блокирует key → cart → intent → coupon; order/items, redemption, consumed intent, cart revision, сохранённый успешный ответ, outbox и terminal ledger фиксируются одной SQL-транзакцией.
  • Vulnerable выбирает именованные учебные adapters и OBSERVE; protected — защищённые adapters и ENFORCE. Переключение режима gateway не отключает owner-check и SQL-ограничения protected shop.
  • OFF: SKIPPED, wouldDecision=null, состояние политики не меняется. OBSERVE вычисляет решение без блокировки. ENFORCE применяет BLOCK→REJECT, ALLOW/FLAG→CONTINUE. При NOT_APPLICABLE/NOT_REACHED/MISSING_CONTEXT/ERROR wouldDecision=null, а не ALLOW.
  • Режимы относятся только к экспериментальным политикам. JWT, технические пределы, admission, audit и изоляция обязательны. OBSERVE/ENFORCE имеют раздельное состояние; snapshot фиксируется до run.
  • Недоступность Redis в ENFORCE даёт 503/INFRA_REJECT; в OBSERVE — ERROR проверки с возможным CONTINUE. Недоступный audit до downstream не позволяет вызвать shop. Инфраструктурный отказ не считается доказанным предотвращением.
  • Detector формирует инциденты, не блокирует HTTP и не читает ground truth. Evaluator отдельно проверяет эффект и качество обнаружения. WouldBlock из OBSERVE — характеристика наблюдённого потока, не точное предсказание ENFORCE.

Детектор наблюдает, evaluator проверяет

Эталон и независимый oracle доступны оценщику, а детектор получает только допустимые наблюдения.

Пояснения и границы схемы

Детали и допущения

  • Верхний путь — наблюдение и обнаружение; нижний — независимая оценка внутри lab-control. Это потоки данных, не полный список сетевых вызовов. PostgreSQL один, но SQL grants разделяют audit, detection и private control.
  • Safe view допускает только фиксированные facts/outcomes, нормализованный producerKind GATEWAY/SHOP и непрозрачную partition. Она исключает source URI, target/backend name, policy mode/snapshot, scenario/case/step, labels и oracle results. Correlation IDs служат join/evidence, но не классификационными признаками правил.
  • Эталон фиксируется до запуска. Oracle проверяет разрешённые поля ответа, before/after committed state и доверенные fixture snapshots через readonly доступ. Production calculator, BLOCK или incident не заменяют независимую проверку.
  • Case effect и invariant verdicts независимы. Первая корректная чужая пара credentials может достигнуть цели при корректной парольной аутентификации. Ошибка инфраструктуры не превращается в успешную защиту.
  • В live-потоке incidents PROVISIONAL. После подтверждения полного набора событий CLOSE пересчитывает окна и делает результаты FINAL либо RETRACTED; история сохраняется. Схема показывает оценку FINAL incidents после DRAINING.
  • Evaluator сопоставляет evidence event → request → attack-specific step и класс угрозы, создаёт TP/FP/UNASSESSED assessment и подтверждает impact. FN относится к episode без incident. Совпадения run/source или подготовительного login недостаточно.
  • ASR считается по cases, recall/benign FPR — по episodes, precision — по incidents. В отчёте видны знаменатели и coverage; нулевой знаменатель — N/A. Неполный run INCONCLUSIVE не участвует в окончательном paired comparison.
  • Ruleset snapshot фиксируется до PREPARE. CLOSE передаёт detector только безопасные event IDs через detection.job_events и ожидаемый hash. Детектор не получает полный evaluation manifest или приватный эталон.

Жизненный цикл одного прогона

Любой выход из RUNNING проходит DRAINING; terminal state сам по себе не разрешает сброс данных.

Пояснения и границы схемы

Детали и допущения

  • Показаны все девять значений state: CREATED, PREPARING, RUNNING, DRAINING, EVALUATING, COMPLETED, FAILED, CANCELLED, INCONCLUSIVE. Переходы долговечны и защищены revision/CAS.
  • PREPARING закрывает старый admission, доказывает отсутствие незавершённых работ, ставит и проверяет фикстуру, сохраняет snapshots, получает detector READY и runner planHash ACK. Только после этого открывается admission и начинается RUNNING.
  • STOP включает конец плана, отмену и fatal во время исполнения. Прямых RUNNING→CANCELLED/FAILED нет. Desired terminal state хранится отдельно: DRAINING завершает работы, прежде чем разрешить FAILED/CANCELLED.
  • DRAINING закрывает admission gateway/shop; сверяет durable receipts, execution ledger и runtime; запечатывает event IDs и terminal coverage; ждёт outbox, processed markers и detector CLOSE с закрытыми окнами.
  • READY к EVALUATING разрешён при полном завершении обычного run. FATAL/CANCEL из DRAINING допустимы после фиксации оставшихся работ; deadline, missing event/result, unresolved receipt или неподтверждённый CLOSE ведут к INCONCLUSIVE.
  • EVALUATING получает readonly snapshot и выполняет независимые oracle. GAPS обозначает невозможность достоверно оценить результат. COMPLETED означает полный проверяемый отчёт; защита при этом может оказаться неэффективной.
  • Для читаемости не нарисованы отмена до RUNNING и все ошибки подготовки/оценки. Они сохраняют причину и состояние полноты. Ни один скрытый переход не обходит DRAINING после начала исполнения.
  • cleanupSafe — самостоятельная гарантия отсутствия старых работ. При false даже terminal run блокирует следующий reset. После crash нужны reconciliation либо явная остановка runtime и проверка DB-сессий; client timeout не доказывает rollback.

Чужой заказ: где проверяется владелец

Один запрос пользователя B к заказу A даёт разные результаты в двух режимах магазина.

Пояснения и границы схемы

Последовательность

  1. B отправляет GET /api/v1/orders/{orderIdA} с собственным корректным JWT.
  2. Gateway проверяет JWT и admission, устанавливает доверенный harness-контекст, сохраняет receipt/решения до proxy и передаёт запрос backend фиксированного listener.
  3. В protected API повторно проверяет JWT и выбирает заказ по id и доверенному actorId из sub.
  4. Чужой заказ не попадает в разрешённую выборку пользователя B.
  5. Protected фиксирует lab.object.accessed.v1 с subjectMatchesOwner=false; событие чтения/отказа долговечно сохранено до ответа 404. Чужие поля клиенту не возвращаются.
  6. Пользователь получает такой же публичный статус, как для отсутствующего объекта.
  7. В vulnerable альтернативный repository adapter выбирает заказ только по id.
  8. База возвращает существующий заказ A без ограничения владельцем.
  9. Vulnerable возвращает чужие поля с 200. Та же наблюдающая логика фиксирует subjectMatchesOwner=false и operationExecuted=true без ground-truth label.
  10. Oracle BO-01 подтверждает раскрытие заказа A пользователю B по контрольным полям ответа.

Детали и допущения

  • ALT — два отдельных последовательных run с одной фикстурой, а не переключатель в HTTP-запросе. Listener gateway выбирает backend; пользовательские headers этого не меняют.
  • JWT подтверждает личность B; право чтения заказа A проверяет shop рядом с данными. JWT обязателен в обоих режимах. ID + OWNER обозначает owner-scoped SQL-выборку.
  • Для внутреннего audit разрешено безопасное чтение метаданных владельца. Чужой и отсутствующий заказ остаются одинаковыми 404 снаружи; неизвестный факт owner передаётся null, не false.
  • События описывают факты одинаково в обеих реализациях. Detector может обнаружить и предотвращённую попытку, и раскрытие с 200. Case BO-01 подтверждает эффект по allowlist полей ответа независимо от incident.
  • Сохранение read/refusal audit до ответа обязательно, но дополнительные SQL-вызовы опущены. Отдельные детализации доставки и итоговой оценки включены в этот альбом.

Вход: лимит и доверенный результат проверки

В ENFORCE лимит допускает попытку либо возвращает 429; ошибки пароля обновляют состояние по доверенному ответу API.

Пояснения и границы схемы

Последовательность

  1. Приходит POST /api/v1/auth/login с синтетической парой. SourceKey назначает control и связывает с проверяемым harness assignment; произвольный X-Forwarded-For его не меняет.
  2. Policy проверяет и расходует бюджет попытки по независимым source и HMAC нормализованного login до вызова shop. Namespace: opaque partition, policy version, mode, source/account key.
  3. Redis возвращает разрешение либо срок действия ограничения.
  4. Если политика допускает запрос, магазин проверяет пароль по хэшу; показан случай неверного пароля.
  5. API возвращает доверенный факт неуспешной аутентификации и сохраняет собственное событие отказа.
  6. Шлюз увеличивает счётчик ошибок и вычисляет ограниченный backoff/nextAllowedAt по snapshot политики.
  7. Состояние счётчиков и TTL сохранено.
  8. Клиент получает отказ аутентификации для допущенной, но неверной пары.
  9. Если ограничение уже активно, шлюз возвращает 429 с Retry-After без проверки пароля в магазине.

Детали и допущения

  • ALT показывает два альтернативных состояния rate policy одного HTTP-запроса. При допуске неверный пароль даёт 401, при активном лимите — 429 с Retry-After без вызова shop.
  • Успешный пароль в разрешённой ветке даёт 200 LoginResult и JWT. Первая корректная чужая fixture-пара может пройти: CS-02 демонстрирует остаточный риск парольной аутентификации. Такой эффект не равен ошибке проверки подписи JWT.
  • Bucket4j/Redis ограничивает source и account. Account key вычисляется одинаково для существующего и неизвестного login. Доверенный authOutcome поступает только от shop; клиент не задаёт результат проверки.
  • Моделируемый sourceKey выдаёт control; runner не превращает произвольный X-Forwarded-For в новый источник. Физическая сеть и синтетическая модель источников различаются и фиксируются в manifest.
  • Backoff — ограниченный timestamp/TTL, а не сон HTTP-потока. Thresholds, окна, TTL и budgets фиксируются до run. Повторы/targets не наследуют счётчики друг друга.
  • При недоступности Redis ENFORCE возвращает 503/INFRA_REJECT. В OBSERVE возможны ERROR и CONTINUE с неполным измерением политики. Это не осмысленный BLOCK и не доказанное предотвращение.
  • В OBSERVE вычисляется wouldDecision, но запрос продолжается с отдельными shadow counters; в OFF evaluate не вызывается и состояние не меняется. 401 от shop не является REJECT login rate policy.
  • Durable receipt/решения до proxy, terminal audit и detector опущены. Эти обязанности выполняются и для раннего 429; пароль и bearer не попадают в audit.

Повтор: прежний результат или конфликт

Идемпотентный retry и повторное расходование уже использованного intent имеют разную семантику.

Пояснения и границы схемы

Последовательность

  1. После успешного checkout приходит POST /api/v1/orders с intentId, quotedTotal и Idempotency-Key. Gateway опущен; JWT и schema проверяются заново до lookup.
  2. Ищется запись по scope (authenticated user, method, route, key), сравнивается SHA-256 канонического тела, версии контракта и route. JWT/requestId/trace не входят в fingerprint.
  3. База возвращает существующую запись либо отсутствие ключа.
  4. Совпали key и fingerprint: возвращаются прежние 201/Order, тот же orderId и Idempotency-Replayed:true без нового эффекта. Lookup выполняется до повторной проверки expiry intent; уже истёкший intent не мешает возврату сохранённого успеха.
  5. Для нового key транзакция резервирует idempotency record, затем блокирует cart и intent в фиксированном порядке key→cart→intent→coupon. Проверяется уже использованный intent; новый key не отменяет его одноразовость.
  6. Intent уже погашен предыдущей операцией; новый ключ не делает его новым подтверждением.
  7. Откатывается новая бизнес-транзакция вместе с временным резервированием ключа.
  8. После rollback отказ фиксируется в outbox отдельной короткой транзакцией; подтверждения двух SQL-фаз опущены.
  9. Возвращается 409 INTENT_ALREADY_USED без нового заказа и без повторного расходования купона. Успешный key исходной операции сохраняется.

Детали и допущения

  • Верхняя ветка соответствует RP-01 и benign retry: прежний успешный 201/Order означает отсутствие дополнительного бизнес-эффекта. Различить злое намерение и технический повтор по одним и тем же HTTP-фактам может быть невозможно.
  • Нижняя ветка — subcase RP-02: новый key со spent intent. Другой subcase RP-02, прежний key с изменённым body, возвращает 409 IDEMPOTENCY_CONFLICT; он оставлен в пояснении, чтобы ALT имел две области.
  • Параллельный тот же key ожидает commit ограниченное время: затем прежний успех либо 409 OPERATION_IN_PROGRESS. Два разных intent одной cart revision могут создать только один order; проигравший получает CART_CHANGED.
  • Порядок полей JSON не меняет fingerprint. Cache lookup после auth/schema предшествует проверке expiry intent. Keys и consumed intents сохраняются до закрытия жизненного цикла фикстуры и отчёта; ошибки бизнес-транзакции не кешируются.
  • При rollback временный key откатывается, refusal audit сохраняется отдельной короткой транзакцией до ответа. Order, успешный key, intent/coupon/cart, outbox и terminal ledger при успехе фиксируются атомарно в PostgreSQL; Redis для этого не используется.
  • Access JWT многократен до истечения. Intent защищает один бизнес-эффект, но не запрещает владельцу украденного bearer создавать новые допустимые операции. Oracle считает committed effects независимо от HTTP-кода и detector.

От бизнес-транзакции до обработанного события

Outbox сохраняет событие вместе с изменением данных, доставка повторяется безопасно по eventId.

Пояснения и границы схемы

Последовательность

  1. Одна SQL-транзакция фиксирует бизнес-мутацию, terminal execution ledger и SecurityEvent в security_outbox. Event содержит CloudEvents envelope и вложенный data.
  2. Бизнес-операция завершена, исходное событие надёжно находится в outbox.
  3. Диспетчер читает ещё не подтверждённые записи outbox.
  4. Получена ограниченная порция событий с исходными eventId и trace context.
  5. Событие вставляется в общий audit store идемпотентно по eventId.
  6. Подтверждено долговременное наличие идентичного события: вставка или повтор того же id/payload. Совпавший id с другим payload — ошибка целостности, не успешная дедупликация.
  7. Только после подтверждения audit store диспетчер отмечает доставку исходной записи.
  8. Outbox хранит подтверждение доставки.
  9. Detector читает whitelist-view через anti-join с processed markers (partition, rulesetHash, eventId). PREPARE проверяет неизменяемый ruleset snapshot; один worker владеет DB lease partition.
  10. Detector получает observation view без ground truth, scenario label и имени режима.
  11. В одной detection-транзакции сохраняются event-time rule state, PROVISIONAL incident/evidence при срабатывании и processed marker. Событие без срабатывания тоже отмечается обработанным.
  12. Обработка завершена атомарно; отсутствие срабатывания тоже получает processed marker.

Детали и допущения

  • Доставка at least once: crash после INSERT EVENT до MARK DELIVERED вызывает безопасный повтор с тем же id/payload. UNIQUE event id не допускает второе событие; conflict payload считается ошибкой целостности.
  • Dispatcher — модуль shop-api. Lab DB — один PostgreSQL database со схемами audit/control/detection, а не отдельное Java-приложение. Detector — отдельный процесс с runtime SQL-role, которой запрещены raw audit, private control и shop DB.
  • Read-only access/refusal тоже долговечно фиксируется до ответа. После rollback failure event сохраняется отдельной короткой транзакцией. Gateway пишет собственные durable receipts/решения напрямую до downstream; зависимости от доступности control нет.
  • Envelope CloudEvents содержит id/source/type/time и вложенный data с context/actor/request/action/outcome/observations. Safe view передаёт whitelist фактов, нормализует producer и скрывает scenario/labels/target/policy mode. Произвольный raw JSON detector не читает.
  • READ UNSEEN использует отсутствие processed marker, не id > lastSeen: меньший sequence id может закоммититься позже. State, evidence и marker атомарны; DB lease предотвращает параллельное владение одной partition.
  • Окна упорядочены по event time и eventId; поздние события пересчитывают затронутые bounded windows. Live incidents PROVISIONAL; только после CLOSE полный набор даёт FINAL/RETRACTED и ACK. Метрики используют FINAL.
  • Incident создаётся правилом по наблюдениям; TP/FP и confirmedImpact назначает evaluator отдельно. Cached checkout retry со stateChanged=false не считается вторым эффектом. Полнота доставки дополнительно требует receipts/terminal coverage, а не одного hash полученных событий.

DRAINING: барьер перед окончательным отчётом

Остановка нагрузки, receipts и ledger, запечатанные события и detector CLOSE образуют проверяемый барьер перед оценкой.

Пояснения и границы схемы

Последовательность

  1. Control останавливает выдачу работ; при досрочной остановке отправляет CANCEL через POST /internal/v1/jobs/{jobId}/commands с commandId/epoch/revision. При нормальном завершении runner сам заканчивает конечный план. 202 подтверждает принятие, не остановку.
  2. Runner прекращает новые шаги и передаёт финальный идемпотентный batch results со step manifest. Heartbeat/lease продолжают определять право работы; потеря lease также запрещает новые шаги.
  3. Control закрывает admission epoch на gateway. Задержанные запросы не принимаются как новая работа данного run.
  4. Закрывается admission epoch на shop; уже принятые операции должны завершиться или получить доказанный terminal abort.
  5. Durable accepted/completed receipts и runtime reconciliation подтверждают исход всех принятых gateway requests. Нулевого in-memory счётчика после restart недостаточно.
  6. Execution ledger, committed state и runtime подтверждают отсутствие незавершённых shop-операций, включая транзакции после клиентского timeout.
  7. После quiescence control запечатывает producer epoch gateway. Поздние отказы старому epoch записываются отдельно от закрытого набора.
  8. Gateway подтверждает event IDs/count/hash, accepted/completed receipts и terminal coverage, а не только hash уже полученных событий.
  9. Control запечатывает producer epoch shop после завершения исполнения. Manifest включает события commit и ещё доставляемого outbox.
  10. Shop передаёт event IDs/count/hash и terminal coverage ledger. Control ждёт outbox, сверяет IDs и обязательные lifecycle slots каждого принятого request.
  11. После проверки доставки и coverage control сохраняет detector CLOSE и безопасный набор event IDs/hash в detection.job_events. Полный private manifest/labels detector не передаются; стрелка означает SQL job и ожидание, не RPC.
  12. Detector обрабатывает все ожидаемые события, закрывает event-time windows, финализирует или отзывает PROVISIONAL incidents и сохраняет ACK: ruleset/manifest hashes, processed count, errors. Только подтверждённый полный ACK разрешает EVALUATING.

Детали и допущения

  • Control→runner commands и runner→control heartbeat/results используют worker-control и отдельные credentials. На рисунке сокращены HTTP 202, чтение durable command status и повторы. Idempotency commandId, expectedRevision и epoch защищают от запоздавших команд.
  • STOP / CANCEL обозначает остановку генерации, не досрочную публикацию terminal state. Любой выход из RUNNING проходит этот барьер. При потере control runner прекращает новые шаги по истечении lease.
  • CLOSE прекращает admission, но не доказывает завершение. Таймаут клиента и нулевой счётчик после crash не заменяют durable receipts/ledger и проверку runtime/DB-сессий.
  • SEAL фиксирует точный event set и полноту lifecycle: каждый принятый request имеет terminal outcome, каждый вызванный shop — result или доказанный abort. Hash только фактически пришедших событий не выявляет пропущенный обязательный event.
  • Аудит и detector — логическая группа существующих lab DB и lab-detector, не новое приложение/контейнер. Collector сверяет manifests и outbox; detector получает только sanitized event IDs через SQL jobs и закрывает окна.
  • FINAL + ACK не заменяет oracle. Control после него снимает readonly конечное состояние, проверяет effects/invariants, оценивает FINAL incidents и сохраняет immutable report. RETRACTED сохраняются в истории, но не входят в основные метрики.
  • Любой missing step/event, unresolved receipt, snapshot error или неподтверждённый CLOSE даёт INCONCLUSIVE. CleanupSafe=false запрещает reset даже у terminal run. Reconciliation либо остановка runtime с проверкой DB-сессий обязательны до смены фикстуры.
