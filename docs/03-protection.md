# Защита внутри приложения и нейтральный gateway

## Граница ответственности

Все экспериментальные защитные проверки выполняет Shop. Gateway — HTTP-прокси: 8081 ведёт в shop-vulnerable, 8082 — в shop-protected. Он не проверяет пользовательский JWT, бизнес-схему, частоту входов, владельцев объектов или содержимое запросов на признаки атак. Backend определяется фиксированным listener, а не Host/query/заголовком клиента.

| Компонент | Ответственность |
|---|---|
| Gateway | Маршрутизация, сквозные X-Request-Id/trace context, передача HTTP, access-логи, таймауты и Runtime admission |
| Оба Shop | JWT для bearer-маршрутов, разбор JSON и типов, инфраструктурные ресурсные пределы, access-логи |
| Protected Shop | Валидация схемы, login limits/backoff, object-level authorization, безопасный SQL, бизнес-инварианты и идемпотентность |
| Vulnerable Shop | Те же маршруты и данные, намеренные пропуски проверок по каталогу сценариев; login limiter отключён |
| Detector | Анализ access-логов и инциденты, без блокировки HTTP |
| Control/evaluator | Независимая проверка эффекта, сопоставление инцидентов, отчёт |

Обязательная JWT-проверка в обоих Shop сохраняет идентичность тестовых пользователей: сценарии BOLA/replay/business abuse не требуют поддельных токенов. Register/login освобождены от bearer. Credential stuffing демонстрирует подбор настоящих credentials; protected ограничивает попытки, vulnerable — нет.

ServiceBearer служебного Runtime API, OPEN/CLOSED, конечные транспортные бюджеты и изоляция сети остаются инфраструктурой стенда. «Gateway без защиты» означает отсутствие экспериментальных политик бизнес-трафика, а не публичный доступ к административным командам. Технические отказы не засчитываются как успешная защита.

## Порядок обработки

1. Gateway проверяет доступность Runtime-контекста и фиксированного маршрута, передаёт запрос выбранному Shop. Политик OFF/OBSERVE/ENFORCE на gateway нет.
2. Shop регистрирует запрос для access-лога, проверяет Runtime admission и JWT (кроме register/login). JWT: фиксированный допустимый алгоритм, подпись, exp/nbf, issuer/audience.
3. Protected применяет ограничения OpenAPI: required/type/bounds, неизвестные поля/query, media type. Проверки после нормализации login/email/coupon выполняются согласно API. До обращения к проверке пароля расходуется бюджет попытки входа.
4. Выбранная реализация application выполняет owner-check, SQL и транзакцию; protected соблюдает инварианты, vulnerable содержит только перечисленные учебные слабости.
5. Shop формирует ответ и одну итоговую access-запись, включая ранние отказы и исключения. Gateway возвращает статус/тело/значимые заголовки и пишет собственную итоговую запись. Producer-доставка в Detector не меняется.

Общие HTTP-контроллеры реализуют lab.contracts.shop.api.DefaultApi и делегируют application. JWT-фильтр находится в Shop, защитные валидаторы и limiter — в lab.shop.secured. Общие DTO генерируются с useBeanValidation=false, чтобы не блокировать учебные запросы до выбора реализации. Для protected отсутствие Bean Validation не отменяет явную валидацию. Vulnerable допускает нарушения quantity/quotedTotal по сценарию; JSON syntax/типы и ограниченные объёмы остаются общими.

Spring-профиль задаёт реализацию при старте: protected → lab.shop.secured, vulnerable → lab.shop.vulnerable. Runtime mode не переключает код; при несовпадении Shop возвращает 409. Запрос клиента не может выбрать вариант, owner или role. Для каждого режима отдельные контейнер и БД.

## Прокси и корреляция

Gateway сохраняет метод, path/query, тело, Authorization, Content-Type, Idempotency-Key, X-Request-Id и значимые заголовки ответа. Hop-by-hop заголовки не пересылаются. Автоматические повторы бизнес-запросов запрещены. Ошибка соединения даёт 502, таймаут — 504; исход операции после timeout может быть неизвестен. Ответы Shop 400/401/403/404/409/429 передаются без переинтерпретации.

Runner создаёт X-Request-Id перед каждой отправкой; каждый retry получает новый UUID. Gateway передаёт его Shop и возвращает клиенту, в том числе при ошибках. Trace context распространяется отдельно. Виртуальный IP из X-Forwarded-For принимается только от доверенного Runner; Shop доверяет только Gateway. Это правило атрибуции логов и limiter, не сценарная защита.

Gateway не извлекает доверенный userId из JWT: его AccessLog.user=null. Shop записывает подтверждённый userId после аутентификации. Detector связывает записи по requestId. При отказе транспорта/закрытом Runtime до Shop есть только лог Gateway; это не доказательство блокировки атаки политикой.

## Ограничение попыток входа

Bucket4j in-memory находится в protected Shop. Ключи независимы: виртуальный IP и HMAC нормализованного login; существующие и отсутствующие аккаунты обрабатываются одинаково. Бюджет расходуется перед проверкой пароля, результат локальной проверки обновляет backoff. Gateway не участвует в этих решениях и не получает auth feedback.

Начальный бюджет — 10000 ключей на run. Thresholds, TTL, backoff, предел ожидающих запросов и версия конфигурации фиксируются до старта. Namespace включает runId/policyVersion/source-or-account. Vulnerable не создаёт shadow counters и не выполняет limiter; отдельное сравнение OBSERVE/ENFORCE/OFF в MVP отсутствует.

Атомарность consume/update/cleanup проверяется при параллельных запросах. Нельзя держать блокировку ключа во время дорогой проверки пароля. TTL удаляет только неиспользуемый ключ с завершённым backoff и восстановленным bucket. Активные ограничения не вытесняются. При исчерпании памяти ключей или внутренней ошибке Shop закрывает admission, возвращает 503; результат run — INCONCLUSIVE, а не успешное предотвращение.

PREPARE создаёт чистое состояние после завершения старых in-flight; callbacks проверяют runId. Состояние не хранится в PostgreSQL. Репликация Shop не входит в MVP; рестарт прерывает опыт. Первая корректная пара credentials может пройти: limiter ограничивает кампанию, но не доказывает кражу пароля.

## Прикладные гарантии

Protected проверяет владельца по authenticated subject; чужой и отсутствующий объект дают одинаковый 404. SQL каталога параметризован, datasource имеет только SELECT products. Schema validation не заменяет object-level authorization или параметризацию.

Checkout фиксирует cart revision и поля идемпотентности одной транзакцией с заказом, корзиной и купоном. Тот же key/body возвращает прежний Order; другой body прежнего key или использованная cartRevision — 409. Сервер рассчитывает цену/скидку, проверяет quantity, expiry и coupon limit; locks/conditional update/constraints обеспечивают допустимый commit. Access JWT остаётся многократным.

Vulnerable намеренно пропускает owner-check, использует ограниченную SQL-конкатенацию, принимает учебные нарушения quantity/quotedTotal, допускает неатомарное расходование купона и пропускает idempotency lookup/cartRevision-check. При checkout не очищает корзину и не меняет revision, чтобы воспроизвести повторный эффект. Полный каталог и критерии эффекта — в документах API и сценариев.

## Измерение и ответственность

Эксперимент сравнивает два приложения с одинаковым HTTP-контрактом через одинаковый нейтральный прокси. Внутренняя диагностика Shop может содержать policy/reason, но Detector получает только AccessLog, без бизнес-фактов и эталона. Действия защищённой реализации проверяются по ответам и БД независимо от detector. При потере логов/сбое run получает INCONCLUSIVE; commit и лог не атомарны.

Р1 реализует API/данные и общие интерфейсы, Р2 — JWT, валидацию, limiter и защищённые проверки совместно с Р1, а также gateway-прокси. Это совместная работа в shop-api, без нового микросервиса. Р3 реализует сценарии, Р4 — Detector/UI/evaluator. Пороговые значения калибруются на benign workload; политики во время run не меняются.
