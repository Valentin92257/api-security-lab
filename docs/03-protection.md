# Защита и Gateway

Нормативные интерфейсы: [Shop API](../contracts/shop-api.openapi.yaml), [Runtime API](../contracts/runtime-api.openapi.yaml), [правила взаимодействия](../contracts/semantics.md).

## Ответственность и профили

Gateway проверяет JWT, форму запросов, лимиты и допуск активного прогона. Shop проверяет владельцев, параметризует SQL и обеспечивает транзакционные бизнес-инварианты. Gateway не читает владельцев заказов и не расходует купоны.

| Механизм | vulnerable | protected |
|---|---|---|
| JWT, кроме register/login | Обязателен | Обязателен |
| OpenAPI validation и login limits | OBSERVE | ENFORCE |
| Owner-check, SQL и бизнес-правила Shop | Учебные уязвимые стратегии | Защищённые стратегии |
| Ресурсные пределы, Runtime и access-логи | Обязательны | Обязательны |

Это два фиксированных профиля. API дашборда не предоставляет отдельных переключателей политик. OBSERVE вычисляет решение без блокировки, ENFORCE применяет его. Внутреннее устройство PolicyChain не является межсервисным контрактом; в Detector передаются только итоговые HTTP-признаки.

## JWT и маршрутизация

Gateway:8081 направляет запросы в vulnerable, Gateway:8082 - в protected. Backend не выбирается клиентским Host/query/header. Для register/login JWT не требуется; остальные операции проверяют подпись, фиксированный alg, issuer/audience и срок действия. Shop также проверяет JWT. Действующий access JWT допускает несколько запросов.

X-Request-Id создаёт Runner, Gateway передаёт его Shop и возвращает в ответе. RunId задаёт Control через Runtime API; запросы обслуживаются только в OPEN. Служебные методы защищены отдельным ServiceBearer.

Для имитации источников Runner передаёт один IP в X-Forwarded-For. Gateway принимает его только от доверенного генератора, иначе использует адрес соединения. В Shop передаётся один вычисленный IP; Shop доверяет только Gateway. Виртуальный IP не определяет пользователя, owner или backend. Дополнительного run credential в бизнес-запросах нет.

## Login limits

Limiter живёт в памяти одного Gateway. Ключи используют вычисленный IP и нормализованный login; допустимо внутреннее HMAC-представление логина. Эти ключи и результат проверки пароля не добавляются в access-логи. Нормализация одинакова для существующих и отсутствующих аккаунтов.

Перед новым run состояние лимитов очищается при закрытом Runtime и отсутствии inFlight. OBSERVE и ENFORCE не наследуют счётчики друг друга. TTL не должен снимать активное ограничение ради освобождения места. Concurrency, backoff, максимальное число ключей и очередей конечны и фиксируются перед испытанием.

Переполнение состояния или внутренняя ошибка не выдаются за осмысленное предотвращение атаки: прогон получает INCONCLUSIVE. Поздний результат старого запроса не обновляет новый контекст. Перезапуск Gateway прерывает опыт.

Первая корректная пара credentials может дать доступ даже при корректной защите: ограничитель анализирует последовательность, а не знает происхождение пароля. Для Detector серии login-ответов являются признаком подозрительного поведения, не доказательством компрометации.

## Предметные гарантии

Protected выбирает профиль/заказ с проверкой JWT subject. Чужой и отсутствующий объект возвращают одинаковый 404. Каталог использует параметризованный SQL; сортировка фиксирована по id. OpenAPI validation не заменяет owner-check или параметризацию.

Checkout проверяет quantity, cartRevision, серверную цену и купон. Key lookup, заказ, позиции, очистка корзины и расход купона согласованы одной транзакцией. Прежний успешный key/body возвращает прежние 201/Order; другое тело или новый key оформленной revision дают 409. Подробнее: [API и данные](02-api-and-data.md).

После завершения запроса создаётся одна access-запись, включая отказы и исключения. Отказ до Shop создаёт только запись Gateway. Отказ передачи/хранения лога делает результат неполным; уже committed заказ не откатывается. События решений политик и признаки успеха атаки не передаются Detector.

Результаты двух фиксированных профилей сравниваются на одинаковых исходных данных. Дополнительные исследования вклада отдельной политики и её overhead не входят в текущий API испытаний.
