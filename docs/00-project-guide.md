# API Security Lab: проект от идеи до реализации

Версия 1.3, 25 октября 2026 года. Документ объясняет весь проект последовательно и не требует предварительного контекста. Описаны принятые решения для будущей реализации; реализация сервисов, испытания и измерения ещё предстоят. HTTP-контракты и генерация Java-интерфейсов/DTO уже находятся в репозитории; актуальные спецификации собраны в [contracts](../contracts/README.md). Названия внутренних Java-классов ниже задают предлагаемое разделение обязанностей, а не обозначают уже существующие классы.

## 1. Что мы строим и какой результат получаем

API Security Lab - учебный локальный стенд, на котором можно воспроизвести опасное поведение клиента, применить защиту, обнаружить подозрительные действия и проверить реальный результат. Все пользователи, пароли, товары и заказы синтетические. Стенд запускается на машине команды в контейнерах и не обращается к внешним целям.

Защищаемый объект - небольшое API магазина. API принимает HTTP-запросы: зарегистрировать пользователя, войти, прочитать профиль, найти товар, изменить корзину и создать заказ. Магазин нужен потому, что у него есть понятные правила безопасности: заказ принадлежит конкретному пользователю, цена задаётся сервером, купон имеет срок и лимит, один запрос на покупку не должен случайно создавать две покупки.

Инвариант - правило, которое должно сохраняться после допустимой операции: например, количество товара положительно, а число заказов одной операции не превышает одного. Такие правила позволяют проверить результат программы независимо от её собственных сообщений.

Одна реализация API запускается в двух режимах. В vulnerable отдельные защитные проверки намеренно ослаблены. В protected они включены и подкреплены транзакциями и ограничениями БД. Через оба режима проходит сопоставимый набор запросов, после чего стенд показывает различие.

Главный результат - отчёт с проверяемыми доказательствами. Он отвечает на четыре самостоятельных вопроса:

1. Достиг ли атакующий цели: например, прочитал чужой заказ или создал повторную покупку?
2. Какая защита разрешила, отметила или остановила действие?
3. Обнаружил ли отдельный detector подозрительное поведение?
4. Все ли необходимые шаги, события и изменения состояния известны, чтобы доверять выводу?

HTTP-отказ, обнаружение и отсутствие ущерба не равнозначны. Запрос может вернуть 200, раскрыть чужие данные и одновременно породить инцидент. Повтор checkout тоже может вернуть 201, но отдать уже созданный заказ без повторного эффекта - это правильная идемпотентность. При сетевом timeout заказ иногда уже записан в БД. Поэтому вывод нельзя строить только по коду ответа.

## 2. Как выглядит один эксперимент

Предположим, пользователь Анна владеет заказом 123, а пользователь Борис пытается его прочитать. Оператор выбирает сценарий доступа к чужому объекту и запускает сравнение.

Сначала стенд создаёт одинаковые исходные данные для двух режимов. Генератор входит как Борис и отправляет `GET /api/v1/orders/123`. В vulnerable стратегия чтения не проверяет владельца и возвращает заказ Анны. В protected запрос проверяется по authenticated user и owner, поэтому получает 404 - так же, как неизвестный заказ.

API и Gateway записывают итоговые HTTP-наблюдения: путь, пользователя, код ответа, размер и длительность. Detector видит только эти access-логи и может заподозрить перебор заказов; владельца и факт утечки по ним установить нельзя. Независимый evaluator знает из исходных данных, кому принадлежал заказ, и проверяет, какие поля получил Борис. Он устанавливает эффект атаки и правильность обнаружения, в том числе для заблокированной попытки.

Оператор открывает карточку опыта: прогресс, результаты проверок, итоговые инциденты с оценкой Control и сравнение режимов. Из неё можно получить JSON-отчёт. Это весь основной цикл проекта; остальные сценарии используют ту же инфраструктуру, меняя исследуемое свойство.

## 3. Какие угрозы демонстрирует стенд

| Семейство | Простое объяснение | Что проверяем |
|---|---|---|
| Credential stuffing | Попытки войти по подготовленному списку синтетических пар логин/пароль | Рабочие сессии, лимиты источника/аккаунта, обнаружение серии и влияние на обычные входы |
| BOLA/IDOR | Подмена идентификатора, чтобы получить чужой объект | Профили и заказы; факт раскрытия данных, а не только HTTP-код |
| Replay | Повтор уже выполненной операции | Один бизнес-эффект при retry, конфликт изменённого запроса и запрет повторного оформления той же версии корзины |
| Injection | Значение параметра меняет смысл SQL в учебном уязвимом адаптере | Попадание скрытого контрольного товара в выдачу; корректная параметризация protected |
| Business logic abuse | Нарушение правил магазина корректными по форме или конкурентными запросами | Купон, quantity, гонка checkout, обход серверной цены |

Для каждого семейства нужен легитимный (benign) контроль: собственный заказ, нормальный поиск, разрешённый купон, обычный вход, безопасный retry. Иначе можно получить формально «эффективную» систему, которая блокирует всех пользователей.

Купонное семейство включает просроченный, исчерпанный и повторно применяемый купон. Конкурентность проверяется отдельно для двух checkout одной корзины и для двух пользователей, претендующих на последнее использование купона. Реальная injection в первой версии - SQL; NoSQL/command-подобные строки проходят как отрицательный ввод без дополнительных движков.

## 4. Архитектура целиком

Четыре Java-приложения образуют пять работающих Java-процессов: магазин запускается дважды. Ещё два контейнера предоставляют PostgreSQL и локальную наблюдаемость. В базовом Compose получается семь постоянно работающих контейнеров; одноразовые задания подготовки в это число не входят.

| Компонент | Что делает | Почему выделен |
|---|---|---|
| `shop-api` × 2 | Пользователи, каталог, корзина, заказ, предметная защита и access-логи | Два независимых режима одного контракта для сравнения |
| `lab-gateway` | Принимает сценарный HTTP, проверяет токен/схему/лимиты, выбирает backend | Общая точка входа и место универсальных защит |
| `lab-detector` | Принимает и хранит access-логи, применяет правила, создаёт incidents | Изоляция от ответов эксперимента и независимая логика обнаружения |
| `lab-control` | Управляет опытом, исполняет сценарии отдельным модулем, готовит данные, оценивает эффект, показывает UI и отчёт | Одна точка управления всем жизненным циклом |
| PostgreSQL | Бизнес-состояние и внутреннее хранение Control/Detector | Долговечные данные и транзакционные гарантии |
| Grafana LGTM | Логи, метрики и traces | Техническая диагностика компонентов |

Полезно различать четыре потока взаимодействия:

- **Бизнес-запросы:** runner → gateway → выбранный shop → его БД.
- **Управление:** оператор → control; затем Java-вызовы runner и Fixture, Runtime API Shop/Gateway и Detector API.
- **Доказательства:** gateway и shop → HTTP/JSON access-логи → detector; detector → итоговые incidents → control; evaluator → результаты и report.
- **Наблюдаемость:** приложения → логи, метрики и traces в LGTM.

```text
                       +-> gateway:8081 -> shop-vulnerable -> shop_vulnerable DB
operator -> control [scenario-runner]
                       +-> gateway:8082 -> shop-protected  -> shop_protected DB

gateway + shop -> HTTP/JSON LogBatch -> detector -> final incidents -> control
control / evaluator  -> plan + attempts + readonly shop state + incidents -> report
```

Control не проксирует каждую покупку через себя. Detector не стоит на пути бизнес-запроса и хранит принятые access-логи у себя. Требования к их полноте и схеме строже, чем к диагностическим сообщениям.

## 5. Стек и причины выбора

| Решение | Зачем оно нужно | Что приходится учитывать |
|---|---|---|
| Java 25, Maven Wrapper | Один язык команды, воспроизводимая сборка; virtual threads для HTTP-исполнения | Потоки не заменяют бюджеты, таймауты и ограничения соединений |
| Spring Boot 4.0.x | Конфигурация приложений, HTTP, security, lifecycle и интеграция с БД | Patch-версии фиксируются после проверки сборки |
| Spring Cloud 2025.1.x, Gateway Server Web MVC 5.0.x | Gateway в совместимой servlet-линии | Проверяется работа фильтров, двух входов и чтения body |
| Spring JDBC/JdbcClient, PostgreSQL 17 | SQL, locks и транзакции видны явно | Нужно самостоятельно аккуратно проектировать запросы и границы транзакций |
| Flyway | Общие и protected-миграции применяются воспроизводимо | Миграционная роль отделена от runtime |
| Bucket4j in-memory | Готовый limiter внутри единственного gateway | Ограниченные ключи/TTL, раздельные run/mode, сброс на PREPARE; restart прерывает опыт |
| OpenAPI 3.1.0, JSON Schema | Проверяемые HTTP-контракты и схемы access-логов | Validator должен реально поддерживать использованные keywords |
| Thymeleaf | Формы, таблицы, фильтры и экспорт в одном control-приложении | Сложная SPA не нужна для результатов стенда |
| OpenTelemetry + LGTM | Связь запросов, логов, метрик и async-обработки | Телеметрия может теряться отдельно от доказательных access-логов |
| JUnit, Testcontainers, jqwik | Функциональные, транзакционные и модельные проверки | Race/grants проверяются в PostgreSQL, не в упрощённой in-memory БД |

Точные версии библиотек/адаптеров и digest образов фиксируются на первом техническом этапе. Проверка OpenAPI включает required/type/bounds/additionalProperties, nullable, local refs, query и повторное чтение тела после validator. Одного номера версии стандарта недостаточно. Это проверка выбранной реализации, а не повод писать собственный универсальный validator.

Отдельный broker не включён в первую версию: producers доставляют логи напрямую в Detector по HTTP/JSON. Внутреннее хранение Control и Detector выбирает реализация, общий SQL-протокол между ними не требуется. Полноценный внешний сервис авторизации тоже не требуется для owner-only модели. Эти решения уменьшают число компонентов, сохраняя основную исследовательскую задачу.

## 6. Как организован Java-проект

Репозиторий - Maven monorepo с отдельным собираемым приложением для каждого процесса. Корневой pom фиксирует общие версии и порядок сборки; Maven Wrapper обеспечивает одинаковый запуск у участников и в CI.

```text
apps/
  shop-api/          # auth, catalog, cart, checkout, orders, runtime, access logs
  lab-gateway/       # listeners, routing, policies, admission, access logs
  lab-detector/      # ingestion, rules, windows, incidents, HTTP ingestion
  lab-control/       # orchestration, fixtures, evaluator, ui, reports
modules/
  scenario-runner/   # plan, scenarios, executor, cancellation, result ports; без Boot main
libs/
  lab-contracts/     # возможная общая библиотека; HTTP DTO пока генерируются в apps
  lab-observability/ # trace propagation, redaction, соглашения метрик
  lab-test-support/  # test clients и fixtures, только test scope
contracts/
  shop-api.openapi.yaml
  control-api.openapi.yaml
  detector-api.openapi.yaml
  runtime-api.openapi.yaml
  schemas/{common,shop,control,detector,runtime,logs}.yaml
config/{policies,rules,scenarios}/
db/{shop/common,shop/protected}/
fixtures/
infra/compose.yaml
tests/acceptance/
```

Дерево показывает предлагаемую организацию будущей реализации; сейчас существуют четыре apps с генерацией HTTP-кода и [Java-порты Control](../contracts/modules.md).

Внутри приложения код группируется по предметной функции. Например, в shop пакет checkout содержит входные команды, прикладной сценарий оформления, правила и SQL-адаптеры этого сценария. Не нужно складывать все контроллеры всех областей в одну гигантскую папку и делить бизнес-логику только по техническим аннотациям.

Практический путь вызова: HTTP controller разбирает запрос → прикладной use case организует операцию → предметные правила проверяют допустимость → repository/adapter выполняет SQL или внешний вызов. Контроллер не управляет купонным счётчиком, repository не решает, что считать успешной атакой, а генератор не читает SQL напрямую.

Общие библиотеки ограничены контрактами и техническими соглашениями. Приложения не импортируют внутренние классы друг друга. В частности, detector не получает fixture catalog или evaluator code через «удобную общую библиотеку»: иначе разделение процессов формально сохранится, а независимость знания о сценариях будет потеряна.

Конфигурации правил, политик и сценариев имеют версию. Их hash фиксируется в run, поэтому отчёт можно связать с точным набором решений. Рабочий экземпляр snapshot не изменяется во время измерения.

## 7. Устройство demo API и двух режимов

### Модули и точки расширения

Shop включает auth, catalog, cart, checkout и orders. Служебный Runtime API управляет допуском запросов и контекстом прогона, но не открывается через обычное API. БД напрямую готовит Fixture внутри Control. Общие controller, DTO (типизированные структуры запросов/ответов) и response mapper задают один внешний контракт.

Выбор уязвимой или защищённой реализации делается при запуске через Spring-конфигурацию. Удобные границы стратегий - `OrderReader`, `CatalogSearch`, `CheckoutExecutor`: они принимают одинаковую типизированную команду и возвращают одинаковый результат, но используют разные проверки и SQL-протоколы. Имена конкретных классов можно уточнить при создании skeleton; существенны интерфейс и конфигурационная граница.

Protected owner query использует id объекта и authenticated user. Vulnerable может читать тот же объект только по id. Protected search использует параметры SQL и фиксированный порядок по id; vulnerable содержит один выделенный адаптер с небезопасным построением запроса. Protected checkout выполняет атомарный протокол; vulnerable содержит именованные учебные слабости для replay, quantity, цены или купона.

Такие отличия не должны размазываться по каждому controller в виде случайных `if (vulnerable)`. У генерации Shop API задано `useBeanValidation=false`: protected явно применяет нормативные проверки. Общий `@Valid` или одинаковый защитный CHECK в обеих БД не должен незаметно исправить слабость, которую требуется показать. JSON syntax и ресурсные пределы остаются общими, а исследуемые проверки включаются выбранной стратегией.

### Внешнее поведение

Путь начинается с `/api/v1`; данные передаются JSON. JWT - подписанный токен, которым клиент подтверждает выданную ему сессию; он обязателен везде, кроме register/login. Числовые ids положительные, UUID используются для запросов, прогонов и инцидентов. Деньги - целые рубли, Java long/SQL bigint, currency RUB; quantity от 1 до 99, не более 100 разных позиций корзины.

| Операция | Запрос и назначение |
|---|---|
| `POST /auth/register` | login/password/name/email; атомарно создаёт User и пустую корзину, возвращает 201; токен через login |
| `POST /auth/login` | login/password; возвращает accessToken, tokenType, expiresIn |
| `GET /users/{userId}` | Собственный профиль; отдельная поверхность BOLA |
| `GET /products` | Поиск q, limit/offset; сортировка по id; только опубликованные товары |
| `GET /cart` | Корзина, revision, позиции, купон и текущие суммы |
| `PUT /cart/items/{productId}` | quantity; создаёт позицию или устанавливает абсолютное количество |
| `PUT /cart/coupon` | code; выбирает один купон без расходования лимита |
| `POST /orders` | cartRevision/quotedTotal и Idempotency-Key; создаёт или возвращает Order |
| `GET /orders/{orderId}` | Собственный Order |

User содержит id/login/name/email; пароль или hash не возвращаются. Product содержит id/name/description/price/currency. Cart содержит id/userId/revision/items/coupon/subtotal/discount/total/currency/updatedAt; позиция - productId/name/quantity/unitPrice/lineTotal. Order сохраняет владельца, cartId/cartRevision, items, суммы, полный успешный ответ, createdAt. Отмен, платежей и возвратов в MVP нет.

Регистрация и создание заказа возвращают 201, чтение/изменение корзины и login - 200. Ошибки имеют единый Problem с type/title/status/code/requestId. Основные статусы: 400 для валидации, 401 для auth, 404 для отсутствующего или чужого объекта, 409 для конфликта состояния, 429 для rate policy, 503 для зависимости или закрытого run. Неожиданный 500 не сообщает SQL/stack trace.

### Данные

Бизнес-таблицы: users, products, coupons, carts/cart_items, orders/order_items. В carts есть revision, в products - published, в купоне - срок, max_uses и used_count. Скрытый draft-товар служит canary: его появление в обычной выдаче - наблюдаемый эффект injection.

Orders хранит успешный ответ, hash ключа и факт использования купона. Таблиц доставки событий и учёта исполнения в магазине нет: факты поступают из структурированных логов.

Protected дополняет PK/FK бизнес-ограничениями: допустимое количество, корректные суммы, used_count≤max_uses, уникальный order на пару cart/revision. Межтабличное равенство суммы заказа сумме его строк нельзя обеспечить одним обычным CHECK; его обеспечивает транзакция и проверяет независимый oracle.

Исторический заказ хранит цену позиции и успешный ответ. Evaluator сверяет суммы с приватным fixture baseline. История фикстуры соответствует тому же каталогу и условиям купонов; их изменение внутри run запрещено.

Магазин ограничен девятью операциями для ИБ-экспериментов. Fixture-модуль до run создаёт пользователей и корзины; отдельная ручка регистрации позволяет создать нового синтетического пользователя; отдельной карточки товара, истории заказов и удалений в публичном API нет. Повтор PUT количества/купона при неизменном состоянии не повышает revision; quantity=0 - отрицательный тест, а не удаление. Профиль текущего пользователя читается по ID из приватного manifest после login.

## 8. Версия корзины и идемпотентность заказа

Клиент читает Cart и передаёт cartRevision/quotedTotal в POST /orders с Idempotency-Key. Revision меняется после реального изменения корзины; no-op её не повышает. Заказ хранит исходные cart_id/cart_revision, hash ключа, fingerprint тела и успешный response_body.

Пример: корзина revision 7 стоит 3000 рублей, купон 10% даёт итог 2700. Запрос с revision=7, quotedTotal=2700 и key K создаёт Order 50. Если ответ потерялся, тот же K/body возвращает Order 50. Новый K2 с revision=7 даёт CART_ALREADY_CHECKED_OUT; прежний K с иным телом - IDEMPOTENCY_CONFLICT.

Protected берёт locks в порядке key → cart → coupon. Сначала ищет успешный key; затем под row lock корзины проверяет ранее оформленную revision, актуальность revision, состав, серверную цену и купон. Order/items, расход купона, сохранённый ответ, очистка позиций/купона корзины и повышение revision фиксируются одним commit. UNIQUE(user_id,key hash) и UNIQUE(cart_id,cart_revision) страхуют от гонок. Итоговый access-лог формируется после commit/rollback и обработки HTTP-ошибки.

Fingerprint - SHA-256 канонических типизированных значений тела, маршрута и версии контракта; JWT/requestId/trace не входят. Успешный retry возвращает кеш до проверки изменённой корзины и истёкшего купона. Ошибки не кешируются; ожидание key lock ограничено и может дать OPERATION_IN_PROGRESS.

Vulnerable пропускает lookup/уникальность key и проверку оформленной revision. Для replay он намеренно сохраняет корзину, её купон и revision после checkout; повтор создаёт второй order. Protected очищает её и повышает revision. Обычные mutations повышают revision в обоих режимах.

Каталог и условия купонов заморожены до отчёта. Поэтому достаточно unit_price позиции и полного response_body заказа; отдельных исторических полей и версий каталога нет. Приватный fixture manifest служит независимым эталоном evaluator. Срок купона проверяется по бизнес-часам строго now < expiresAt, JWT - по реальным часам. JWT многократен: защита от повторного эффекта не запрещает новые допустимые операции обладателю украденного bearer.

## 9. Как реализуется gateway и применение политик

Gateway имеет два бизнес-входа и отдельный служебный интерфейс. Маршрут определяется доверенным входным listener, а не значением Host или заголовком клиента. runId берётся из активного Runtime-контекста. Генератор создаёт X-Request-Id до каждой отправки; Gateway передаёт его в Shop и возвращает в ответе. Для виртуального IP используется один X-Forwarded-For: Gateway доверяет ему только от генератора, Shop - только от Gateway. Role/owner headers клиента не определяют права; Shop самостоятельно проверяет access JWT.

Внутренние обязанности разделены между admission, routing, PolicyChain, access-log writer и proxy. Admission отвечает, можно ли принимать новые requests этого run. Routing знает фиксированные backend. Политики вычисляют решение, а chain определяет фактическое продолжение или отказ.

```java
interface GatewayPolicy {
    String id();
    int order();
    boolean appliesTo(RequestContext request);
    PolicyEvaluation evaluate(RequestContext request, PolicySnapshot snapshot);
}
```

Результат содержит policyId/version, evaluationStatus, wouldDecision, reasonCode, duration и безопасные facts. В OFF проверка не выполняется. В OBSERVE вычисляется решение и обновляется отдельное shadow-state, но запрос продолжается. В ENFORCE BLOCK останавливает запрос. FLAG означает продолжение с отметкой и не создаёт incident автоматически.

Нужно хранить обе стороны: `wouldDecision=ALLOW/BLOCK/FLAG` и `enforcedAction=CONTINUE/REJECT/INFRA_REJECT`. Для пропуска/ошибки wouldDecision=null. EvaluationStatus различает EVALUATED, SKIPPED, NOT_APPLICABLE, NOT_REACHED, MISSING_CONTEXT, ERROR. Например, wouldDecision=BLOCK при OBSERVE не увеличивает число реальных блокировок.

Порядок обработки: обязательный admission/ресурсные пределы → обязательный JWT для закрытых endpoints → OpenAPI validation → login/rate policy → дополнительные признаки ввода → разрешённый proxy и итоговая access-запись. После первого отказа остальные экспериментальные проверки имеют NOT_REACHED. Access-логирование является внешней обязательной обвязкой и выполняется даже при раннем 400/401/413/429.

JWT проверяется по фиксированным alg, подписи, issuer, audience, exp и nbf. Начальный TTL access token - 15 минут, clock skew - 5 секунд. Отдельный target имеет свою ожидаемую конфигурацию ключа/claims. Успешная аутентификация устанавливает личность; право прочитать Order по-прежнему проверяет shop.

Rate policy использует Bucket4j in-memory и два бюджета: источник и HMAC нормализованного login. Результат проверки пароля приходит от доверенного shop. На нём строятся backoff/временная блокировка; очереди, задержки и concurrency ограничены. Источник - IP виртуального клиента из доверенного X-Forwarded-For; недоверенный заголовок игнорируется.

State namespace включает runId, policy version и mode, поэтому target/run не наследует чужую блокировку. Переполнение бюджета ключей или внутренняя ошибка limiter закрывают admission, дают 503/INFRA_REJECT и INCONCLUSIVE независимо от mode; это инфраструктурный отказ, а не решение rate policy. Ошибка сохранения обязательного access-лога делает run INCONCLUSIVE; подтверждённый commit не отменяется. Ошибка после downstream требует проверки результата, а не заявления «защита сработала».

Обычная paired-конфигурация: vulnerable с OBSERVE gateway-политик и учебными shop-стратегиями; protected с ENFORCE и защищёнными стратегиями. Общие границы безопасности и access-логирование включены в обоих режимах. Текущий API предоставляет только эти два фиксированных набора; OFF и отдельное исследование стоимости политики не входят в интерфейс запуска.

Локальные buckets и backoff потокобезопасны; один gateway без реплик. PREPARE создаёт чистый run namespace после завершения старых запросов. Бюджет - начальные 10000 ключей на run, фиксируемые в snapshot. TTL не удаляет активный backoff или невосстановленный bucket; cleanup и callback проверяют runId. При restart локальное состояние теряется, run INCONCLUSIVE без продолжения. Новому run задаются чистые данные и политики.

## 10. Как работает встроенный генератор сценариев

Scenario-runner - библиотека внутри lab-control, а не отдельное приложение или контейнер. Р3 реализует планирование/сценарии/HTTP-исполнение; Р4 подключает модуль к orchestration, хранению и UI. Один trial с двумя последовательными runs выполняется в MVP; control атомарно резервирует слот перед PREPARING, конкурентному start отвечает 409; последовательные paired runs сохраняют сопоставимость нагрузки.

`PlanExecutor` управляет порядком, barriers и конечными циклами; `StepExecutor` превращает типизированный шаг в запрос; `ScenarioHttpClient` выбирает фиксированный gateway origin; `AttemptSink` передаёт результат адаптеру control. Модуль не импортирует JDBC, evaluator, log-reader или admin-клиенты. Отдельный Maven-модуль и ArchUnit проверяют эти зависимости. Это доверенный код, не песочница для произвольных программ.

Orchestrator вызывает Runner.prepare(runId, mode, families, seed, fixture, deadlineAt), получает PreparedRun с plan(), затем запускает start(http, attemptSink). CompletionStage завершается после сохранения всех начатых attempts. cancel() запрещает новые steps/retries. Точные сигнатуры заданы в [ControlPorts.java](../apps/lab-control/src/main/java/lab/control/ControlPorts.java). HTTP-протокола runner↔control, heartbeat и lease нет; конкретные таблицы хранения не являются контрактом между модулями.

У runner отдельный executor; HTTP I/O может использовать virtual threads с semaphore. Ограничены concurrency, attempts, body/response, очередь результатов и длительность. UI и orchestration не используют этот executor или common ForkJoinPool. Общие JVM/heap/CPU всё равно остаются общей областью отказа: resource limits и отмена обязательны, OOM не изолирован от UI.

requestId - UUID, создаваемый Runner до отправки в X-Request-Id и сохраняемый Gateway/Shop. Retry получает новый requestId, но сохраняет cartRevision/key повторяемой бизнес-операции. Пароли/JWT живут только в памяти; AttemptSink сохраняет безопасные результаты. Completion подтверждается после их записи; потеря результата даёт INCONCLUSIVE.

Сценарии принимают target enum и версионированные routes, не произвольный baseUrl. ScenarioHttpClient запрещает redirects, proxy, absolute URL override, смену origin и management routes. Query/body могут содержать учебный ввод, но не менять адрес назначения. Fixtures подготавливает orchestration через собственный admin adapter. У процесса control есть права на admin/SQL; встроенный runner технически разделяет их. Программные ограничения здесь нельзя описывать как сетевой запрет доступа модуля к ресурсам control. Внешний egress запрещён для всего контейнера.

Run deadline и cancellation token проверяются перед каждой отправкой, retry и ожиданием barrier. Ошибка сохранения/переполнение очереди останавливают новые действия. Отмена клиентского Future или timeout не означают rollback в магазине: FINALIZING отдельно ждёт его in-flight и логи. После падения control старый run INCONCLUSIVE и не возобновляется.

CS-01 генерирует 200 попыток, включая три корректные пары: один detection episode и три case доступа. Неверные пары не раздувают знаменатель ASR. Race использует barriers и повторения; seed не фиксирует планирование потоков и SQL interleaving.

## 11. Структурированные логи как источник детектора

### Факт, инцидент и независимая оценка

AccessLog сообщает HTTP-наблюдение: кто обратился, куда, с каким итоговым кодом, размером и временем ответа. Incident - вывод detector по одному или нескольким запросам. Assessment - независимая оценка control по плану, результатам запросов и состоянию магазина. Producer не пишет «успешная атака BOLA», а detector не получает ожидаемый ответ сценария.

Поля AccessLog: sequence, requestId, time, remote_addr, user, method, path с query, route, status, bytes, request_time, user_agent, req_hash. Неизвестные user/route/user_agent равны null. req_hash - SHA-256 метода, исходного path/query и полного тела; если тело недоступно, null. Пароли, JWT, Authorization и исходное тело не сохраняются. Формат и ограничения заданы в [схеме](../contracts/schemas/logs.yaml).

### Как приложение пишет лог

Gateway и каждый shop формируют одну итоговую access-запись на запрос, включая отказы и исключения. Если запрос остановлен Gateway, записи Shop нет. Две записи с одинаковым requestId описывают один запрос, а не две атаки. Фактический status записывается после обработки ошибки; успешная mutation - после commit. Счётчик in-flight уменьшается после фиксации access-записи.

sequence начинается с 1 отдельно для producer/run и назначается упорядоченным writer. Sampling и тихое отбрасывание запрещены. Ограничения: до 100 записей в пачке, 64 KiB на запись, 8 MiB на пачку, 100000 записей на producer/run. Локальный файл может использовать JSONL, но формат межсервисной доставки - HTTP/JSON LogBatch, без чтения томов Control.

Бизнес-транзакция и лог не атомарны. В MVP предполагается, что процессы и хранилища не падают во время run. Ошибка логирования после commit не отменяет созданный заказ: admission закрывается, опыт признаётся INCONCLUSIVE. Продолжение прерванного опыта и восстановление потерянных логов не реализуются.

### Сбор логов и проверка полноты

Shop/Gateway отправляют LogBatch прямо в Detector с токеном своей роли. Detector хранит логи у себя; 204 подтверждает сохранение всей пачки. Повтор producer/sequence с тем же содержимым безопасен; конфликт отклоняет пачку целиком с 409. Схемы и [Detector API](../contracts/detector-api.openapi.yaml) заменяют SQL-проекцию и сборщик внутри Control.

В run участвуют два producer: Gateway и выбранный Shop. Control сначала закрывает Gateway и ждёт CLOSED, затем закрывает Shop. Runtime возвращает окончательный lastSequence; CLOSED означает in-flight=0 при неизменном instanceId. После этого Control передаёт обе границы и deadlineAt в finishAnalysis.

Detector принимает оставшиеся записи только внутри объявленных границ, проверяет непрерывные sequence 1..N и завершает анализ. После COMPLETED новые записи запрещены; идентичные сохранённые повторы допустимы. observedRequestIds сверяется с результатами Runner. Потеря записи, конфликт, превышение бюджета или смена instanceId делают отчёт INCONCLUSIVE. Старый run после перезапуска не возобновляется.

## 12. Как устроен detector

### Какие данные ему разрешены

Detector получает runId и access-логи через HTTP, без режима vulnerable/protected, сценариев, labels, владельцев объектов, ожидаемого эффекта и oracle results. requestId нужен для join/evidence, runId - для изоляции состояния; правила не используют технические UUID или выбранный виртуальный IP как готовую метку атаки.

Это ограничение обеспечивается содержимым API, сетевым доступом и полномочиями. Detector не получает credentials бизнес-БД или приватного хранилища Control. Даже ошибочный запрос из detector не должен получить ground truth.

### Обработка внутри процесса

Предлагаемые обязанности: приём и хранение access-логов, RuleEngine с whitelist правил, ограниченные группы/окна, сохранение incidents и завершение анализа. Конкретные таблицы и внутренние классы выбирает реализация; общего SQL-протокола с Control нет.

MVP использует match одного запроса, countWindow и именованные Java kinds для последовательностей. Например, серия login с 401 одного IP - оконный сигнал, последующий 200 - последовательность; перебор ID и SQL-подобный query тоже могут быть признаками. Owner mismatch, изменение цены или реальное число покупок по access-логам неизвестны. Это ограничение источника, а не гарантия обнаружить любую атаку.

YAML допускает eq/in, count/countDistinct, groupBy и bounded window. Нет arbitrary JavaScript/SpEL/SQL. Неизвестное поле/operator останавливает подготовку. Ruleset фиксируется до run; пределы числа групп, длительности окна и evidence ограничены. Каталог доступных HTTP-признаков приведён в [документе 04](04-events-and-detection.md).

Повтор req_hash может означать replay или обычный retry: он не доказывает новый бизнес-эффект. Отказы Gateway позволяют исследовать попытки, которые вообще не достигли Shop. Несколько HTTP-наблюдений одного requestId не должны повторно увеличивать счётчик.

### Повторы, поздние события и окна

Для каждого producer/sequence сохраняется содержимое; повтор не добавляет новый вклад в правила. Сохранение данных и прогресса обработки должно исключать потерю или двойной учёт, но восстановление после падения процесса в MVP не используется.

Нельзя передвигать общий watermark только по максимальному увиденному sequence: пачка с меньшим номером может прийти позже из другого потока. Непрерывность проверяется отдельно для Gateway и Shop; одинаковый requestId связывает их записи.

Окна строятся по времени наблюдения с детерминированным порядком при равных timestamps. Поздняя запись может изменить внутренний вывод, поэтому нужное окно пересчитывается в ограниченном буфере. Несколько реплик detector и failover не входят в MVP.

Состояния анализа: ACCEPTING → FINISHING → COMPLETED либо FAILED. После finish Detector обрабатывает полные диапазоны, закрывает окна и публикует итоговые инциденты. До COMPLETED чтение incidents возвращает 409; после завершения набор неизменяем. Правила повторов и границ заданы в [semantics.md](../contracts/semantics.md).

### Содержимое incident

Incident содержит incidentId, detectedAt, непустые requestIds, description и необязательный family. Он сообщает подозрение на попытку, а не подтверждённый ущерб. Severity, confidence, история операторских статусов и предварительные инциденты в текущий контракт не входят.

Control добавляет IncidentAssessment с TRUE_POSITIVE/FALSE_POSITIVE/UNASSESSED, matchedEpisodeIds и reason. Пропуск хранится в detection результата case/episode; искусственный incident для FN не создаётся. Ошибка либо отсутствие family не меняет вердикт обнаружения; ошибку классификации Control поясняет в reason.

## 13. Control, evaluator и пользовательский интерфейс

Control объединяет четыре связанные функции: управление экспериментом, подготовку фикстур, независимую оценку и представление результата. Их не нужно превращать в четыре отдельных сетевых сервиса, но внутри Java-приложения они остаются разными модулями.

`TrialService` принимает families/seed и создаёт trial. `RunCoordinator` управляет состояниями и командами компонентов. `FixtureCoordinator` готовит исходные данные. `EvaluationService` запускает независимые проверки. `ReportAssembler` соединяет результаты без изменения фактов. UI-контроллеры отвечают только за формы, фильтры и выдачу отчёта.

| Сущность | Значение |
|---|---|
| Trial | Испытание выбранных families с seed, содержит последовательные vulnerable/protected runs |
| Run | Один режим, отдельный runId, данные и исполнение плана |
| Case | Один критерий достижения цели атакующего и применимые инварианты |
| Episode | Заранее выделенная последовательность для оценки обнаружения |
| Step / attempt | Плановое действие / конкретная HTTP-отправка |
| Snapshot | Зафиксированные данные или конфигурация, используемые в этом run |
| Ground truth | Приватные ожидаемые свойства: кто owner, какие шаги malicious, какие эффекты допустимы |

Ground truth создаётся до запуска. Например, evaluator знает, что order 123 принадлежит пользователю 8 и что шаг Бориса пытается прочитать именно его. Это знание хранится приватно в Control и не передаётся detector. Для расчёта результата evaluator получает readonly state shop и безопасные response facts, но не вызывает защищаемый calculator как «эталон правильного ответа».

Разделяются effect и detection. Проверки инвариантов служат доказательством effect и описываются в reason. EFFECT_OBSERVED означает достижение заданной цели; EFFECT_NOT_OBSERVED - доказанное отсутствие эффекта; INCONCLUSIVE - недостаток доказательств; техническая ошибка отражается в состоянии run и error. Первая корректная пара credentials может дать EFFECT_OBSERVED при корректной password/JWT-проверке: сильная гарантия против такой кражи в MVP не заявлена.

UI показывает trials/runs, общий progress и причину неполноты, cases и итоговые incidents с оценкой Control. Для missed episode есть результат без выдуманного incident. TrialReport содержит families/seed, результаты обоих режимов и причины исходов; показатели со знаменателями UI вычисляет из cases/incidents. JSON-отчёт сохраняется на стороне UI. Готовый report immutable; редактирование инцидентов и версии отчёта в текущем API не предусмотрены.

Operator Bearer, escaping и пагинация входят в минимальный UI. Control публикуется на loopback, Authorization передаётся явно; cookie-аутентификации нет. Сценарный текст никогда не интерпретируется как HTML. Grafana служит диагностике; число WARN в логах не становится метрикой качества detector.

## 14. Жизненный цикл опыта и служебный протокол

Оператор выбирает одно или несколько из пяти families (либо все пять) и необязательный seed. Остальные параметры фиксированы конфигурацией стенда до запуска. Произвольный baseUrl, callback, Java-код и SQL assertion не принимаются.

Через `/control/v1` доступны GET /scenarios, POST /trials, GET /trials, GET /trials/{trialId}, POST /trials/{trialId}/cancel и GET /trials/{trialId}/report. Создание сразу запускает оба режима. Idempotency-Key обязателен: тот же ключ/body возвращает прежний trial, изменённый body - 409. Отдельного start нет.

Control вызывает внутренние Fixture/Runner/Evaluator через Java-порты, управляет Shop/Gateway через Runtime API prepare/open/close и Detector через prepare/status/log-batches/finish/incidents. Подготовка БД - прямой административный доступ Fixture, без HTTP RESET. Повторы одинаковых управляющих запросов безопасны; изменённые контекст или границы дают 409. HTTP 202 означает принятие, окончание подтверждается состоянием.

Нормальные состояния Trial:

```text
PREPARING -> RUNNING -> FINALIZING -> COMPLETED
```

- В PREPARING закрывается старый доступ, проверяется отсутствие операций, загружаются фикстуры, проверяется baseline, готовятся Runtime-контексты, Runner и Detector.
- В RUNNING открыт admission, Runner исполняет план, политики применяются, access-логи доставляются в Detector.
- В FINALIZING прекращаются новые действия, доказывается завершение принятых операций, завершается анализ, выполняется независимый oracle и сохраняется report.

FAILED означает технически невыполненную подготовку/работу, CANCELLED - отмену, INCONCLUSIVE - недоказанный исход или неполноту. Достоверно успешная атака против protected тоже может дать COMPLETED: опыт завершён, просто защита не выдержала проверку. Любой выход из RUNNING проходит безопасное завершение; terminal state сам по себе не разрешает reset, если cleanupSafe=false.

Сравнение состоит из двух последовательных runs: сначала vulnerable, затем protected. Данные, workload, seed, businessTimeBase и ruleset одинаковы. Одновременная нагрузка двух режимов на одном ноутбуке затруднила бы сравнение из-за конкуренции за общие ресурсы.

### Почему недостаточно дождаться последнего ответа runner

Пусть клиент получил timeout через пять секунд, а SQL-транзакция ещё выполняется. Если немедленно посчитать заказ отсутствующим и сбросить данные, поздний commit может одновременно исказить отчёт и следующий опыт. Аналогичная проблема возникает, если последняя пачка access-логов ещё не получена Detector или detector не закрыл окно.

Поэтому завершение имеет явный барьер:

1. Runner прекращает новые steps и подтверждает сохранение выполненных attempts.
2. Control закрывает Gateway и ждёт CLOSED, затем закрывает Shop и ждёт CLOSED.
3. CLOSED подтверждает in-flight=0 и окончательный lastSequence; instanceId не должен измениться.
4. Control передаёт Detector gatewayLastSequence, shopLastSequence и deadlineAt; тот проверяет непрерывные диапазоны 1..N и завершает анализ.
5. После COMPLETED Control сверяет observedRequestIds с attempts и получает все итоговые incidents.
6. Control снимает итоговое состояние, выполняет oracle и сохраняет report; только затем допускается подготовка следующего прогона.

Каждая стадия имеет deadline. Пропуски или неподтверждённое завершение дают INCONCLUSIVE. При отказе/перезапуске run не продолжается: старые исполнители останавливаются, новый запуск получает свежие фикстуры. Поздние admission rejects закрытого run попадают только в операционный лог и не меняют завершённый поток.

## 15. Как считаются результаты

Метрики считают заранее определённые случаи и последовательности. Один HTTP-запрос может породить итоговый лог Gateway и итоговый лог Shop; это один запрос, а не две атаки.

| Метрика | Что означает и как считается |
|---|---|
| ASR | Доля malicious cases с EFFECT_OBSERVED среди полноценно оценённых cases |
| Detection recall | Доля malicious episodes с detection=DETECTED среди полностью наблюдённых malicious episodes |
| Incident precision | TP incidents / (TP + FP incidents): какая часть итоговых выводов правильна |
| Benign FPR | Доля benign episodes хотя бы с одним ложным incident |
| False block rate | Доля пригодных легитимных logical operations, ошибочно остановленных защитой |
| Detection delay | Время incident минус первое attack-specific evidence; только по итоговым incidents, при отдельном измерении |
| Coverage | Сколько запланировано, выполнено и оценено; сколько ошибок, пропусков данных и INCONCLUSIVE |
| Performance | Latency percentiles, throughput, ошибки и ресурсы при фиксированном workload |

Recall включает предотвращённые попытки: атака может существовать, хотя ущерба нет. ASR не заменяет число нарушенных инвариантов; отсутствие эффекта не всегда является заслугой защиты. Нулевой знаменатель даёт N/A. Неполные случаи исключаются из основной доли с явным показом их численности и причин; итоговая пара требует двух COMPLETED runs.

Incident связывается с episode по requestId → attack-specific step. Одного общего IP/run или подготовительного login недостаточно. Несколько incidents дают один detected episode, но несколько элементов precision. Ошибка/отсутствие family не превращает подтверждённую попытку в FP. INCONCLUSIVE/UNASSESSED исключаются из соответствующих знаменателей. Поле detection рассчитывается единообразно для всех cases одного episode по [правилам контракта](../contracts/semantics.md), отдельно от effect; связанный TP несовместим с MISSED.

False block rate, detection delay и performance требуют отдельных технических измерений: текущий TrialReport не содержит их исходных данных.

Для гонок публикуются repetitions/seeds и число эффектов k/n. Коррелированные запросы одного episode не объявляются независимой статистической выборкой. Пороги качества и достаточное число повторов калибруются пилотом и фиксируются до итоговой серии; заранее обещанных универсальных процентов защиты нет.

## 16. Развёртывание, доступ к данным и отказы

### PostgreSQL и права

Один PostgreSQL обслуживает независимые `shop_vulnerable` и `shop_protected`, а также внутренние хранилища стенда. Control хранит план/попытки/эталон/отчёты, Detector - полученные логи и инциденты. Их физическая схема не является общим контрактом; общей audit-view и SQL jobs между сервисами нет.

Обычная shop-role имеет DML только собственной БД, без DDL/TRUNCATE. Catalog adapter использует отдельную SELECT-only роль, чтобы учебная SQL-слабость не давала доступ к пользователям или изменению данных. Gateway/Shop отправляют логи по HTTP, без SQL-credentials Control/Detector. Detector читает только своё хранилище и пишет собственные результаты. Evaluator читает бизнес-состояние без password_hash. Fixture admin и migration owner используются отдельным служебным путём. Сценарным классам не передаются admin/evaluator adapters; внутри общей JVM это граница кода, а не изоляция прав процесса.

Роли ограничиваются SQL grants и функциями/политиками записи, а не названием Java-сервиса. Общий PostgreSQL остаётся общей точкой отказа: логические БД не создают физическую отказоустойчивость. Для локального учебного стенда это осознанный компромисс.

### Сети

| Internal network | Участники и назначение |
|---|---|
| `lab-traffic` | Control со встроенным runner, gateway, LGTM collector: сценарный HTTP и telemetry |
| `shop-backend` | Gateway и оба shop: бизнес-запросы |
| `shop-admin` | Control/gateway/shop: подготовка, admission, завершение |
| `lab-data` | Control/detector/shop и PostgreSQL: SQL своих хранилищ; gateway не входит |
| `lab-logs` | Shop/gateway/control и detector: Detector API |
| `lab-observe` | Control/detector/gateway/shop и LGTM: наблюдаемость |

Control имеет доступ к shop-admin и lab-data, а его встроенный runner разделяет сетевые права процесса. Ограничения ScenarioHttpClient и запрет зависимостей от admin/SQL - программные, не контейнерные. Внешний egress запрещён сетевыми средствами; внутренние endpoints дополнительно защищены binding и credentials. Пользовательский Java/shell не исполняется.

На host по умолчанию публикуются только UI и Grafana через loopback. Для ручной демонстрации API допустим отдельный profile с loopback-входами gateway; прямой shop не публикуется. В runtime нет Docker socket, host network, privileged-контейнеров и внешнего proxy. Запрет egress проверяется настоящими запросами, включая внешний IP/hostname, host gateway, DNS/redirect и служебные endpoints.

### Инициализация и эксплуатация

Планируемая команда `docker compose -f infra/compose.yaml up --build` запускает локальную генерацию keys/credentials, миграции, seed и readiness. Health означает готовность работать с зависимостями, а не только поднятый JVM. В git входят versioned config и `.env.example` с placeholders; рабочие ключи лежат в локальном хранилище.

Fixture generator создаёт 24 синтетических пользователя с корзинами, 12 опубликованных товаров и draft canary, пять купонных состояний и согласованную историю заказов. Seed, бизнес-время, owners, counts и snapshots фиксируются. Пустые password hashes запрещены; реальные credentials не используются.

Цель готовности на чистой описанной машине - не более 10 минут с учётом загрузок; тёплый запуск измеряется отдельно. CPU/RAM, размер очередей, connection pools, длительность и объём evidence ограничиваются до опыта. Это требования к реализации, а не уже полученные результаты запуска.

### Допущение о непрерывной работе

Во время измерения все необходимые процессы и хранилища работают непрерывно. Мы сохраняем данные для отчёта, но не строим восстановление выполняющегося run. При restart control оставшиеся нетерминальные runs помечаются INCONCLUSIVE; старое исполнение не возобновляется. Новый опыт начинается после остановки старых исполнителей, перезапуска стенда и подготовки фикстур.

| Ситуация | Что происходит |
|---|---|
| Чтение логов или detector отстаёт, процессы живы | Очереди доставки сохраняют записи; FINALIZING ждёт ingest и COMPLETED до deadline |
| Перезапуск shop/gateway/detector/control либо отказ обязательной БД | Run INCONCLUSIVE, без автоматического продолжения; новый запуск после подготовки |
| Потерян HTTP-ответ, сервер жив | In-flight, итоговые access-логи и readonly state устанавливают результат; обычный retry проверяет идемпотентность |
| Переполнен бюджет локального limiter | Admission закрывается, запрос 503/INFRA_REJECT, run INCONCLUSIVE; активные ограничения не вытесняются |
| Ошибка записи/схемы/полноты security-логов | Закрыть admission, INCONCLUSIVE; бизнес-commit не отменяется задним числом |
| LGTM недоступен | Отдельная неисправность наблюдаемости; путь HTTP/JSON → Detector от LGTM не зависит |
| Quiescence не доказан | cleanupSafe=false; reset запрещён до остановки старого исполнения |

Логи связаны requestId/traceId; OpenTelemetry продолжает причинную связь до detector через span links. Измеряются latency/errors, policy time, log-ingest/detector lag, пропуски sequence, run deadline и report coverage. Redaction действует также на ошибки и HTTP-debug. Размер строки ограничен 64 KiB, число записей - 100000 на producer/run; достижение лимита останавливает опыт с INCONCLUSIVE, без тихого отбрасывания.

## 17. Принятые решения и их последствия

| Решение | Почему принято | Ограничение или цена |
|---|---|---|
| Один shop codebase, два процесса/DB | Один контракт и одинаковые нормальные операции облегчают сопоставление | Учебные слабости нужно явно изолировать стратегиями и миграциями |
| Магазин как модульное приложение | Checkout и купон помещаются в одну транзакцию | Нет исследования распределённой торговой транзакции |
| Runner внутри control; gateway и detector отдельно | Меньше процессов и нет сетевого протокола управления генератором | Общие heap/CPU и права JVM; нужны bounded executor, cancellation и проверки границ кода |
| Detector отдельно от control | Ground truth закрыт интерфейсами и полномочиями; анализ выполняется независимо | Р4 обслуживает два приложения; часть адаптеров распределена между остальными ролями |
| JDBC и PostgreSQL | Видны locking, условия UPDATE и транзакционные границы | Дисциплина SQL/индексов/rollback и реальные concurrency tests |
| Cart revision + idempotency в orders | Повтор возвращает прежний результат; одна версия корзины создаёт один заказ | Locks и UNIQUE; каталог/условия купонов неизменяемы в run |
| Прямая доставка HTTP/JSON в Detector | Detector использует access-логи API/gateway, без сборщика в Control | Commit и лог не атомарны; сбой делает run INCONCLUSIVE, восстановления нет |
| Rule-based detector | Вывод объясняется конкретным правилом/evidence и воспроизводится | Нет обещания обнаруживать неизвестные паттерны или распознавать намерение по одинаковому HTTP |
| Immutable snapshots и paired runs | Известно, что именно сравнивается и с какими параметрами | Конфигурацию нельзя незаметно менять посередине опыта |
| CLOSED/lastSequence/finishAnalysis | Конечный отчёт основан на полном исполнении и анализе | Orchestration сложнее, чем запуск HTTP-скрипта |
| Thymeleaf, JSON-export, локальный LGTM | Достаточный интерфейс и диагностика при небольшом числе технологий | Дизайнерская SPA и PDF pipeline не являются частью MVP |
| Whole RUB и числовые ids | Простые точные вычисления и понятные сценарии объекта | Дробные цены не поддержаны; id не рассматривается как секрет |

Внешний authorization service имеет смысл при более сложных отношениях sharing/organization, а ML - при отдельном исследовании качества обнаружения. OpenFGA, Schemathesis и PyOD допустимы после baseline, с независимой оценкой и своими условиями сравнения. Они не нужны для доказательства пяти основных семейств первой версии.

## 18. Как команда реализует и проверит систему

### Четыре роли

| Роль | Основной результат | Помощь общей интеграции |
|---|---|---|
| Р1: API и данные | Shop в двух режимах, API/DTO, миграции, fixtures, transactions и access logging | Readonly данные и адаптеры независимого oracle |
| Р2: защита | Gateway, политики, JWT, limiter, access logs | Compose/сети, Runtime/lastSequence, базовая наблюдаемость |
| Р3: генератор | Сценарии/benign, seed/планы, concurrency, HTTP execution | Java prepare/start/cancel, ограниченный HTTP-клиент и AttemptSink |
| Р4: detector/dashboard | Rules/windows/incidents, control/evaluator, UI и reports | Общая семантика эксперимента и окончательных метрик |

API-контракт ревьюят Р1+Р2, access-логи/политики - Р2+Р4, plan/steps - Р3+Р4. Oracle проверяют Р1+Р3+Р4, чтобы ошибка production-логики не попала в независимый эталон. Вклад фиксируется по фактически выполненным модулям, тестам и демонстрациям.

### Порядок работ

Сначала создаются schemas и сборочный spike: совместимость зависимостей, validator keywords, локальный limiter и SQL grants. Затем поднимаются skeleton/сети/БД, минимальные listeners и trace. Первый вертикальный результат - BO-01: свой/чужой order, запрос через gateway, access-логи, одно правило detector, независимый owner oracle и JSON-отчёт в UI.

После этого расширяется API, реализуются checkout/rate/injection и остальные сценарии с benign controls. Следующий этап посвящён достоверности: поздний commit при живом сервере, задержки/дубли/пропуски логов, deadline/instanceId, закрытие окон и reset. Завершают работу измерения paired series, cold start, нагрузка защитного слоя, документация реализации и демонстрация.

Такой порядок проверяет самые рискованные границы рано: команда видит всю цепочку доказательства до того, как написан полный магазин или сложный дашборд.

### Проверки

Unit tests проверяют чистые политики/parser/calculator. Contract tests проверяют реальные schemas, нормальные запросы обоих режимов, неизвестные поля/типы и errors. Testcontainers с PostgreSQL проверяет row locks, coupon/cart races, уникальность, rollback и SQL grants. State model с jqwik генерирует последовательности setQuantity/coupon/checkout/retry и сравнивает их с независимой моделью.

Integration suite включает JWT claims/signature, BOLA profile/order, все варианты повторов checkout, expiry equality, server-price и canary injection. Logging tests проверяют одну итоговую access-запись после commit/rollback/ошибки, отсутствие секретов, identical retry/conflict, sequence gaps и INCONCLUSIVE при неполноте. Detector tests проверяют поздние/out-of-order пачки, отсутствие повторного вклада, границы finish и неизменность итоговых incidents. Сетевые проверки подтверждают отсутствие обхода Gateway, а secret scans/escaping tests - отсутствие утечки или интерпретации входа в UI.

Планируемые команды: `./mvnw verify` для основной сборки/unit/integration/smoke и `./mvnw -Pacceptance verify` для полной серии с фиксированными seeds/budgets и reports. Это план будущей приёмки. Сейчас `./mvnw clean generate-sources` генерирует HTTP-код, `./mvnw compile` проверяет его сборку; CI проверяет воспроизводимость генерации. Protected-инвариант, нарушенная изоляция, утрата обязательного evidence или невоспроизведённый vulnerable baseline не дают успешную приёмку. Объявленный остаточный риск, например первая корректная пара, оценивается по фактической гарантии.

### Результат сдачи

Команда предоставляет воспроизводимый локальный стенд, исходный код, актуальную архитектуру/контракты, автоматические тесты и сохранённые отчёты, сценарий либо видео демонстрации и фактический вклад участников. На демонстрации показываются BOLA, безопасный retry и race, все пять семейств с benign traffic, завершение отложенной обработки логов, INCONCLUSIVE при потере доказательства и экспорт сравнения.

Граница завершённого MVP - возможность повторить опыт и объяснить его результат по сохранённым фактам, конфигурациям и независимым проверкам. Это проверяемое свойство реализации; наличие выбранного framework, diagram или контейнера само по себе его не подтверждает.

## Физическая реализация модели данных

Shop хранит 7 таблиц: users, products, coupons, carts, cart_items, orders и order_items. Логическая схема одинакова для двух режимов; отдельные protected constraints добавляют бизнес-границы и уникальность эффекта. Orders хранит цену позиции и успешный ответ; приватный fixture manifest фиксирует независимый эталон каталога, условий купонов и начальных счетчиков. Эти источники нельзя смешивать.

Control и Detector хранят собственные данные; фиксированной общей lab-схемы в текущих контрактах нет. Прежние 12 lab-таблиц, SQL jobs и audit-проекция сохранены в [архиве](data/legacy-lab/README.md) как история проектирования, а не текущие миграции. Case/episode/assessment входят в итоговый TrialReport, отдельные HTTP-сущности для них не требуются.

Полный словарь shop-полей и решения о транзакциях приведены в документе 02. Начальные DDL, независимые SQL-проверки, DBML и ER-исходники находятся в docs/data. Источником физической модели магазина служит SQL; изменение таблицы должно сопровождаться обновлением DBML/ER и словаря полей. Документ 04 описывает HTTP-контракт access-логов и инцидентов. Обзорные схемы показывают концепции и последовательности; внутреннее хранение Control/Detector определяется реализацией. OpenAPI находится в contracts, подготовка данных - в модуле Fixture.
