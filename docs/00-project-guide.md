# API Security Lab: проект от идеи до реализации

Версия 1.2, 21 октября 2026 года. Документ объясняет весь проект последовательно и не требует предварительного контекста. Описаны принятые решения для будущей реализации; код, испытания и измерения ещё предстоят. Названия внутренних Java-классов ниже задают предлагаемое разделение обязанностей, а не обозначают уже существующие классы.

## 1. Что мы строим и какой результат получаем

API Security Lab — учебный локальный стенд, на котором можно воспроизвести опасное поведение клиента, применить защиту, обнаружить подозрительные действия и проверить реальный результат. Все пользователи, пароли, товары и заказы синтетические. Стенд запускается на машине команды в контейнерах и не обращается к внешним целям.

Защищаемый объект — небольшое API магазина. API принимает HTTP-запросы: зарегистрировать пользователя, войти, прочитать профиль, найти товар, изменить корзину и создать заказ. Магазин нужен потому, что у него есть понятные правила безопасности: заказ принадлежит конкретному пользователю, цена задаётся сервером, купон имеет срок и лимит, один запрос на покупку не должен случайно создавать две покупки.

Инвариант — правило, которое должно сохраняться после допустимой операции: например, количество товара положительно, а число заказов одной операции не превышает одного. Такие правила позволяют проверить результат программы независимо от её собственных сообщений.

Одна реализация API запускается в двух режимах. В vulnerable отдельные защитные проверки намеренно ослаблены. В protected они включены и подкреплены транзакциями и ограничениями БД. Через оба режима проходит сопоставимый набор запросов, после чего стенд показывает различие.

Главный результат — отчёт с проверяемыми доказательствами. Он отвечает на четыре самостоятельных вопроса:

1. Достиг ли атакующий цели: например, прочитал чужой заказ или создал повторную покупку?
2. Какая защита разрешила, отметила или остановила действие?
3. Обнаружил ли отдельный detector подозрительное поведение?
4. Все ли необходимые шаги, события и изменения состояния известны, чтобы доверять выводу?

HTTP-отказ, обнаружение и отсутствие ущерба не равнозначны. Запрос может вернуть 200, раскрыть чужие данные и одновременно породить инцидент. Повтор checkout тоже может вернуть 201, но отдать уже созданный заказ без повторного эффекта — это правильная идемпотентность. При сетевом timeout заказ иногда уже записан в БД. Поэтому вывод нельзя строить только по коду ответа.

## 2. Как выглядит один эксперимент

Предположим, пользователь Анна владеет заказом 123, а пользователь Борис пытается его прочитать. Оператор выбирает сценарий доступа к чужому объекту и запускает сравнение.

Сначала стенд создаёт одинаковые исходные данные для двух режимов. Генератор входит как Борис и отправляет `GET /api/v1/orders/123`. В vulnerable стратегия чтения не проверяет владельца и возвращает заказ Анны. В protected запрос проверяется по authenticated user и owner, поэтому получает 404 — так же, как неизвестный заказ.

API записывает наблюдаемые факты: кто обращался, к какому типу объекта, совпал ли владелец, что реально вернулось. Detector видит эти факты и может создать инцидент несовпадения владельца в обоих режимах, включая незаблокированное чтение. Независимый evaluator знает из исходных данных, кому принадлежал заказ, и проверяет, какие поля получил Борис. Он устанавливает эффект атаки и правильность обнаружения.

Оператор открывает карточку опыта: запросы, решения защиты, события, инциденты, проверку владельца и сравнение. Из неё можно получить JSON-отчёт. Это весь основной цикл проекта; остальные сценарии используют ту же инфраструктуру, меняя исследуемое свойство.

## 3. Какие угрозы демонстрирует стенд

| Семейство | Простое объяснение | Что проверяем |
|---|---|---|
| Credential stuffing | Попытки войти по подготовленному списку синтетических пар логин/пароль | Рабочие сессии, лимиты источника/аккаунта, обнаружение серии и влияние на обычные входы |
| BOLA/IDOR | Подмена идентификатора, чтобы получить чужой объект | Профили и заказы; факт раскрытия данных, а не только HTTP-код |
| Replay | Повтор уже выполненной операции | Один бизнес-эффект при retry, конфликт изменённого запроса и запрет повторного intent |
| Injection | Значение параметра меняет смысл SQL в учебном уязвимом адаптере | Попадание скрытого контрольного товара в выдачу; корректная параметризация protected |
| Business logic abuse | Нарушение правил магазина корректными по форме или конкурентными запросами | Купон, quantity, гонка checkout, обход серверной цены |

Для каждого семейства нужен легитимный (benign) контроль: собственный заказ, нормальный поиск, разрешённый купон, обычный вход, безопасный retry. Иначе можно получить формально «эффективную» систему, которая блокирует всех пользователей.

Купонное семейство включает просроченный, исчерпанный и повторно применяемый купон. Конкурентность проверяется отдельно для двух checkout одной корзины и для двух пользователей, претендующих на последнее использование купона. Реальная injection в первой версии — SQL; NoSQL/command-подобные строки проходят как отрицательный ввод без дополнительных движков.

## 4. Архитектура целиком

Пять Java-приложений образуют шесть работающих Java-процессов: магазин запускается дважды. Ещё три контейнера предоставляют PostgreSQL, Redis и локальную наблюдаемость. В базовом Compose получается девять постоянно работающих контейнеров; одноразовые задания подготовки в это число не входят.

| Компонент | Что делает | Почему выделен |
|---|---|---|
| `shop-api` × 2 | Пользователи, каталог, корзина, заказ, предметная защита и события | Два независимых режима одного контракта для сравнения |
| `lab-gateway` | Принимает сценарный HTTP, проверяет токен/схему/лимиты, выбирает backend | Общая точка входа и место универсальных защит |
| `scenario-runner` | Исполняет план запросов, создаёт конкурентность, сохраняет результаты attempts | Нагрузка и таймауты сценария не занимают процесс UI |
| `lab-detector` | Читает безопасную проекцию событий, применяет правила, создаёт incidents | Изоляция от ответов эксперимента и самостоятельное восстановление |
| `lab-control` | Управляет опытом, готовит данные, оценивает эффект, показывает UI и отчёт | Одна точка управления всем жизненным циклом |
| PostgreSQL | Бизнес-состояние, audit, задания, incidents, reports | Долговечные данные и транзакционные гарантии |
| Redis | Краткоживущее состояние ограничений входа | Готовые распределённые счётчики без вмешательства в checkout |
| Grafana LGTM | Логи, метрики и traces | Техническая диагностика компонентов |

Полезно различать четыре потока взаимодействия:

- **Бизнес-запросы:** runner → gateway → выбранный shop → его БД.
- **Управление:** оператор → control; затем задания runner, подготовка shop, открытие/закрытие gateway и задания detector.
- **Доказательства:** gateway и shop → audit; detector → incidents; evaluator → результаты и report.
- **Наблюдаемость:** приложения → логи, метрики и traces в LGTM.

```text
                       +-> gateway:8081 -> shop-vulnerable -> shop_vulnerable DB
operator -> control -> runner
                       +-> gateway:8082 -> shop-protected  -> shop_protected DB

gateway + shop outbox -> audit -> detector view -> detector -> incidents
control / evaluator  -> steps + audit + readonly shop state + incidents -> report
```

Control не проксирует каждую покупку через себя. Detector не стоит на пути HTTP-запроса. Отчётный audit не заменяется обычными логами: потерянный debug log и потерянное доказательство успешной операции имеют разные последствия.

## 5. Стек и причины выбора

| Решение | Зачем оно нужно | Что приходится учитывать |
|---|---|---|
| Java 25, Maven Wrapper | Один язык команды, воспроизводимая сборка; virtual threads для HTTP-исполнения | Потоки не заменяют бюджеты, таймауты и ограничения соединений |
| Spring Boot 4.0.x | Конфигурация приложений, HTTP, security, lifecycle и интеграция с БД | Patch-версии фиксируются после проверки сборки |
| Spring Cloud 2025.1.x, Gateway Server Web MVC 5.0.x | Gateway в совместимой servlet-линии | Проверяется работа фильтров, двух входов и чтения body |
| Spring JDBC/JdbcClient, PostgreSQL 17 | SQL, locks и транзакции видны явно | Нужно самостоятельно аккуратно проектировать запросы и границы транзакций |
| Flyway | Общие и protected-миграции применяются воспроизводимо | Миграционная роль отделена от runtime |
| Bucket4j + Redis | Переиспользование limiter, а не разработка собственного продукта счётчиков | Поведение при отказе Redis задаётся явно |
| OpenAPI 3.1.0, JSON Schema | Проверяемые HTTP/event/config contracts | Validator должен реально поддерживать использованные keywords |
| Thymeleaf | Формы, таблицы, фильтры и экспорт в одном control-приложении | Сложная SPA не нужна для результатов стенда |
| OpenTelemetry + LGTM | Связь запросов, логов, метрик и async-обработки | Телеметрия может теряться отдельно от доказательного audit |
| JUnit, Testcontainers, jqwik | Функциональные, транзакционные и модельные проверки | Race/grants проверяются в PostgreSQL, не в упрощённой in-memory БД |

Точные версии библиотек/адаптеров и digest образов фиксируются на первом техническом этапе. Проверка OpenAPI включает required/type/bounds/additionalProperties, nullable, local refs, query и повторное чтение тела после validator. Одного номера версии стандарта недостаточно. Это проверка выбранной реализации, а не повод писать собственный универсальный validator.

Отдельный broker не включён в первую версию: события и задания могут надёжно обрабатываться из PostgreSQL при нужном масштабе. Полноценный внешний сервис авторизации тоже не требуется для owner-only модели. Эти решения уменьшают число компонентов, сохраняя основную исследовательскую задачу.

## 6. Как организован Java-проект

Репозиторий — Maven monorepo с отдельным собираемым приложением для каждого процесса. Корневой pom фиксирует общие версии и порядок сборки; Maven Wrapper обеспечивает одинаковый запуск у участников и в CI.

```text
apps/
  shop-api/          # auth, catalog, cart, checkout, orders, lab-admin, audit
  lab-gateway/       # listeners, routing, policies, admission, audit
  scenario-runner/   # plan, scenarios, executor, lease, results
  lab-detector/      # ingestion, rules, windows, incidents, jobs
  lab-control/       # experiments, fixtures, evaluator, ui, reports
libs/
  lab-contracts/     # общие wire records/enums
  lab-observability/ # trace propagation, redaction, соглашения метрик
  lab-test-support/  # test clients и fixtures, только test scope
contracts/
  shop-api.yaml
  control-api.yaml
  runner-api.yaml
  lab-admin-api.yaml
  security-event.schema.json
  incident.schema.json
  experiment.schema.json
config/{policies,rules,scenarios}/
db/{shop/common,shop/protected,lab}/
fixtures/
infra/compose.yaml
tests/acceptance/
```

Внутри приложения код группируется по предметной функции. Например, в shop пакет checkout содержит входные команды, прикладной сценарий оформления, правила и SQL-адаптеры этого сценария. Не нужно складывать все контроллеры всех областей в одну гигантскую папку и делить бизнес-логику только по техническим аннотациям.

Практический путь вызова: HTTP controller разбирает запрос → прикладной use case организует операцию → предметные правила проверяют допустимость → repository/adapter выполняет SQL или внешний вызов. Контроллер не управляет купонным счётчиком, repository не решает, что считать успешной атакой, а генератор не читает SQL напрямую.

Общие библиотеки ограничены контрактами и техническими соглашениями. Приложения не импортируют внутренние классы друг друга. В частности, detector не получает fixture catalog или evaluator code через «удобную общую библиотеку»: иначе разделение процессов формально сохранится, а независимость знания о сценариях будет потеряна.

Конфигурации правил, политик и сценариев имеют версию. Их hash фиксируется в run, поэтому отчёт можно связать с точным набором решений. Рабочий экземпляр snapshot не изменяется во время измерения.

## 7. Устройство demo API и двух режимов

### Модули и точки расширения

Shop включает auth, catalog, cart, checkout и orders. Служебные lab-admin и audit обслуживают стенд, но не открываются через обычное API. Общие controller, DTO (типизированные структуры запросов/ответов) и response mapper задают один внешний контракт.

Выбор уязвимой или защищённой реализации делается при запуске через Spring-конфигурацию. Удобные границы стратегий — `OrderReader`, `CatalogSearch`, `CheckoutExecutor`: они принимают одинаковую типизированную команду и возвращают одинаковый результат, но используют разные проверки и SQL-протоколы. Имена конкретных классов можно уточнить при создании skeleton; существенны интерфейс и конфигурационная граница.

Protected owner query использует id объекта и authenticated user. Vulnerable может читать тот же объект только по id. Protected search использует параметры SQL и разрешённый enum сортировки; vulnerable содержит один выделенный адаптер с небезопасным построением запроса. Protected checkout выполняет атомарный протокол; vulnerable содержит именованные учебные слабости для replay, quantity, цены или купона.

Такие отличия не должны размазываться по каждому controller в виде случайных `if (vulnerable)`. При этом общий `@Valid` или одинаковый защитный CHECK в обеих БД не должен незаметно исправить слабость, которую требуется показать. JSON syntax и ресурсные пределы остаются общими, а исследуемые проверки включаются выбранной стратегией.

### Внешнее поведение

Путь начинается с `/api/v1`; данные передаются JSON. JWT — подписанный токен, которым клиент подтверждает выданную ему сессию; он обязателен везде, кроме register/login. Числовые ids положительные, UUID используются для intent/requests/events. Деньги — целые рубли, Java long/SQL bigint, currency RUB; quantity от 1 до 99, не более 100 разных позиций корзины.

| Операция | Запрос и назначение |
|---|---|
| `POST /auth/register` | login/password/name/email; создаёт User и пустую корзину |
| `POST /auth/login` | login/password; возвращает accessToken, tokenType, expiresIn |
| `GET /users/me` | Профиль текущего subject |
| `GET /users/{userId}` | Собственный профиль; отдельная поверхность BOLA |
| `GET /products` | Поиск q, sort=id/name/price, limit/offset; только опубликованные товары |
| `GET /products/{productId}` | Опубликованная карточка |
| `GET /cart` | Корзина, revision, позиции, купон и текущие суммы |
| `POST /cart/items` | productId/quantity; добавляет количество |
| `PATCH /cart/items/{productId}` | quantity; устанавливает абсолютное количество |
| `DELETE /cart/items/{productId}` | Удаляет позицию; отсутствие допустимо |
| `PUT /cart/coupon` | code; выбирает один купон без расходования лимита |
| `DELETE /cart/coupon` | Убирает купон |
| `POST /checkout-intents` | cartRevision; создаёт серверный snapshot будущего checkout |
| `POST /orders` | intentId/quotedTotal и Idempotency-Key; создаёт или возвращает Order |
| `GET /orders` | Собственная история с пагинацией |
| `GET /orders/{orderId}` | Собственный Order |

User содержит id/login/name/email; пароль или hash не возвращаются. Product содержит id/name/description/price/currency. Cart содержит id/userId/revision/items/coupon/subtotal/discount/total/currency/updatedAt; позиция — productId/name/quantity/unitPrice/lineTotal. Order сохраняет владельца, intentId, items и условия цены/купона на момент операции, суммы, createdAt и status CREATED. Отмен, платежей и возвратов в MVP нет.

Создание пользователя, intent и заказа возвращает 201, чтение/изменение корзины и login — 200. Ошибки имеют единый Problem с type/title/status/code/requestId. Основные статусы: 400 для валидации, 401 для auth, 404 для отсутствующего или чужого объекта, 409 для конфликта состояния, 429 для rate policy, 503 для зависимости или закрытого run. Неожиданный 500 не сообщает SQL/stack trace.

### Данные

Бизнес-таблицы: users, products, coupons, carts/cart_items, orders/order_items. В carts есть revision, в products — published/catalog_version, в купоне — срок, max_uses, used_count и terms_version. Скрытый draft-товар служит canary: его появление в обычной выдаче — наблюдаемый эффект injection.

Служебные таблицы решают конкретные задачи: checkout_intents хранит одноразовое намерение; idempotency_records — результат успешной операции; coupon_redemptions связывает расход лимита с заказом; security_outbox хранит ещё не доставленные события; execution_ledger — принятые и завершённые запросы.

Protected дополняет PK/FK бизнес-ограничениями: допустимое количество, корректные суммы, used_count≤max_uses, уникальный order на intent и на пару cart/revision. Межтабличное равенство суммы заказа сумме его строк нельзя обеспечить одним обычным CHECK; его обеспечивает транзакция и проверяет независимый oracle.

Исторический заказ хранит свои цены и условия. Evaluator сравнивает их с trusted fixture snapshot соответствующей версии, а не с нынешней ценой товара. Иначе обычное изменение каталога ошибочно выглядело бы нарушением старого заказа.

## 8. Почему checkout устроен через intent и idempotency key

Обычная сеть может потерять ответ уже выполненного запроса. Если клиент просто повторит «создай заказ», сервер рискует выполнить покупку второй раз. Одновременно нужно отличить технический retry от попытки изменить уже выполненную команду или заново использовать прежнюю корзину.

Для этого применяются два механизма с разными обязанностями:

- **Checkout intent** — серверное разрешение выполнить конкретную операцию над конкретной revision корзины и snapshot цены. У него есть owner, срок и отметка использования.
- **Idempotency key** — идентификатор попытки клиента получить один результат. Повтор с тем же key и телом возвращает сохранённый результат, не создавая новый эффект.

Пример: корзина revision 7 содержит две позиции общей стоимостью 3000 рублей; купон 10% даёт итог 2700. Сервер создаёт intent I. Клиент отправляет I, quotedTotal=2700 и key K. Сервер создаёт Order 50, но ответ теряется. Retry I/K возвращает тот же Order 50. Новый key K2 с уже использованным I даёт INTENT_ALREADY_USED. K с другим quotedTotal даёт IDEMPOTENCY_CONFLICT.

Транзакция объединяет изменения: они фиксируются вместе при commit или откатываются при rollback. Protected выполняет checkout в одной PostgreSQL-транзакции при явном протоколе locks:

1. Занимает key в scope user/method/route/key; для прежнего успеха сравнивает fingerprint и возвращает сохранённый ответ.
2. Блокирует cart, затем intent; проверяет owner, revision, срок и consumed state.
3. Сверяет состав, цены, условия купона и quotedTotal с серверным расчётом.
4. Атомарно расходует купон при действующем сроке и остатке.
5. Создаёт order/items/redemption, отмечает intent использованным, очищает корзину и увеличивает revision.
6. Сохраняет успешный status/body для key, terminal record и outbox event; фиксирует всё одним commit.

Единый порядок блокировок: key → cart → intent → coupon; внутри одного типа — возрастающий id. Все mutations корзины берут её row lock. Два intent одной revision не дают две покупки; constraints выступают дополнительным рубежом. Лишний no-op DELETE/PATCH не меняет revision.

Fingerprint вычисляется по каноническим типизированным значениям запроса, маршруту и версии контракта. Порядок JSON-полей не меняет его, JWT/requestId/trace в него не входят. При повторе успешного key lookup результата предшествует новой проверке expiry intent. Неуспешная транзакция не оставляет committed pending key; в MVP сохраняются только успешные результаты.

TTL intent первоначально 120 секунд по бизнес-часам; даты купонов проверяются строго `now < expiresAt`. Бизнес-часы двух прогонов имеют одинаковую стартовую базу. JWT использует реальные часы и остаётся многократным: проверка каждого jti как одноразового сломала бы обычные последовательные запросы пользователя. Эта защита предотвращает повторный бизнес-эффект, но не новые допустимые действия обладателя украденного bearer.

## 9. Как реализуется gateway и применение политик

Gateway имеет два бизнес-входа и отдельный служебный интерфейс. Маршрут определяется доверенным входным listener, а не значением Host/X-Target или иным заголовком клиента. Run/step/epoch-контекст принимается только после проверки harness credential и активного задания. Role/owner headers клиента удаляются; shop самостоятельно проверяет access JWT.

Внутренние обязанности разделены между admission, routing, PolicyChain, audit writer и proxy. Admission отвечает, можно ли принимать новые requests этого run. Routing знает фиксированные backend. Политики вычисляют решение, а chain определяет фактическое продолжение или отказ.

```java
interface GatewayPolicy {
    String id();
    int order();
    boolean appliesTo(RequestContext request);
    PolicyEvaluation evaluate(RequestContext request, PolicySnapshot snapshot);
}
```

Результат содержит policyId/version, evaluationStatus, wouldDecision, reasonCode, duration и безопасные facts. В OFF проверка не выполняется. В OBSERVE вычисляется решение и обновляется отдельное shadow-state, но запрос продолжается. В ENFORCE BLOCK останавливает запрос. FLAG означает продолжение с отметкой и не создаёт incident автоматически.

Нужно хранить обе стороны: `wouldDecision=ALLOW/BLOCK/FLAG` и `enforcedAction=CONTINUE/REJECT/INFRA_REJECT`. Для пропуска/ошибки wouldDecision=null. EvaluationStatus различает EVALUATED, SKIPPED, NOT_APPLICABLE, NOT_REACHED, MISSING_CONTEXT, ERROR. Например, wouldDecision=BLOCK при OBSERVE не увеличивает число реальных блокировок.

Порядок обработки: обязательный admission/ресурсные пределы → обязательный JWT для закрытых endpoints → OpenAPI validation → login/rate policy → дополнительные признаки ввода → durable audit и разрешённый proxy. После первого отказа остальные экспериментальные проверки имеют NOT_REACHED. Audit является внешней обязательной обвязкой и выполняется даже при раннем 400/401/413/429.

JWT проверяется по фиксированным alg, подписи, issuer, audience, exp и nbf. Начальный TTL access token — 15 минут, clock skew — 5 секунд. Отдельный target имеет свою ожидаемую конфигурацию ключа/claims. Успешная аутентификация устанавливает личность; право прочитать Order по-прежнему проверяет shop.

Rate policy использует Bucket4j/Redis и два бюджета: источник и HMAC нормализованного login. Результат проверки пароля приходит от доверенного shop. На нём строятся backoff/временная блокировка; очереди, задержки и concurrency ограничены. Источник задаётся доверенным harness-контекстом, а не произвольным X-Forwarded-For.

State namespace включает opaque partition, policy version и mode, поэтому target/run не наследует чужую блокировку. Если Redis не отвечает, ENFORCE даёт 503/INFRA_REJECT, OBSERVE отмечает ERROR проверки. Если нельзя записать обязательный audit, новый downstream не вызывается. Ошибка после downstream требует проверки результата, а не заявления «защита сработала».

Обычная paired-конфигурация: vulnerable с OBSERVE gateway-политик и учебными shop-стратегиями; protected с ENFORCE и защищёнными стратегиями. Общие границы безопасности и audit включены в обоих режимах. Для отдельного исследования стоимости политики backend фиксируют и меняют только OFF/OBSERVE/ENFORCE.

## 10. Как работает генератор сценариев

Runner получает готовый исполнимый план. В нём описаны actors, шаги, данные, последовательные/конкурентные группы, число повторов, допустимые ветвления и бюджет. Генератор не импровизирует по ответам, если такое поведение не предусмотрено версией сценария.

Внутри удобно разделить `PlanExecutor`, `StepExecutor`, bounded HTTP client, `LeaseClient` и `ResultPublisher`. PlanExecutor управляет порядком и barriers. StepExecutor превращает типизированный шаг в HTTP-вызов. HTTP client отвечает за allowlist, timeout, отсутствие redirects и предел ответа. ResultPublisher надёжно передаёт результаты control.

Для HTTP I/O используются virtual threads, но доступ ограничивается семафорами. Это важно: дешёвый поток не делает бесплатными DB connection, память тела ответа и вычисления backend. У задания есть предел attempts, concurrency, длительности и объёма данных.

Control выдаёт jobId/runId/epoch, target enum, plan/hash, budget, lease token и expiry. Lease — ограниченное по времени право продолжать работу. Runner подтверждает hash, присылает heartbeat и прекращает новые шаги при утрате lease. Потеря связи с control не должна создавать бесконечный поток запросов.

Один step может иметь несколько HTTP-attempts. AttemptId создаётся до отправки; requestId выдаёт gateway. Retry получает новый requestId, но для повторяемого checkout сохраняет прежние intent/key. Step result содержит время, method/route, transport outcome, status и безопасные response facts. Пароли/token остаются в памяти; результаты не содержат Authorization и исходного secret body.

Подготовка данных выполняется через control, а не SQL runner. Runner не имеет доступа к shop-admin, Redis или БД. Его targets — только два gateway origin; redirects и proxy отключены, а контейнерная сеть отдельно ограничивает egress.

CS-01 генерирует 200 попыток, среди которых три корректные пары разных аккаунтов. Для detection это одна кампания/episode, а для ASR — три case доступа к известным аккаунтам. Неверные пары не раздувают знаменатель заведомыми неуспехами. Для race фиксируются barrier, число потоков, repetitions и seed; интерливинг SQL может различаться, поэтому оценивается серия.

## 11. События и надёжная доставка

### Факт, инцидент и вывод — три разных объекта

SecurityEvent сообщает наблюдаемый факт: вход не удался, owner не совпал, policy заблокировала запрос, order создан. Incident — вывод detector, что один или несколько фактов соответствуют правилу подозрительного поведения. Assessment — независимая оценка control: какое нарушение действительно произошло и был ли incident правильным.

Это разделение принципиально. Если producer пишет в событие «здесь успешная атака BOLA», detector фактически получает готовый ответ. Если detector объявляет подтверждённый ущерб без доступа к независимому эталону, он смешивает гипотезу и доказательство.

События имеют CloudEvents envelope: specversion=1.0, id, source, type, time, datacontenttype, dataschema; предметные данные находятся в `data`. Внутри data находятся context, actor, request, action, outcome и observations. Context связывает run/partition/epoch/request/trace; actor содержит authenticated subject либо anonymous; request — method/route/sourceKey; outcome — фактический статус и причина.

Примеры типов: request.started/completed, policy.evaluated, auth.attempted, object.accessed, operation.completed, input.observed. Полные имена версионированы, например `lab.object.accessed.v1`. EventId создаётся один раз и сохраняется при повторной доставке. Неизвестное наблюдение передаётся как null, а не false; исходные passwords/JWT/query не копируются в event.

### Зачем нужен outbox

Shop изменяет бизнес-состояние в своей БД, а audit живёт в другой логической БД. Простая последовательность «commit заказа, затем отправка события» опасна: процесс может упасть между действиями, и созданный заказ останется без события.

Вместо этого бизнес-транзакция записывает заказ и строку `security_outbox` в одну БД. После commit отдельный publisher читает outbox и вставляет event в lab DB. Получив подтверждение, он отмечает delivered. Если процесс падает после вставки, но до отметки, publisher отправит то же eventId ещё раз, а unique key исключит повторное сохранение факта.

Таким образом доставка допускает повторы; логическая обработка идемпотентна. Это не обещание магического end-to-end exactly-once. Ошибка одного и того же id с другим payload считается нарушением целостности, а не безобидным retry.

Read-only чтение и отказ тоже имеют audit. Событие успешной mutation входит в её транзакцию; после rollback событие отказа сохраняется отдельно, иначе оно откатилось бы вместе с операцией. Publisher работает с ограниченными batch/backoff и не удаляет недоставленные события.

### Как увидеть потерянное завершение

Gateway до downstream сохраняет receipt — долговечную запись, что запрос принят. Shop ведёт execution ledger: начатые и завершённые операции. После crash пустой счётчик JVM ничего не доказывает; незавершённая ledger row остаётся поводом проверить, был ли commit/rollback.

На завершении producer фиксирует manifest: точный набор event IDs, count/hash, принятые и завершённые requests. Manifest — опись доказательств. Один hash фактически полученных событий недостаточен: нужно ещё проверить, что для каждого принятого request есть требуемый terminal outcome. Иначе одинаковые списки могут быть одинаково неполными.

Audit хранится независимо от LGTM. Retention/cleanup не удаляет необработанные события; переполнение очереди или размера evidence не превращается в тихое отбрасывание. Неполнота видна в состоянии run.

## 12. Как устроен detector

### Какие данные ему разрешены

Detector читает `audit.detector_observations`, специально построенную SQL-view. Она содержит event type/time, opaque partition, producerKind GATEWAY/SHOP, route, actor/source keys и разрешённые observations/outcomes. Raw source вроде `shop:vulnerable` нормализуется, чтобы не раскрывать target mode.

В view нет scenario/case/step labels, ожидаемого эффекта, именованного backend, fixture annotations, policy mode и oracle results. RequestId/trace используются для evidence и дедупликации, partition — для разделения состояния; YAML не сравнивает эти технические идентификаторы с литералами для распознавания класса атаки.

Это ограничение enforced правами PostgreSQL, а не только аккуратностью Java DTO. Runtime-role detector не читает base audit, control schema или shop DB. Даже ошибочный запрос из detector не должен получить ground truth.

### Обработка внутри процесса

Предлагаемые обязанности: `ObservationReader` выбирает необработанные события; `RuleEngine` проверяет whitelist правил; `WindowStateRepository` хранит состояние групп/окон; `IncidentRepository` сохраняет результат и evidence; `DetectionJobWorker` выполняет PREPARE/CLOSE и подтверждает завершение.

MVP использует три формы правил: match одного события, countWindow и именованные Java kinds для более сложных последовательностей. Например, `subjectMatchesOwner=false` — непосредственный сигнал; серия auth failures по source — оконный; failures с последующим success — последовательность.

YAML допускает eq/in, count/countDistinct, groupBy и bounded window. Нет arbitrary JavaScript/SpEL/SQL. Неизвестное поле/operator останавливает подготовку. Ruleset имеет version/hash/engine version; пределы числа групп, длительности окна и evidence фиксируются вместе с ним.

Для checkout правило считает разные orderId по intent/cart revision только при stateChanged=true. Cached retry не создаёт новый эффект и не должен увеличивать этот счётчик. Отдельный conflict может указывать на попытку replay, но не доказывает её успешность. Правила на gateway refusal дополняют анализ попыток, которые вообще не достигли shop.

### Повторы, поздние события и окна

Для каждого event есть processed marker `(partition, rulesetHash, eventId)`. Изменение rule state, incident/evidence и marker фиксируется одной транзакцией. Crash до commit приводит к повторной обработке, после commit — к обнаружению существующего marker.

Выборка ищет отсутствие marker, а не только `id > lastSeen`. Пример: транзакция A получила id 101 и задержалась, B получила 102 и завершилась. Consumer увидел 102. Если он навсегда передвинул watermark на 102, поздний commit 101 потеряется. Anti-join по markers сохраняет возможность его обработки.

Окна строятся по времени события; одинаковое время упорядочивается eventId. Позднее событие может изменить вывод, поэтому state хранится в ограниченном буфере и нужное окно пересчитывается. На partition работает один worker с DB lease; масштабирование на множество concurrent consumers не требуется первой версии.

Live incident сначала PROVISIONAL. После команды CLOSE detector получает полный безопасный список event IDs, обрабатывает его, закрывает окна и делает результат FINAL. Если предварительный вывод больше не подтверждается, он становится RETRACTED; история не стирается. Метрики используют только FINAL.

### Содержимое incident

Incident содержит id/partition, category/technique, severity, rule/ruleset/engine versions, время обнаружения, analysisState, event/request evidence и безопасное объяснение. Предполагаемый impact имеет SUSPECTED/UNKNOWN. Числовая confidence в MVP null; severity не является вероятностью.

Статус работы оператора хранится отдельно: OPEN → ACKNOWLEDGED → RESOLVED, комментарий и revision. Закрытие оператором не превращает FP в TP. Control позже добавляет независимый IncidentAssessment; у пропуска нет реального incident, поэтому FN хранится на episode.

## 13. Control, evaluator и пользовательский интерфейс

Control объединяет четыре связанные функции: управление экспериментом, подготовку фикстур, независимую оценку и представление результата. Их не нужно превращать в четыре отдельных сетевых сервиса, но внутри Java-приложения они остаются разными модулями.

`ExperimentService` принимает конфигурацию и создаёт definition. `RunCoordinator` управляет состояниями и командами компонентов. `FixtureCoordinator` готовит исходные данные. `EvaluationService` запускает независимые проверки. `ReportAssembler` соединяет результаты без изменения фактов. UI-контроллеры отвечают только за формы, фильтры и выдачу отчёта.

| Сущность | Значение |
|---|---|
| Definition | Неизменяемое описание выбранных scenarios, targets, seeds и конфигураций |
| Experiment | Запрос выполнить definition; может включать несколько runs |
| Run | Один target, отдельные данные/epoch/partition и исполнение плана |
| Case | Один критерий достижения цели атакующего и применимые инварианты |
| Episode | Заранее выделенная последовательность для оценки обнаружения |
| Step / attempt | Плановое действие / конкретная HTTP-отправка |
| Snapshot | Зафиксированные данные или конфигурация, используемые в этом run |
| Ground truth | Приватные ожидаемые свойства: кто owner, какие шаги malicious, какие эффекты допустимы |

Ground truth создаётся до запуска. Например, evaluator знает, что order 123 принадлежит пользователю 8 и что шаг Бориса пытается прочитать именно его. Это знание хранится в control schema и не передаётся detector. Для расчёта результата evaluator получает readonly state shop и безопасные response facts, но не вызывает защищаемый calculator как «эталон правильного ответа».

Разделяются effect и invariant verdict. EFFECT_OBSERVED означает достижение заданной цели; EFFECT_NOT_OBSERVED — доказанное отсутствие эффекта; ERROR/INCONCLUSIVE — техническую проблему или недостаток доказательств. Отдельный инвариант имеет HELD/VIOLATED/NOT_APPLICABLE. Первая корректная пара credentials может дать EFFECT_OBSERVED при корректной password/JWT-проверке: сильная гарантия против такой кражи в MVP не заявлена.

UI показывает experiments/runs, progress и причину неполноты, incidents с фильтрами, evidence timeline, decisions и assessment. Для missed episode есть карточка без выдуманного incident. Отчёт содержит versions/hashes, условия сравнения, цели/исходы, метрики со знаменателями и остаточные риски. JSON-export обязателен, Markdown дополнительный. Готовый report immutable; пересчёт создаёт новую revision, operator notes хранятся отдельно.

Operator authentication, CSRF, escaping и пагинация входят в минимальный UI. Сценарный текст никогда не интерпретируется как HTML. Grafana служит диагностике; число WARN в логах не становится метрикой качества detector.

## 14. Жизненный цикл опыта и служебный протокол

Оператор задаёт имя, версии сценариев, targets VULNERABLE/PROTECTED, seed, fixtureVersion, policyProfile, rulesetVersion, parallelism и repetitions. Произвольный baseUrl, callback, Java-код и SQL assertion не принимаются. Настройки валидируются и превращаются в immutable definition/manifest.

Основные команды control доступны через `/control/v1/experiments` и `/control/v1/runs/{runId}`: create, start, status, cancel и report. Control передаёт runner PREPARE/START/CANCEL через отдельный internal listener; runner возвращает heartbeat/results через scoped worker listener. Gateway/shop принимают PREPARE/OPEN/CLOSE/SEAL/RESET. Detector получает PREPARE/CLOSE/CANCEL через таблицу jobs.

Команда содержит schemaVersion, commandId, runId, epoch и ожидаемую state/revision. Повтор commandId с тем же payload безопасен; с другим — conflict. HTTP 202 означает принятие, а окончание подтверждается состоянием/ACK. Epoch обозначает поколение работы: запоздавшая команда прошлого run не может открыть admission или сбросить новые данные.

Нормальные состояния:

```text
CREATED -> PREPARING -> RUNNING -> DRAINING -> EVALUATING -> COMPLETED
```

- В PREPARING закрывается старый доступ, проверяется отсутствие операций, загружаются фикстуры, проверяются baseline invariants и фиксируются snapshots. Detector возвращает READY, runner подтверждает planHash.
- В RUNNING открыт admission, runner исполняет план, политики применяются, события доставляются, detector создаёт предварительные выводы.
- В DRAINING новые действия прекращаются и доказывается завершение всех уже принятых.
- В EVALUATING независимый oracle и сопоставление incidents формируют окончательный report.

FAILED означает технически невыполненную подготовку/работу, CANCELLED — отмену, INCONCLUSIVE — недоказанный исход или неполноту. Достоверно успешная атака против protected тоже может дать COMPLETED: опыт завершён, просто защита не выдержала проверку. Любой выход из RUNNING проходит остановку и DRAINING; terminal state сам по себе не разрешает reset, если cleanupSafe=false.

Сравнение состоит из последовательных paired runs. Данные, workload, seed, бизнес-время, concurrency и ruleset одинаковы, а режим цели и выбранные механизмы защиты различаются. Порядок vulnerable/protected чередуется в повторениях. Одновременная нагрузка двух targets на одном ноутбуке затруднила бы сравнение latency из-за конкуренции за общие ресурсы.

### Почему недостаточно дождаться последнего ответа runner

Пусть клиент получил timeout через пять секунд, а SQL-транзакция ещё выполняется. Если немедленно посчитать заказ отсутствующим и сбросить данные, поздний commit может одновременно исказить отчёт и следующий опыт. Аналогичная проблема возникает, если последний event ещё лежит в outbox или detector не закрыл окно.

Поэтому завершение имеет явный барьер:

1. Runner прекращает новые steps и передаёт manifest выполненных attempts.
2. Gateway/shop закрывают admission текущего epoch, включая задержавшиеся запросы.
3. Ledger/receipts и runtime state подтверждают отсутствие незавершённых работ — состояние quiescence.
4. Producers запечатывают набор events; outbox доставляется, проверяются IDs и terminal coverage.
5. Detector обрабатывает полный безопасный manifest, закрывает окна и подтверждает hashes/counts/errors.
6. Control снимает итоговое состояние, выполняет oracle и сохраняет report.

Каждая стадия имеет deadline. Неполнота не маскируется дополнительным ожиданием без ограничений: run получает INCONCLUSIVE. После crash сохранённые состояния позволяют продолжить reconciliation. Если завершение доказать нельзя, runtime останавливается и проверяются DB-сессии; только затем допускается reset. Поздние admission rejects старого epoch записываются вне запечатанного набора.

## 15. Как считаются результаты

Метрики считают заранее определённые случаи и последовательности. Один HTTP-запрос может породить gateway receipt, policy event, shop event и terminal event; это не четыре атаки.

| Метрика | Что означает и как считается |
|---|---|
| ASR | Доля malicious cases с EFFECT_OBSERVED среди полноценно оценённых cases |
| Detection recall | Доля malicious episodes с подходящим FINAL incident среди полностью наблюдённых malicious episodes |
| Incident precision | TP incidents / (TP + FP incidents): какая часть окончательных выводов правильна |
| Benign FPR | Доля benign episodes хотя бы с одним ложным incident |
| False block rate | Доля пригодных легитимных logical operations, ошибочно остановленных защитой |
| Detection delay | Время incident минус первое attack-specific evidence; live и final отдельно |
| Coverage | Сколько запланировано, выполнено и оценено; сколько пропусков данных/ERROR/INCONCLUSIVE |
| Performance | Latency percentiles, throughput, ошибки и ресурсы при фиксированном workload |

Recall включает предотвращённые попытки: атака может существовать, хотя ущерба нет. ASR не заменяет число нарушенных инвариантов; отсутствие эффекта не всегда является заслугой защиты. Нулевой знаменатель даёт N/A. Неполные случаи исключаются из основной доли с явным показом их численности и причин; итоговая пара требует двух COMPLETED runs.

Incident связывается с episode по evidence event → request → attack-specific step и правильному классу. Одного общего source/run или подготовительного login недостаточно. Несколько incidents дают один detected episode, но несколько элементов precision. Wrong class — FP; отсутствие подходящего incident — FN. UNASSESSED допускается только при объективно неполной или неоднозначной привязке.

Для гонок публикуются repetitions/seeds и число эффектов k/n. Коррелированные запросы одного episode не объявляются независимой статистической выборкой. Пороги качества и достаточное число повторов калибруются пилотом и фиксируются до итоговой серии; заранее обещанных универсальных процентов защиты нет.

## 16. Развёртывание, доступ к данным и отказы

### PostgreSQL и права

Один PostgreSQL обслуживает `shop_vulnerable`, `shop_protected` и `lab`. Первые две БД хранят независимые бизнес-состояния, третья — работу стенда. В lab schema `audit` хранит события/receipts/manifests, `control` — runs/steps/labels/oracle/reports, `detection` — jobs/markers/state/incidents.

Обычная shop-role имеет DML только собственной БД, без DDL/TRUNCATE. Catalog adapter использует отдельную SELECT-only роль, чтобы учебная SQL-слабость не давала доступ к пользователям или изменению данных. Audit writer может добавлять события только своего producer. Detector читает лишь безопасную view и пишет собственные результаты. Evaluator читает бизнес-состояние без password_hash. Fixture admin и migration owner используются отдельным служебным путём; их полномочия не выдаются runner.

Роли ограничиваются SQL grants и функциями/политиками записи, а не названием Java-сервиса. Общий PostgreSQL остаётся общей точкой отказа: логические БД не создают физическую отказоустойчивость. Для локального учебного стенда это осознанный компромисс.

### Сети

| Internal network | Участники и назначение |
|---|---|
| `lab-traffic` | Runner, gateway, LGTM collector: сценарный HTTP и telemetry |
| `worker-control` | Runner/control: задания, heartbeat, results |
| `shop-backend` | Gateway и оба shop: бизнес-запросы |
| `shop-admin` | Control/gateway/shop: подготовка, admission, завершение |
| `lab-data` | Control/detector/gateway/shop и PostgreSQL/Redis: хранилища |
| `lab-observe` | Control/detector/gateway/shop и LGTM: наблюдаемость |

Runner не получает сети shop-backend, shop-admin и lab-data. Отсутствие опубликованного host-порта само по себе недостаточно: контейнеры одной сети могут обращаться друг к другу. Поэтому listener binding и проверка credential обязательны. Worker listener control не предоставляет operator/reset/proxy endpoints.

На host по умолчанию публикуются только UI и Grafana через loopback. Для ручной демонстрации API допустим отдельный profile с loopback-входами gateway; прямой shop не публикуется. В runtime нет Docker socket, host network, privileged-контейнеров и внешнего proxy. Запрет egress проверяется настоящими запросами, включая внешний IP/hostname, host gateway, DNS/redirect и служебные endpoints.

### Инициализация и эксплуатация

Планируемая команда `docker compose -f infra/compose.yaml up --build` запускает локальную генерацию keys/credentials, миграции, seed и readiness. Health означает готовность работать с зависимостями, а не только поднятый JVM. В git входят versioned config и `.env.example` с placeholders; рабочие ключи лежат в локальном хранилище.

Fixture generator создаёт 24 синтетических пользователя с корзинами, 12 опубликованных товаров и draft canary, пять купонных состояний и согласованную историю заказов. Seed, бизнес-время, owners, counts и snapshots фиксируются. Пустые password hashes запрещены; реальные credentials не используются.

Цель готовности на чистой описанной машине — не более 10 минут с учётом загрузок; тёплый запуск измеряется отдельно. CPU/RAM, размер очередей, connection pools, длительность и объём evidence ограничиваются до опыта. Это требования к реализации, а не уже полученные результаты запуска.

### Поведение при сбое

| Ситуация | Что происходит |
|---|---|
| Detector остановлен | API работает при доступном audit; события накапливаются, после restart дочитываются; report ждёт CLOSE |
| Control/UI остановлен | Состояние остаётся в DB, runner прекращает новые шаги по lease; recovery начинает с reconciliation |
| Redis недоступен | Rate ENFORCE возвращает infrastructure reject; OBSERVE сообщает ошибку измерения политики |
| Lab DB недоступна | Новый downstream без durable receipt запрещён; финализация невозможна |
| Shop падает после commit | Order/key/outbox сохранены; прежний key позволяет восстановить ответ |
| Gateway теряет ответ backend | Исход устанавливается по receipt, shop ledger/outbox и состоянию |
| LGTM недоступен | Audit продолжает работать; техническая потеря telemetry отмечается отдельно |
| Закончился бюджет хранения | Новый admission закрывается; необработанные доказательства не удаляются |
| Quiescence не доказан | INCONCLUSIVE и cleanupSafe=false; reset откладывается до безопасного завершения runtime |

Логи JSON связываются requestId/traceId. OpenTelemetry продолжает причинную связь до async detector через span links. Операционные метрики включают latency/errors, policy time, outbox/detector lag, незавершённые receipts, lease expiry и report coverage. Redaction применяется и к ошибкам/HTTP-debug, чтобы секрет не появился обходным путём.

## 17. Принятые решения и их последствия

| Решение | Почему принято | Ограничение или цена |
|---|---|---|
| Один shop codebase, два процесса/DB | Один контракт и одинаковые нормальные операции облегчают сопоставление | Учебные слабости нужно явно изолировать стратегиями и миграциями |
| Магазин как модульное приложение | Checkout и купон помещаются в одну транзакцию | Нет исследования распределённой торговой транзакции |
| Отдельные gateway, runner, detector и control | Разделены HTTP-допуск, нагрузка, анализ и управление | Несколько процессов и явные служебные контракты |
| Detector отдельно от control | Ground truth закрыт SQL-полномочиями; анализ восстанавливается независимо | Р4 обслуживает два приложения; часть адаптеров распределена между остальными ролями |
| JDBC и PostgreSQL | Видны locking, условия UPDATE и транзакционные границы | Дисциплина SQL/индексов/rollback и реальные concurrency tests |
| Intent + idempotency в бизнес-DB | Различаются повторный результат и новая попытка прежней операции; атомарность едина | Дополнительные таблицы и двухшаговый checkout |
| SQL outbox и polling | Доказательство не теряется между бизнес-commit и доставкой; меньше инфраструктуры | Нужно обрабатывать duplicate/late events, backlog и recovery |
| Rule-based detector | Вывод объясняется конкретным правилом/evidence и воспроизводится | Нет обещания обнаруживать неизвестные паттерны или распознавать намерение по одинаковому HTTP |
| Immutable snapshots и paired runs | Известно, что именно сравнивается и с какими параметрами | Конфигурацию нельзя незаметно менять посередине опыта |
| DRAINING/manifests/CLOSE | Конечный отчёт основан на полном исполнении и анализе | Orchestration сложнее, чем запуск HTTP-скрипта |
| Thymeleaf, JSON-export, локальный LGTM | Достаточный интерфейс и диагностика при небольшом числе технологий | Дизайнерская SPA и PDF pipeline не являются частью MVP |
| Whole RUB и числовые ids | Простые точные вычисления и понятные сценарии объекта | Дробные цены не поддержаны; id не рассматривается как секрет |

Внешний authorization service имеет смысл при более сложных отношениях sharing/organization, а ML — при отдельном исследовании качества обнаружения. OpenFGA, Schemathesis и PyOD допустимы после baseline, с независимой оценкой и своими условиями сравнения. Они не нужны для доказательства пяти основных семейств первой версии.

## 18. Как команда реализует и проверит систему

### Четыре роли

| Роль | Основной результат | Помощь общей интеграции |
|---|---|---|
| Р1: API и данные | Shop в двух режимах, API/DTO, миграции, fixtures, transactions и outbox | Readonly данные и адаптеры независимого oracle |
| Р2: защита | Gateway, политики, JWT, limiter, audit | Compose/сети, admission/manifests, базовая наблюдаемость |
| Р3: генератор | Сценарии/benign, seed/планы, concurrency, HTTP execution | Job/lease/cancel и надёжная доставка step results |
| Р4: detector/dashboard | Rules/windows/incidents, control/evaluator, UI и reports | Общая семантика эксперимента и окончательных метрик |

API-контракт ревьюят Р1+Р2, события/политики — Р2+Р4, jobs/steps — Р3+Р4. Oracle проверяют Р1+Р3+Р4, чтобы ошибка production-логики не попала в независимый эталон. Вклад фиксируется по фактически выполненным модулям, тестам и демонстрациям.

### Порядок работ

Сначала создаются schemas и сборочный spike: совместимость зависимостей, validator keywords, Redis adapter и SQL grants. Затем поднимаются skeleton/сети/три DB, минимальные listeners и trace. Первый вертикальный результат — BO-01: свой/чужой order, запрос через gateway, audit, одно правило detector, независимый owner oracle и JSON-отчёт в UI.

После этого расширяется API, реализуются checkout/rate/injection и остальные сценарии с benign controls. Следующий этап посвящён достоверности: crash, late commit, duplicate/loss, lease/epoch, закрытие окон и reset. Завершают работу измерения paired series, cold start, нагрузка защитного слоя, документация реализации и демонстрация.

Такой порядок проверяет самые рискованные границы рано: команда видит всю цепочку доказательства до того, как написан полный магазин или сложный дашборд.

### Проверки

Unit tests проверяют чистые политики/parser/calculator. Contract tests проверяют реальные schemas, нормальные запросы обоих режимов, неизвестные поля/типы и errors. Testcontainers с PostgreSQL проверяет row locks, coupon/cart races, уникальность, rollback и SQL grants. State model с jqwik генерирует последовательности add/change/coupon/intent/checkout/retry и сравнивает их с независимой моделью.

Integration suite включает JWT claims/signature, BOLA profile/order, все варианты повторов checkout, expiry equality, server-price и canary injection. Audit tests моделируют падение между commit/delivery/ack, конфликт eventId и отсутствие terminal event. Detector tests проверяют late/out-of-order events, atomic state/marker и CLOSE/retraction. Сетевые проверки подтверждают отсутствие обхода gateway, а secret scans/escaping tests — отсутствие утечки или интерпретации входа в UI.

Планируемые команды: `./mvnw verify` для основной сборки/unit/integration/smoke и `./mvnw -Pacceptance verify` для полной серии с фиксированными seeds/budgets и reports. Эти же команды запускаются в CI. Protected-инвариант, нарушенная изоляция, утрата обязательного evidence или невоспроизведённый vulnerable baseline не дают успешную приёмку. Объявленный остаточный риск, например первая корректная пара, оценивается по фактической гарантии.

### Результат сдачи

Команда предоставляет воспроизводимый локальный стенд, исходный код, актуальную архитектуру/контракты, автоматические тесты и сохранённые отчёты, сценарий либо видео демонстрации и фактический вклад участников. На демонстрации показываются BOLA, безопасный retry и race, все пять семейств с benign traffic, восстановление detector, INCONCLUSIVE при потере доказательства и экспорт сравнения.

Граница завершённого MVP — возможность повторить опыт и объяснить его результат по сохранённым фактам, конфигурациям и независимым проверкам. Это проверяемое свойство реализации; наличие выбранного framework, diagram или контейнера само по себе его не подтверждает.
