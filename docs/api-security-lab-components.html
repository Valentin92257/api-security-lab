Подробная архитектура локального учебного стенда. Защита выполняется в gateway и API, обнаружение - отдельным detector, управление и независимая оценка - в control со встроенным runner.

Как читать связи

Голубые линии - сценарные HTTP-вызовы, серые - SQL и поток данных. LogBatch поступает из Gateway/Shop напрямую в Detector; верхний блок логов показывает доставку, нижний - обработку. LOG STORAGE и INCIDENTS - собственное хранение Detector. FINAL INCIDENTS - HTTP-ответ Control, не чтение чужой БД. Полный набор административных и readonly SQL-вызовов опущен.

Управление и отчёт

Orchestrator готовит фикстуры напрямую в shop DB через отдельный модуль Control, открывает/закрывает Runtime-контексты и управляет анализом через Detector API. Сценарии выполняются внутри Control. Лимиты хранятся внутри Gateway, отдельно для runId/mode. Restart прерывает опыт; несколько реплик Gateway не поддерживаются. Evaluator использует приватный baseline, attempts/ответы, итоговые incidents и readonly Shop. Отдельного сервиса отчётов нет.

Что именно изолировано

Один код Shop запускается дважды с независимыми БД. PostgreSQL обслуживает бизнес-данные и внутреннее хранение стенда; общая физическая lab-схема не является контрактом. Detector не получает credentials Shop/Control, producers отправляют логи по HTTP. У встроенного Runner общие права JVM Control: ограничения интерфейсов и клиента проверяются кодом и тестами, а не выдаются за контейнерный sandbox.

Завершение опыта

Stop Runner → сохранить attempts → закрыть Gateway и дождаться CLOSED → закрыть Shop и дождаться CLOSED → finish с обоими lastSequence → COMPLETED Detector → сверить observedRequestIds/получить incidents → readonly oracle → отчёт. Commit и лог не атомарны. Сбой, restart или неполнота дают INCONCLUSIVE, продолжения старого run нет.
