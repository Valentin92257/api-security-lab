# Модель угроз: описание обязательных сценариев

## 1. Назначение и границы

Документ описывает пять обязательных семейств угроз для учебного API интернет-магазина: credential stuffing, BOLA/IDOR, replay, injection и злоупотребление бизнес-логикой. Для каждого семейства зафиксированы точка входа, ожидаемое нарушение в режиме `vulnerable`, мера защиты в режиме `protected` и остаточный риск.

Обе версии API должны получать одинаковые исходные данные и запросы. Успех атаки определяется не HTTP-статусом и не сообщением runner, а фактическим нарушением инварианта ответа или состояния БД. Проверку выполняет независимый evaluator по синтетическим fixtures и снимкам состояния до/после.

### Допущения о нарушителе

- Нарушитель обращается к API только через предусмотренную точку входа стенда.
- Он может действовать без авторизации, со своей тестовой учётной записью или с известной синтетической парой логин/пароль.
- Он знает публичный контракт API и может подбирать предсказуемые идентификаторы объектов.
- У него нет прямого доступа к БД, ключу подписи JWT, служебному API сброса данных и ожидаемым результатам evaluator.
- Компрометация Docker-хоста, реальных учётных данных и внешних систем находится вне границ проекта.

## 2. Сводная матрица угроз

| Семейство | Точка входа | Ожидаемое нарушение в `vulnerable` | Мера защиты в `protected` | Остаточный риск |
|---|---|---|---|---|
| Credential stuffing | `POST /auth/login`, поля `login` и `password`, источник запроса | После серии попыток выдан JWT синтетической учётной записи, вход в которую должен был быть ограничен политикой | Совместные лимиты по аккаунту и источнику, cooldown/задержка после ошибок, журналирование и независимое правило detector | Первая верная украденная пара или медленная распределённая кампания может пройти; MFA не входит в MVP |
| BOLA/IDOR | `GET /users/{userId}` и `GET /orders/{orderId}` с JWT другого пользователя | Возвращены защищаемые поля чужого профиля или заказа | Principal только из проверенного JWT; выборка по `id` и `owner_id`; одинаковый `404` для чужого и отсутствующего объекта | Проверку можно забыть в новом endpoint; скомпрометированный JWT владельца остаётся действительным до истечения/отзыва |
| Replay | Повтор мутирующего запроса, прежде всего `POST /orders`, с теми же JWT, телом и `X-Request-Nonce` | Повторно создан заказ, повторно списан купон или иначе дважды выполнен один бизнес-эффект | Одноразовый nonce с ограниченным сроком, атомарная регистрация повтора, блокировка/версионирование корзины и единая транзакция checkout | Украденный bearer-токен можно применить к новой операции с новым nonce; сбой или рассинхронизация хранилища nonce может открыть окно повтора |
| Injection | Строковый параметр поиска/фильтра каталога в `GET /products` | Ввод меняет смысл SQL-запроса и добавляет в выдачу seeded canary-товар, который не соответствует нормальному фильтру | Параметризованный SQL, allowlist динамических полей, OpenAPI-валидация типов/длины и минимальные права роли каталога | Покрывается один контролируемый SQL-сценарий; second-order и неизвестные классы injection вне выбранного адаптера остаются возможными |
| Business logic abuse | `POST/PATCH /cart/items`, `PUT /cart/coupon`, конкурентные `POST /orders`, поле `quotedTotal` | В состояние попадает недопустимое количество; применяется просроченный/исчерпанный купон; создаются два заказа; принимается заниженная цена | Серверный расчёт цены, проверки схемы и домена, ограничения БД, условное атомарное списание купона, транзакция и защита checkout от повтора/гонки | Стенд не обнаруживает правила, которых нет в формальной модели магазина; возможны гонки в новых переходах состояния и формально разрешённое, но нежелательное использование |

## 3. Детализация сценариев и критериев успеха

### 3.1. Credential stuffing

**Точка входа.** Неавторизованный `POST /auth/login` с синтетическим списком пар логин/пароль. Кампания содержит неверные попытки и как минимум одну известную корректную пару. Учитываются идентификатор аккаунта и нормализованный источник запроса.

**Ожидаемое нарушение.** В `vulnerable` атакующий получает JWT fixture-пользователя после количества ошибок, превышающего установленный порог. Критерий успеха — не только ответ `200`, а возможность использовать выданный JWT для чтения профиля соответствующего пользователя.

**Мера защиты.** `protected` ограничивает кампанию одновременно по аккаунту и источнику, вводит cooldown или задержку после серии неудач и записывает причины `allow`/`block`. Detector независимо агрегирует неудачные входы и создаёт инцидент, даже если верная пара всё-таки сработала.

**Остаточный риск.** Rate limit не доказывает владение аккаунтом: корректная пара на первой попытке или достаточно медленная распределённая кампания может пройти. MFA и проверка скомпрометированных паролей являются более сильными мерами, но не входят в MVP.

**Легитимный контроль.** Одна опечатка с последующим корректным входом до порога, а также несколько обычных пользователей за одним источником не должны приводить к ложной блокировке.

### 3.2. BOLA/IDOR

**Точка входа.** Авторизованный пользователь B подставляет идентификатор пользователя A в `GET /users/{userId}` или идентификатор заказа A в `GET /orders/{orderId}`.

**Ожидаемое нарушение.** `vulnerable` выбирает объект только по `id` и возвращает чужие защищаемые поля. Для профиля проверяется раскрытие имени/email, для заказа — состава, суммы, купона и владельца. Один лишь статус `200` без чужих данных не считается доказательством.

**Мера защиты.** `protected` извлекает principal только из проверенного JWT и выполняет object-level authorization там, где загружается объект: запрос ограничивается одновременно `id` и `owner_id`. Чужой и отсутствующий объект дают одинаковый `404`, чтобы не создавать дополнительный канал перечисления.

**Остаточный риск.** Локальная проверка не защищает endpoint, в котором её забыли вызвать. Поэтому нужна полная матрица `subject × resource × action` и regression-тесты для каждого нового чтения и изменения. При краже действительного JWT запросы владельца внешне неотличимы без дополнительных механизмов.

**Легитимный контроль.** Пользователь читает собственные профиль и заказ; запрос неизвестного ID возвращает тот же публичный результат, что и запрос чужого объекта.

### 3.3. Replay

**Точка входа.** Повтор ранее принятого мутирующего запроса с теми же JWT, телом и `X-Request-Nonce`; основной сценарий — `POST /orders`. Отдельно проверяется одновременная отправка двух копий.

**Ожидаемое нарушение.** `vulnerable` выполняет одну логическую операцию более одного раза: создаёт второй заказ, повторно увеличивает `used_count` купона либо применяет иной повторный бизнес-эффект. Критерий успеха определяется снимком БД, а не порядком HTTP-ответов.

**Мера защиты.** `protected` атомарно регистрирует nonce в контексте пользователя и операции, ограничивает срок его действия и отклоняет повтор. Checkout блокирует или версионирует корзину и в одной транзакции создаёт заказ, фиксирует цены, списывает купон и очищает корзину. При конкурентном повторе допустим только один бизнес-эффект.

**Остаточный риск.** Access JWT по своей природе многократно используется до истечения срока: запрет каждого повторного `jti` сломал бы обычный клиент. Поэтому защита относится к конкретной операции. Обладатель украденного bearer-токена всё ещё может сформировать новую допустимую операцию с новым nonce. В распределённой реализации отказ хранилища nonce требует явно выбранного fail-safe поведения.

**Легитимный контроль.** Разные операции с разными nonce выполняются независимо. Технический retry не должен создавать второй эффект; контракт должен явно выбрать возвращение прежнего результата либо детерминированный конфликт.

### 3.4. Injection

**Точка входа.** Контролируемая строка поиска или фильтра каталога в `GET /products`. Для воспроизводимого сценария OpenAPI-контракт должен явно определить такой query-параметр; без него необходимо выбрать другой конкретный строковый ввод и зафиксировать его до реализации runner.

**Ожидаемое нарушение.** В `vulnerable` один изолированный catalog adapter собирает SQL конкатенацией строки. Специальное значение изменяет условие выборки и добавляет в результат seeded canary-товар, который не соответствует нормальному фильтру. Выполнение shell-команд или добавление отдельной NoSQL-БД для MVP не требуется.

**Мера защиты.** `protected` использует параметризованные запросы, фиксированный allowlist для имён сортировки/полей, ограничения длины и типа по OpenAPI. Роль БД каталога имеет минимальные права только на необходимые синтетические таблицы.

**Остаточный риск.** Валидация схемы не заменяет параметризацию. Один SQL-сценарий не доказывает отсутствие injection во всех адаптерах, динамических запросах или последующих преобразованиях сохранённых данных. Неизвестные классы и second-order injection требуют отдельного покрытия.

**Легитимный контроль.** Апострофы, кавычки, дефисы и Unicode в обычных поисковых строках трактуются как данные и не блокируются только из-за присутствия специальных символов.

### 3.5. Злоупотребление бизнес-логикой

Это одно семейство угроз с четырьмя обязательными подслучаями.

| Подслучай и точка входа | Ожидаемое нарушение | Мера защиты | Остаточный риск |
|---|---|---|---|
| Купон: `PUT /cart/coupon` и последующий `POST /orders` | Применён просроченный/исчерпанный купон, превышен `max_uses` или один лимит списан несколько раз | Серверное время; один купон на заказ; условный атомарный `UPDATE`; `CHECK`; списание в транзакции checkout | Новые промо-правила не защищены автоматически; корректный код купона может распространяться шире ожидаемого |
| Количество: `POST /cart/items` и `PATCH /cart/items/{productId}` | Сохранено `quantity <= 0` либо значение вне установленного диапазона | OpenAPI-ограничение, доменная проверка и независимый `CHECK` в БД | Несогласованные пределы между контрактом, кодом и БД; переполнение в производных расчётах |
| Гонка checkout: два конкурентных `POST /orders` | Для одной корзины создано более одного заказа или купон списан более одного раза | Блокировка/версия корзины, уникальность операции, атомарная транзакция и повторная проверка состояния | Гонки в новых переходах заказа или при появлении внешних эффектов вне транзакции |
| Обход цены: поле `quotedTotal` в `POST /orders` | Заказ сохранён с суммой ниже серверного расчёта | Цена и скидка вычисляются на сервере по актуальным товарам/купону; несовпадение даёт `409 PRICE_CHANGED` либо требует нового подтверждения | Формально корректное злоупотребление скидками, если соответствующего ограничения нет в модели |

Evaluator после каждого подслучая проверяет committed-состояние: количество заказов, `total`, `quantity`, `used_count` купона и состояние корзины. Ошибка `500`, timeout или недоступная БД дают `ERROR/INCONCLUSIVE`, а не успешную защиту.

## 4. Требования к сравнению и отчёту

- Для одного case используются одинаковые fixtures, seed и последовательность шагов в `vulnerable` и `protected`.
- Предотвращение, обнаружение detector и фактическое нарушение инварианта отражаются отдельно.
- У каждого malicious case есть близкий benign case для оценки ложных блокировок и false positives.
- События не передают detector готовую метку атаки как признак; ground truth хранится у runner/evaluator.
- В отчёт не попадают пароли, JWT, nonce и другие секреты.
- Сценарий считается завершённым только после проверки ответа и, для мутаций, committed-состояния БД.
